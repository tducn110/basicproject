[7523:7547] CHAPTER 1. INTRODUCTION
[7547:7577] 1.1 Background and motivation
[7577:8183] Caro is a two-player placement game in which a small set of rules produces a large adversarial decision space. A player places one stone on an empty cell, attempts to complete a winning line and must anticipate the opponent's reply. The board representation is simple enough to implement explicitly, while the number of possible move sequences makes exhaustive search impractical beyond shallow depths. This combination makes the project suitable for studying data structures, recursive search, evaluation functions, pruning and the relationship between algorithmic results and an interactive application.
[8183:8871] The project develops both a playable web application and material for explaining its algorithms. In the application, React supplies the surrounding interface, Pixi renders the board and a controller coordinates accepted moves, match state and AI requests. The AI path combines a TypeScript tactical check with a Worker-based WebAssembly engine. The repository also preserves a TypeScript search implementation, native Rust benchmark programs, baseline Rust engine code, weekly research reports and a separate presentation website. These modules form a cohesive architecture spanning interactive gameplay, WebAssembly search execution, and reproducible algorithmic benchmarks. [1] [2] [3]
[8871:9431] The practical problem is to return a legal and useful move while maintaining coherent application state. A search that produces a high score is insufficient if it changes the caller's board, uses an incompatible win rule, blocks interaction unnecessarily or commits a result after the user has reset the round. The report therefore considers both the mathematical search problem and the application boundary at which a result becomes a move. It also distinguishes an observed counter from a configured limit and a native experiment from a browser measurement.
[9431:9469] 1.2 Objectives and research questions
[9469:10071] The first objective is to specify the actual game rules and state transitions. A 15 × 15 board and a five-stone target do not uniquely define a Caro variant. The application's Freestyle rule accepts a contiguous line of at least five stones, including longer lines. Its implementation is explained from the last-move scan, with the assumptions under which that local test is valid. The second objective is to specify the AI algorithms precisely: their inputs, outputs, recurrence or decision policy, candidate membership, state mutation and restoration, stopping conditions and computational cost. [4]
[10071:10649] The third objective is to connect those algorithms to the implementation. The report identifies which component owns the board, who may commit a move, how history is replayed into the Rust/WASM object and how stale responses are rejected. The fourth objective is to evaluate the published experiment records without turning limited measurements into universal claims. In particular, it asks whether Minimax and Alpha-Beta agree on the same selected tree, whether ordering reduces total work or only visited nodes, and whether a cap can discard an immediate tactical completion.
[10649:11318] These objectives lead to four research questions. RQ1 asks how legal board state and the Freestyle win condition can be represented and checked deterministically. RQ2 asks how evaluation, candidate generation and adversarial recursion produce a move, and which assumptions preserve correctness. RQ3 asks how pruning, ordering and caching affect the measured search, including counterexamples and context hazards. RQ4 asks how the native and browser components preserve a consistent game when requests are asynchronous. The evaluation chapter answers each question using the corresponding source implementation, mathematical invariants, and empirical benchmark records.

[16663:16706] 2.2 Board representation and legal updates
[16706:16758] 2.2.1 Matrix, index conversion, and state ownership
[16758:17988] A position consists of 225 cells, each containing empty, X or O. In an array indexed as B[y][x], row-major conversion to a flat logical index is i = 15y + x; the inverse is x = i mod 15, y = floor(i/15). Hence the center (7,7) has index 112, and (14,14) has index 224. The system divides board representation across three specialized structures according to architectural role: (1) the Rust search engine (Board) stores a contiguous 15 × 15 grid of 225 one-byte repr(u8) cells (Empty = 0, Black = 1, White = 2) paired with move_count; (2) the match wrapper (Game) and frontend (GameState) store match progression and an ordered Move history; and (3) the legacy TypeScript bot (BotBoard) uses a 1D sentinel-padded array with directional bitmask segments. The rationale for this division is to decouple high-frequency recursive search from match-lifecycle management. Its primary benefit is O(1) direct indexing, O(1) in-place apply/undo during depth-first search, zero per-node heap allocation, and compact L1-cache locality; the trade-off is that the raw 225-cell matrix does not record chronological move order, requiring the outer Game/GameState layer to maintain history and full-board unindexed scans to take O(N²) time [13].
[17988:18557] The archived Rust place excerpt validates bounds, rejects an empty stone, rejects an occupied cell, writes a cell and increments a move counter. The companion undo rejects an out-of-range or already-empty cell and otherwise clears it and decrements that counter [6]. Dividing responsibility between low-level cell mutation (Board::place and Board::undo) and match-level legality (Game::play_move and GameController) keeps inner-loop search operations lightweight while ensuring that turn alternation and post-win lockouts are strictly enforced on committed game moves.
[18557:19256] A board and a game are different state owners. Cells and the count describe the position; turn, winner, and move history describe the match's progression. A history provides the information needed to restore actual game moves in reverse order. A recursive search temporarily changes a working board to explore alternatives, which must not silently become the player's actual move. The documented Rust search makes a copy at its outer entry, while its in-place search relies on restoration of the working board [6]. Cloning the root board once per search request isolates exploratory tree mutations from the live game state, while in-place apply and undo avoid O(N²) board copying at internal nodes.

[19351:19372] 2.2.2 Apply and undo
[19372:19823] Inputs and output. APPLY(B,m,p) takes the working board, a coordinate and a nonempty player; it returns success or failure. UNDO(B,m) takes the coordinate of a previously applied move and returns whether removal was possible. An individual undo that merely removes an occupied cell does not enforce the whole history discipline.

[20418:20908] The finally in this explanatory version means every normal return, cutoff and supported abort must pass through restoration. [20908:21516] Invariant and argument. Immediately before exploring each sibling, the working state must equal the state at the parent node. A successful apply changes exactly the selected empty cell and increments the count. Its matching undo clears that same cell and decrements the count; therefore these fields equal their former values. By induction over nested calls, assuming each recursive child restores every state field it owns, the parent sees the same state for the next sibling. The induction depends on legal matching calls; it is not guaranteed if an exception bypasses undo or a different move is removed.
[21516:22234] For example, let X occupy (7,7), O occupy (8,7), and the count be two. Trying X at (7,8) changes that cell and makes the count three. Undoing (7,8) returns both the cells and count to their initial values. Clearing the cell but leaving count three makes fullness checks unreliable; decrementing without clearing contaminates the next branch. With direct indexing, each operation is O(1) time and O(1) auxiliary space; copying an N × N board costs O(N²). Rejecting an occupied or out-of-bounds move must leave the board unchanged. Together with the inductive restoration invariant, automated root-restoration checks across 820 engine search runs confirm that the working board is returned unchanged after every search.

[22355:22383] 2.3 Freestyle win detection
[22383:22828] The frontend win rule treats a contiguous line of at least five stones as a win, including an overline of six or more. It checks four axes through the last move, with both directions on each axis. It does not require exactly five or impose an additional two-blocked-ends condition [4]. The term Caro is used for the application, but this particular rule is specified explicitly because games with similar names may use other winning conditions.
[22828:23411] Inputs, outputs and preconditions. The procedure takes a board and the last placed coordinate m, and returns the winner and a collection of winning cells when a qualifying line is found, or no result otherwise. It assumes m refers to the move that may have just caused the transition. If the board was already won before that move, testing only a line through m cannot detect every earlier win. A root-level validation of an arbitrary imported board needs a separate full-board check. The current frontend rule reads the player at m; an empty or invalid location produces no winner.
[23411:23877] For directions D = {(1,0), (0,1), (1,1), (1,-1)}, let f_d and b_d count consecutive stones equal to the stone at m in the positive and negative direction. A win through the last move occurs exactly when some 1 + f_d + b_d ≥ K. To decide whether the threshold is reached, scanning at most K−1 matching cells in each direction is sufficient: any additional cells cannot change a negative result to a positive result after K−1 matching cells already exist on one side.

[24334:24998] The scan invariant is that every collected cell is on the selected axis, adjacent to the preceding segment and occupied by p. Stopping at the first boundary or different cell prevents joining disconnected sequences. If a contiguous run through m has length at least K, either its collected positive and negative portions together reach K−1 neighbors or a single portion does, so the check succeeds. Conversely, K collected stones form a contiguous same-player segment through m, establishing the stated rule. The returned display collection may be truncated to K−1 stones per side; it is sufficient to prove a win but is not necessarily the full maximal overline.
[24998:25997] Consider X X [X] X X on one row with the bracketed center as the last move. Each side contributes two; 1+2+2=5. For X X X [X] X X, the value exceeds five and remains a win. An empty last cell returns no winner; a gap interrupts the run; edge and corner scans stop safely. Why last-move 4-axis ray scanning is used: because any newly formed winning line in an ongoing game must pass through the stone m just placed, scanning at most K − 1 = 4 steps in both directions (+1 and −1) along the 4 axes D = {(1,0), (0,1), (1,1), (1,−1)} inspects at most 4 × 2 × 4 = 32 neighboring cells. Benefits and trade-offs: this reduces terminal win detection at every recursive search node from an O(N²) full-board scan (225 × 4 = 900 directional checks) to O(K) = O(1) time and O(K) space, yielding a major speedup inside Minimax and Alpha-Beta; the trade-off is that it relies on the inductive invariant that no prior move had already won, so arbitrary imported positions require a one-time O(N²) root validation.

[26090:26137] 2.4 Baselines: random play and rule-based play
[26137:26159] 2.4.1 Random baseline
[26159:26607] A random baseline makes the meaning of added search explicit: it selects without comparing a tree of future replies. The documented Rust baseline first checks for a terminal position or an invalid empty player; for Easy it gathers legal empty cells, uses a seeded pseudo-random value modulo the number of cells, and evaluates the resulting move for the returned result. That evaluation occurs after selection and does not choose the Easy move [6].
[26607:26700] // Algorithm 2.3 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — RANDOM_MOVE(B, p, seed):
[26700:26748]     if p is empty or B is terminal: return NONE
[26748:26783]     L ← all legal empty cells in B
[26783:26814]     if L is empty: return NONE
[26814:26857]     i ← SEEDED_INTEGER(seed) mod length(L)
[26857:26873]     return L[i]
[26873:27462] The input includes the seed because pseudo-random generation is deterministic for a particular generator state and input. The output is either an element of L or no move. With a board containing only one stone, |L|=224; a one-element list always returns its sole entry. A full or terminal board must not perform modulo zero. The legality argument is immediate from construction of L, provided the game-level preconditions and list are correct. Using a deterministic 64-bit splitmix-style mixer over the legal move list ensures fast O(1) index selection after O(N²) empty-cell enumeration.
[27462:27834] Gathering all cells takes O(N²) time and O(N²) space in the worst case; selection after that is O(1). A post-selection evaluation has its own cost. [55388:55431] 2.11 Zobrist hashing and incremental state
[55431:55460] 2.11.1 Definition and update
[55460:56003] A transposition can arise when different sequences of moves lead to the same board and relevant side to move. Comparing all cells at each cache access costs O(N²), so a compact hash can serve as an index. Zobrist's method assigns a pseudorandom word to each (cell, player) pair and combines the keys for occupied cells with exclusive OR (XOR) [19]. One also needs a side-to-move key if the same occupancy can be evaluated with different players to move. The hash is a compact fingerprint, not mathematical proof that two states are identical.
[56003:56104] Define Z[x,y,p] as a fixed random word for a stone, and S as a fixed side key. Under one convention,
[56104:56193] H(B,p) = XOR Z[x,y,color] over occupied cells, XOR S if p is the designated second side.
[56193:56447] All keys must remain fixed for the lifetime of the table. Applying a move of p at m adds its key with XOR. If the transition changes the side, XOR S as well. Undo repeats the same XOR operations in reverse. The essential identity is (h XOR z) XOR z = h.

[58786:58840] 2.12 Transposition table: entries, bounds and context
[58840:58872] 2.12.1 Meaning of stored values
[58872:59378] A transposition table (TT) maps a position fingerprint to a previously computed search result. A typical entry stores a hash or verification key, remaining search depth, value, bound type and a suggested best move. The move may help order later search even if the stored score is unusable. A cache lookup is sound only when its represented search problem is compatible with the current one, its depth is sufficient under the selected contract, and its bound justifies the requested cutoff or exact result.
[59378:59871] For an original search window [α₀,β₀], a common classification is: result v ≤ α₀ is an upper bound; v ≥ β₀ is a lower bound; and α₀ < v < β₀ is exact, subject to the search's assumptions. Equality is treated conservatively at the boundary. For instance, with window [3,8], a returned 2 is an upper bound, 5 is exact and 9 is a lower bound. Consequently, a stored LOWER bound triggers an immediate cutoff whenever entry.score ≥ β, and an UPPER bound triggers a cutoff whenever entry.score ≤ α.

[61147:61177] 2.12.2 Why reuse can be wrong
[61177:61722] A useful invariant is: whenever a TT score is reused, it is valid for the current position, depth interpretation, perspective, rule set, evaluation and move-generation context, and its bound permits the intended conclusion. An exact compatible entry may answer a query; a lower or upper bound is usable only in its permitted direction. If any premise is false, the stored number can change the decision. A full hash comparison narrows ordinary index collisions but still does not guarantee that different game states cannot share a fingerprint.
[61722:62579] The historical reference report documents a concrete context hazard. [64044:64096] 2.13 Quiescence search in the legacy TypeScript bot
[64096:64586] A fixed-depth search can stop at an unstable position: a static evaluator may prefer a move just before an immediate tactical reply. Quiescence extends selected tactical continuations beyond the ordinary horizon so that the evaluator is applied after a limited forcing sequence. This is a selective model and has its own horizon; it cannot eliminate every tactical error. The relevant implementation is the legacy TypeScript bot, not a feature established for the current WASM engine [11].
[64586:65372] Inputs and state. The legacy routine receives the board, alpha and beta bounds, current ply and a quiescence depth. It works from the perspective of the side to move, uses negamax sign reversal, increments a node counter and checks for abort. Its state includes board cells, side, hash and cached pattern counts. Its output is a bounded score for the selected forcing continuation, or an abort propagated to the caller. It first checks whether either side has a five pattern. It then calculates standPat, applies a beta cutoff if that static score is at least beta, raises alpha if appropriate, and stops at quiescence depth five. Otherwise it generates forcing candidates, orders them and recurses after a move with (-beta,-alpha); each recursive branch uses try/finally to undo [11].

[73029:74625] Why the six difficulty tiers are divided this way: the configuration table is designed around two mathematical principles. First, it separates qualitative decision regimes: Easy (d = 0, Random across all empty cells) provides a non-tactical baseline for beginners; Normal (d = 1, uncapped local neighborhood) introduces 1-ply immediate win/block priority and static heuristic scoring; and Hard through Master (d = 2 to 5, Chebyshev radius r = 2) engage multi-ply Alpha-Beta look-ahead. [75891:75943] 2.16 Synthesis and limits of the algorithmic claims
[75943:76626] The algorithms in this chapter have different responsibilities. Win detection decides the stated terminal rule; board mutation maintains a position; random and rule-based choices provide baselines; the evaluator assigns an approximate horizon value; candidate generation restricts the moves explored; ordering permutes the retained moves; minimax evaluates the resulting tree; alpha-beta skips provably irrelevant branches of that same tree; iterative deepening manages progressive search; and hashing plus a transposition table aim to reuse compatible earlier work. Quiescence extends a selected class of tactical moves at a horizon, but its own assumptions and depth limit remain.
[76626:77248] Each algorithmic layer enforces a distinct invariant within the overall decision pipeline: 4-axis ray scanning detects Freestyle terminal lines in O(K) time; in-place apply/undo preserves board state across recursive branches in O(1) time; Chebyshev spatial generation and the soft tactical cap bound the branching factor while retaining 100% of immediate 1-ply threats; move ordering prioritizes high-value branches; Alpha-Beta pruning eliminates provably suboptimal subtrees while preserving the exact Minimax root value; and Zobrist XOR hashing with bound-typed transposition tables accelerates repeated state lookups.
[77248:77967] The recorded research tests and experiments are useful because they specify fixtures, configurations and counters, including negative cases and restoration checks. Together, the native algorithmic benchmarks, Node WASM parity checks, and browser Web Worker telemetry provide complementary multi-level validation [8]. For a reproducible claim about a particular application build, the report must identify the source revision or snapshot, binary provenance, rule and evaluation configuration, player and position, candidate set, depth, platform, and meaning of each reported counter. The following chapters can then describe the system integration and evidence without turning theory into an unmeasured product outcome.

[87718:87773] 3.4 Board state, history and legal transition contract
[87773:88283] The frontend GameState stores one value per cell and an ordered move history. A move records its player, cell and index; history is also the input used to reconstruct a fresh Rust game for a search. These two uses require consistency. If a board cell changed without a corresponding history update, the display could show one position while the engine searched another. The transition contract therefore relates the occupied-cell set to the history sequence rather than treating them as independent data. [14]
[88283:88994] The board has N = 15 and N² = 225 cells. A frontend cell is (row, col); Rust entry points use (x,y) with x = col and y = row. The row-major linear index is row × N + col. The normal pointer route applies floor, producing integer cell coordinates, and checks that they lie in 0 through 14. The WASM result adapter separately validates both integer-ness and bounds before mapping a result to a frontend cell. The core isBoardCell function itself checks numeric bounds but does not test Number.isInteger; direct fractional inputs therefore require an additional guard. A public API should not rely exclusively on the renderer to supply integers, because tests or other callers can enter through other routes. [27]
[88994:89508] The playMove behaviour rejects an occupied cell before mutation, records the accepted move and evaluates the supplied rule. The higher controller supplies the current player and enforces pause, phase and AI-turn guards. This division is significant: a low-level board operation may not know which UI phase is active, while the controller should not duplicate the geometric win scan. The report therefore describes the legal move as a composed contract rather than attributing every guard to one function. [28] [2]
[89508:89911] The history sequence is not merely a move counter. It preserves alternation and the exact order needed for hydration. A full board without a winner is declared a draw after the win test. That order matters on the last empty cell: a winning final placement must remain a win rather than being classified as a draw merely because the board is now full. The controller's finishMove uses this ordering. [2]
[89911:89950] 3.5 Match phases and state transitions
[89950:90427] MatchController defines setup, ready, playing and game-over. Its initial state is ready, local two-player mode, normal difficulty and round identifier zero. Calling playCell from setup or ready invokes startRound, which increments the round identifier, clears the old outcome and enters playing. An accepted win or full-board draw changes the match to game-over. The thinking flag belongs to the AI request lifecycle; it is not a fifth value in the phase enumeration. [23] [2]

[91927:91978] 3.6 Asynchronous request protocol and cancellation
[91978:92535] An AI action captures a new turn token, the round identifier and difficulty before setting thinking state. The request contains a copied move history. The transport wrapper adds its own message identifier so the correct pending promise receives the corresponding Worker response. The returned domain result carries its request/round identity, difficulty, move and statistics. The message identifier, AI request identifier and round identifier serve related but different scopes; they should not be collapsed into a single undocumented counter. [2] [3] [26]
[92535:93055] On completion, the controller compares the captured token with its current token, checks pause and the returned round identifier, and repeats the phase, mode and current-player conditions. Only then does it clear thinking state, save feedback and pass the proposed O move through the same domain move behaviour used elsewhere. A rejected returned move produces an error instead of being painted directly. A missing move in an active round is also an error. This keeps the authoritative board inside the domain path. [2]
[93055:93624] A concrete race illustrates the mechanism. Suppose request A is searching round 8. The person invokes a New game before A finishes. The controller increments its token, clears state and changes the round. Even if A's response was already queued, its captured token no longer matches. The promise resolution cannot insert A's move into the new board. Meanwhile, cancelPending rejects pending transport promises and terminates the old Worker, so future requests construct a new one. The token guard and resource cancellation address different parts of the race. [2] [26]
[93624:94100] The rejection path is also scoped. A caught error changes feedback only when the captured token still equals the current token. Thus cancellation of an old request should not overwrite the error display of a newer turn. The Worker wrapper ignores messages from a worker object that is no longer its current worker, and ignores message identifiers absent from its pending map. These guards are source mechanisms; whether all possible races are covered remains a test question.

[96553:96610] 3.8 Search-result contract and presentation of telemetry
[96610:97116] The Rust result validator expects integer x/y coordinates in bounds, a finite score, the requested difficulty, one of the known strategy names and nonnegative safe-integer counters. [97116:97765] The adapter maps the fields into application terminology and explicitly labels the source as Rust. A displayed duration therefore has a defined scope: it is not a complete user-perceived round trip and is not a measurement of only the recursive search. [97765:98235] Completed depth is the depth reported for the finished computation. A configuration table is a requested policy, while completed depth is output telemetry. [101303:101332] 4.2 Accepted move processing
[101332:102237] At the action boundary, GameController.playCell first rejects a paused state. It starts a round when appropriate, rejects an ended match and prevents a human action while AI is thinking or while O owns the turn in AI mode. The controller then calls playMove with the current player and proposed cell. A nonaccepted result returns immediately without modifying board or history. However, from setup or ready, startRound runs before cell validation: a rejected direct call can advance the internal phase and round identifier without a notification. [102237:102752] The sequence is deliberate. Notification occurs after the accepted domain change, so the interface receives a coherent snapshot. [116225:116259] CHAPTER 5. RESULTS AND EVALUATION
[116259:116309] 5.1 Evaluation questions, evidence and boundaries
[116309:116911] The evaluation addresses four separate questions. First, do the game and the recorded Rust engine preserve basic board and search behaviour on the tested positions? [135729:135772] 5.7 Threats to validity and interpretation
[135772:136207] Internal validity. Search comparisons require the same position, depth, terminal rules, evaluation perspective and candidate set. Otherwise an apparent improvement can arise from searching a different tree. A table that ignores rule or perspective context can return a stale value. An aborted iteration must be counted separately from completed work. These issues are directly motivated by the cap-loss, cache-scope and budget probes.
[136207:136718] Measurement validity. The native experiments distinguish recursive nodes, leaf evaluations, ranking evaluations, cutoffs and time. Treating one counter as a substitute for all computation can reverse the apparent conclusion, as the clustered ordered example shows. Three sequential timing repeats and lack of randomized order, CPU isolation or uncertainty intervals support descriptive comparisons only. Native timer scope, Worker hydration and search, and browser round-trip duration are different quantities.
[136718:137127] External validity. The fixtures cover controlled and seeded boards but not the full space of legal games. Tactical test positions may be synthetic. A 100-game Rule-Based versus Random result is narrow, and it does not calibrate six difficulty levels against human skill. Node execution and headless-browser synthetic input do not establish physical touchscreen, Wink host, deployment or production behaviour.
[137127:137530] Reproducibility and provenance. The public repository includes raw records, harnesses, source excerpts and cryptographic hashes. Appendix B summarizes the verification artifacts and scope across each subsystem. A reproducible follow-up should archive exact source, build configuration, dependencies, tool versions, random seed, raw runs and a measurement protocol together under one immutable revision.

[137568:137604] 6.1 Work completed and contribution
[137604:138210] The project combines a playable Caro application with an educational sequence on representation, rules, heuristic evaluation and adversarial search. The application repository provides the user interface and game-side code; the weekly material documents the development sequence from initial proposal to search and advanced techniques. The presentation project supplies visual and executable teaching examples. Separate research artifacts provide controlled search data and record experimental boundaries. These products have different purposes and should not be treated as one executable engine. [1] [52]
[138210:138984] The technical contribution is the mapping from game decisions to data structures and algorithms. A board state supports legal placement, directional line checks, history and rollback. A heuristic gives a bounded estimate for nonterminal positions, while terminal outcomes take precedence. Minimax specifies alternating decisions; Alpha-Beta can discard branches that cannot alter the selected-tree value. Candidate generation restricts the search space, and ordering changes traversal order. The reference experiments further evaluate incremental Zobrist hashing, transposition-table bounds, and iterative-deepening budgets on controlled native benchmarks. The application and reference implementations must each be described through their own source and evidence. [44] [8]
[138984:139590] The 23 October native record reports agreement and restoration on its finite corpus, and the separate Node and browser artifacts exercise selected integration paths. The reference data shows a substantial node reduction in one paired example and also shows that ordering can consume enough additional evaluation work to remove the elapsed-time benefit. The cap-loss and cross-root cache probes expose concrete correctness risks. These findings are more useful than a single headline speedup because they identify both the assumptions under which the method works and the conditions that require more care.
[139590:139606] 6.2 Limitations
[139606:139875] First, while the engine's soft tactical cap preserves all immediate 1-ply winning and blocking moves, tightening the non-tactical candidate cap at higher depths (from 15 at Hard to 8 at Master) trades broad positional exploration for deeper 5-ply tactical calculation.
[139875:140235] Second, the active WebAssembly engine uses stateless fixed-depth Alpha-Beta search per turn without a persistent cross-turn transposition table or wall-clock iterative deepening, and empirical evaluation is currently scoped to controlled benchmark fixtures and automated bot-versus-bot matches rather than large-scale human tournament play. [41] [44] [8] [40]
[140235:140509] Third, the static heuristic evaluator scans maximal contiguous runs and therefore relies on multi-ply search recursion and the tactical candidate assessor to recognize gapped formations (such as XX_XX) or multi-axis forks, motivating the future enhancements outlined below.
