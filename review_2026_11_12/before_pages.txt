ABSTRACT 
This project studies the design and implementation of a Caro web application 
together with a set of adversarial-search experiments and teaching materials. The 
report specifies a 15 × 15 Freestyle game, the board and move-history contracts, 
and the algorithms used to select and evaluate moves. It explains random and 
rule-based baselines, contiguous-run heuristics, tactical checks, Chebyshev 
candidate generation, soft candidate caps, Minimax and Alpha-Beta. It also treats 
iterative deepening, Zobrist hashing, transposition-table bounds, quiescence and 
incremental pattern counting in their corresponding reference or legacy 
implementations. Each algorithm is presented with its inputs, state, decision 
procedure, invariants, complexity, worked examples and limitations. 
The application combines React interface components, a Pixi board, an 
authoritative controller and a Worker-based Rust/WebAssembly route. Request 
identity, round identity, cancellation, coordinate conversion and telemetry 
validation preserve the connection between a proposed AI move and the round in 
which it may be committed. The separate presentation website provides interactive 
explanations and Python/Pyodide examples. Its demonstrations are analysed 
individually rather than treated as measurements of the game engine. 
Evaluation distinguishes published native experiments, binary/adapter parity, actual 
browser Worker observations, selected UI interactions and historical cross-language 
benchmarks. GitHub references identify immutable source and evidence snapshots. 
The analysis includes negative findings such as tactical moves discarded by a 
reference candidate cap, increased timing despite fewer searched nodes, and unsafe 
table reuse across a changed context. The resulting report connects algorithmic 
principles to concrete implementation while stating the boundaries of finite tests, 
source availability and reproducibility. 
Keywords: Caro; Gomoku; Minimax; Alpha-Beta; candidate generation; Rust; 
WebAssembly; game-state consistency.

CHAPTER 1. INTRODUCTION 
1.1 Background and motivation 
Caro is a two-player placement game in which a small set of rules produces a large 
adversarial decision space. A player places one stone on an empty cell, attempts to 
complete a winning line and must anticipate the opponent's reply. The board 
representation is simple enough to implement explicitly, while the number of 
possible move sequences makes exhaustive search impractical beyond shallow 
depths. This combination makes the project suitable for studying data structures, 
recursive search, evaluation functions, pruning and the relationship between 
algorithmic results and an interactive application. 
The project develops both a playable web application and material for explaining its 
algorithms. In the application, React supplies the surrounding interface, Pixi renders 
the board and a controller coordinates accepted moves, match state and AI requests. 
The AI path combines a TypeScript tactical check with a Worker-based 
WebAssembly engine. The repository also preserves a TypeScript search 
implementation, native Rust benchmark programs, baseline Rust engine code, 
weekly research reports and a separate presentation website. These modules form a 
cohesive architecture spanning interactive gameplay, WebAssembly search 
execution, and reproducible algorithmic benchmarks. [1] [2] [3] 
The practical problem is to return a legal and useful move while maintaining 
coherent application state. A search that produces a high score is insufficient if it 
changes the caller's board, uses an incompatible win rule, blocks interaction 
unnecessarily or commits a result after the user has reset the round. The report 
therefore considers both the mathematical search problem and the application 
boundary at which a result becomes a move. It also distinguishes an observed 
counter from a configured limit and a native experiment from a browser 
measurement. 
1.2 Objectives and research questions 
The first objective is to specify the actual game rules and state transitions. A 15 × 
15 board and a five-stone target do not uniquely define a Caro variant. The 
application's Freestyle rule accepts a contiguous line of at least five stones, 
including longer lines. Its implementation is explained from the last-move scan, 
with the assumptions under which that local test is valid. The second objective is to 
specify the AI algorithms precisely: their inputs, outputs, recurrence or decision

2.2 Board representation and legal updates 
2.2.1 Matrix, index conversion, and state ownership 
A position consists of 225 cells, each containing empty, X or O. In an array indexed 
as B[y][x], row-major conversion to a flat logical index is i = 15y + x; the inverse is 
x = i mod 15, y = floor(i/15). Hence the center (7,7) has index 112, and (14,14) has 
index 224. The system divides board representation across three specialized 
structures according to architectural role: (1) the Rust search engine (Board) stores 
a contiguous 15 × 15 grid of 225 one-byte repr(u8) cells (Empty = 0, Black = 1, 
White = 2) paired with move_count; (2) the match wrapper (Game) and frontend 
(GameState) store match progression and an ordered Move history; and (3) the 
legacy TypeScript bot (BotBoard) uses a 1D sentinel-padded array with directional 
bitmask segments. The rationale for this division is to decouple high-frequency 
recursive search from match-lifecycle management. Its primary benefit is O(1) 
direct indexing, O(1) in-place apply/undo during depth-first search, zero per-node 
heap allocation, and compact L1-cache locality; the trade-off is that the raw 
225-cell matrix does not record chronological move order, requiring the outer 
Game/GameState layer to maintain history and full-board unindexed scans to take 
O(N²) time [13]. 
The archived Rust place excerpt validates bounds, rejects an empty stone, rejects an 
occupied cell, writes a cell and increments a move counter. The companion undo 
rejects an out-of-range or already-empty cell and otherwise clears it and decrements 
that counter [6]. Dividing responsibility between low-level cell mutation 
(Board::place and Board::undo) and match-level legality (Game::play_move and 
GameController) keeps inner-loop search operations lightweight while ensuring that 
turn alternation and post-win lockouts are strictly enforced on committed game 
moves. 
A board and a game are different state owners. Cells and the count describe the 
position; turn, winner, and move history describe the match's progression. A history 
provides the information needed to restore actual game moves in reverse order. A 
recursive search temporarily changes a working board to explore alternatives, 
which must not silently become the player's actual move. The documented Rust 
search makes a copy at its outer entry, while its in-place search relies on restoration 
of the working board [6]. Cloning the root board once per search request isolates

exploratory tree mutations from the live game state, while in-place apply and undo 
avoid O(N²) board copying at internal nodes.

2.2.2 Apply and undo 
Inputs and output. APPLY(B,m,p) takes the working board, a coordinate and a 
nonempty player; it returns success or failure. UNDO(B,m) takes the coordinate of 
a previously applied move and returns whether removal was possible. The stronger 
search precondition is that undo is paired with the most recent successful 
hypothetical move on that branch. An individual undo that merely removes an 
occupied cell does not enforce the whole history discipline.

APPLY(B, (x,y), p): 
    if x or y is outside the board, or p is empty: return failure 
    if B[y][x] is not empty: return failure 
    B[y][x] ← p 
    B.move_count ← B.move_count + 1 
    return success 
 
UNDO(B, (x,y)): 
    if (x,y) is outside the board or B[y][x] is empty: return 
failure 
    B[y][x] ← empty 
    B.move_count ← B.move_count - 1 
    return success 
 
VISIT_CHILD(B, p, m): 
    require APPLY(B, m, p) succeeds 
    try: value ← VISIT(B, opp(p), m) 
    finally: require UNDO(B, m) succeeds 
    return value 
The finally in this explanatory version means every normal return, cutoff and 
supported abort must pass through restoration. In languages without such a 
construct, equivalent structured cleanup is necessary. Additional state such as a 
hash, side to move, cached pattern counts, last move or winner must also be 
restored by its actual owner. This paired apply/undo contract guarantees O(1) state 
transitions per branch while preserving parent-state integrity across arbitrary search 
depths. 
Invariant and argument. Immediately before exploring each sibling, the working 
state must equal the state at the parent node. A successful apply changes exactly the 
selected empty cell and increments the count. Its matching undo clears that same 
cell and decrements the count; therefore these fields equal their former values. By 
induction over nested calls, assuming each recursive child restores every state field 
7 


=== PAGE 17 ===
it owns, the parent sees the same state for the next sibling. The induction depends 
on legal matching calls; it is not guaranteed if an exception bypasses undo or a 
different move is removed. 
For example, let X occupy (7,7), O occupy (8,7), and the count be two. Trying X at 
(7,8) changes that cell and makes the count three. Undoing (7,8) returns both the 
cells and count to their initial values. Clearing the cell but leaving count three 
makes fullness checks unreliable; decrementing without clearing contaminates the 
next branch. With direct indexing, each operation is O(1) time and O(1) auxiliary 
space; copying an N × N board costs O(N²). Rejecting an occupied or 
out-of-bounds move must leave the board unchanged. Together with the inductive 
restoration invariant, automated root-restoration checks across 820 engine search 
runs confirm that the working board is returned unchanged after every search.

2.3 Freestyle win detection 
The frontend win rule treats a contiguous line of at least five stones as a win, 
including an overline of six or more. It checks four axes through the last move, with 
both directions on each axis. It does not require exactly five or impose an additional 
two-blocked-ends condition [4]. The term Caro is used for the application, but this 
particular rule is specified explicitly because games with similar names may use 
other winning conditions. 
Inputs, outputs and preconditions. The procedure takes a board and the last placed 
coordinate m, and returns the winner and a collection of winning cells when a 
qualifying line is found, or no result otherwise. It assumes m refers to the move that 
may have just caused the transition. If the board was already won before that move, 
8 


=== PAGE 18 ===
testing only a line through m cannot detect every earlier win. A root-level validation 
of an arbitrary imported board needs a separate full-board check. The current 
frontend rule reads the player at m; an empty or invalid location produces no 
winner. 
For directions D = {(1,0), (0,1), (1,1), (1,-1)}, let f_d and b_d count consecutive 
stones equal to the stone at m in the positive and negative direction. A win through 
the last move occurs exactly when some 1 + f_d + b_d ≥ K. To decide whether the 
threshold is reached, scanning at most K−1 matching cells in each direction is 
sufficient: any additional cells cannot change a negative result to a positive result 
after K−1 matching cells already exist on one side. 
// Algorithm 2.2 (CaroGame/src/game/core/WinRules.ts) — WIN_AT(B, 
m, K): 
    if m is out of bounds or B[m] is empty: return NONE 
    p ← B[m] 
    for d in [(1,0),(0,1),(1,1),(1,-1)]: 
        cells ← [m] 
        for sign in [+1,-1]: 
            for step from 1 to K-1: 
                q ← m + sign * step * d 
                if q is outside or B[q] ≠ p: break 
                append q to cells 
        if length(cells) ≥ K: return (p, cells) 
    return NONE 
The scan invariant is that every collected cell is on the selected axis, adjacent to the 
preceding segment and occupied by p. Stopping at the first boundary or different 
cell prevents joining disconnected sequences. If a contiguous run through m has 
length at least K, either its collected positive and negative portions together reach 
K−1 neighbors or a single portion does, so the check succeeds. Conversely, K 
collected stones form a contiguous same-player segment through m, establishing 
the stated rule. The returned display collection may be truncated to K−1 stones per 
side; it is sufficient to prove a win but is not necessarily the full maximal overline. 
Consider X X [X] X X on one row with the bracketed center as the last move. Each 
side contributes two; 1+2+2=5. For X X X [X] X X, the value exceeds five and

remains a win. An empty last cell returns no winner; a gap interrupts the run; edge

invariant that no prior move had already won, so arbitrary imported positions 
require a one-time O(N²) root validation.

2.4 Baselines: random play and rule-based play 
2.4.1 Random baseline 
A random baseline makes the meaning of added search explicit: it selects without 
comparing a tree of future replies. The documented Rust baseline first checks for a 
terminal position or an invalid empty player; for Easy it gathers legal empty cells, 
10 


=== PAGE 20 ===
uses a seeded pseudo-random value modulo the number of cells, and evaluates the 
resulting move for the returned result. That evaluation occurs after selection and 
does not choose the Easy move [6]. 
// Algorithm 2.3 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — 
RANDOM_MOVE(B, p, seed): 
    if p is empty or B is terminal: return NONE 
    L ← all legal empty cells in B 
    if L is empty: return NONE 
    i ← SEEDED_INTEGER(seed) mod length(L) 
    return L[i] 
The input includes the seed because pseudo-random generation is deterministic for 
a particular generator state and input. The output is either an element of L or no 
move. With a board containing only one stone, |L|=224; a one-element list always 
returns its sole entry. A full or terminal board must not perform modulo zero. The 
legality argument is immediate from construction of L, provided the game-level 
preconditions and list are correct. Using a deterministic 64-bit splitmix-style mixer 
over the legal move list ensures fast O(1) index selection after O(N²) empty-cell 
enumeration. 
Gathering all cells takes O(N²) time and O(N²) space in the worst case; selection 
after that is O(1). A post-selection evaluation has its own cost. A fixed seed makes 
the selection reproducible under the same generator and ordering, not necessarily 
across different implementations or changed inputs. A random policy does not 
promise to notice an immediate win or threat. 
2.4.2 Immediate tactics and one-ply heuristic 
The documented Normal baseline first obtains candidates, then chooses an 
immediate win when available, otherwise an immediate blocking coordinate, and 
otherwise compares the evaluations of candidate moves. These are priorities, not a 
multi-ply adversarial proof. The candidate assessment is the source of the 
immediate-win and block markers [6]. The current frontend also has a separate 
tactical resolver for Hard, Very Hard, Expert and Master before it requests the 
WASM engine. Easy and Normal skip that frontend prepass. A tactical response 
reports its own source and zero Rust search work; it must not be presented as a 
completed alpha-beta search [10].

// Algorithm 2.4 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — 
RULE_BASED(B, p, policy): 
    if B is terminal or p is invalid: return NONE 
    C ← SELECT_CANDIDATES(B, p, policy) 
    if an m in C wins immediately for p: return m 
    if an m in C is an immediate winning cell for opp(p): return m 
    best_move ← NONE; best_score ← -infinity 
    for m in C: 
        APPLY(B,m,p) 
        try: 
            score ← TERMINAL_OR_EVALUATE(B,p,m) 
        finally: 
            UNDO(B,m) 
        if best_move is NONE or score > best_score: 
            best_move ← m; best_score ← score 
    return best_move, best_score 
The decision invariant after processing the first j non-tactical candidates is that 
best_score is the greatest observed value among those j moves and the board is 
restored. A separate invariant places the win and block checks before the one-ply 
loop. Thus the routine picks the best score among the evaluated candidates when 
neither tactical condition applies. Correctness of the tactical marker itself depends 
on the assessment recognizing the corresponding winning geometry and on the 
move being included in C. 
For a concrete threat, suppose X occupies row 0, columns 0–3, column 4 is empty, 
and O is to move. The left endpoint lies outside the board; placing O at (4,0) blocks 
the only immediate completion along this row. If the same four consecutive X 
stones are in the interior with both endpoints empty, there are two distinct winning 
cells. A single O move can occupy one cell, not both. Retaining both choices avoids 
losing information but does not establish that either saves the game. Similarly, an 
immediate winning move for O takes priority over blocking if both are available 
under the algorithm's ordering. 
If k candidates are generated, one-ply evaluation costs roughly O(k × 
evaluation-cost), in addition to candidate generation and ordering. A constant-time

2.5 Static evaluation and terminal utility 
2.5.1 Evaluation of nonterminal positions 
A search with finite depth can stop before a winner exists. Its evaluator assigns an 
approximate score to that horizon position. In the documented modified Rust 
snapshot, evaluate scans maximal contiguous runs in four directions, adds the root 
player's run weights, subtracts the opponent's, and adds or subtracts a center 
preference. The snapshot counts a run once per axis by skipping a cell when the 
previous cell on the same axis has the same color. It then clamps the final heuristic 
to a range below terminal scores [6].

their number of empty endpoints. Let c(x,y)=max(0,14−|x−7|−|y−7|) and C(B,p) be 
p's sum of c minus the opponent's. The descriptive formula is

2.5.2 Terminal states and the score hierarchy 
Terminal outcomes must be evaluated before a depth cutoff. In the engine 
implementation, the terminal base constant is M = 100,000,000, the ply distance 
from the root is q ≤ 225, and nonterminal heuristic scores are clamped to (−H, +H) 
with H = M − 225 − 1 = 99,999,774 [6]. The result from root perspective is M−q 
for a root win, −M+q for a root loss, and zero for a draw. An unfinished board has 
no terminal utility and is evaluated only when the search horizon is reached [6]. 
// Algorithm 2.6 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — 
TERMINAL_UTILITY(winner, full, root, ply): 
    q ← min(ply, 225) 
    if winner = root: return M - q 
    if winner is the opponent: return -M + q 
    if full: return 0 
    return NONE 
The clamp ensures every nonterminal heuristic lies between −H and H. Since 
M−225 = 99,999,775 > H, even the slowest represented win exceeds a nonterminal 
score; similarly a loss is below every nonterminal score. A win at q=2 receives 
99,999,998 and a win at q=4 receives 99,999,996, so maximizing prefers the earlier 
win. Conversely, if a loss is unavoidable, increasing q makes its negative score less 
severe and thus delays the loss. This preference follows from the formula; it is 
conditional on the search actually reaching and correctly identifying those terminal 
outcomes. The winner must be decided before a full-board draw when the last 
empty cell completes a line. 
2.6 Candidate generation and a soft tactical cap 
2.6.1 Spatial neighborhood 
Considering every empty cell creates a large branching factor. A candidate policy 
can instead choose empty cells close to existing stones. For cells a and b, 
Chebyshev distance is d∞(a,b)=max(|a_x−b_x|, |a_y−b_y|). With radius r, a spatial 
candidate is an empty cell within distance r of at least one occupied cell. The empty 
board has a special center choice, and a full board has no move. The exact selection, 
fallback and ranking below describe the archived modified-engine policy, not the 
legacy bot's different forcing-move generator [6].

2.7 Move ordering versus move selection 
A search traverses the retained moves in an order. Ordering permutes an already 
chosen set; filtering or capping changes its membership and therefore the tree itself. 
In a complete minimax evaluation of the same deterministic tree, any permutation 
produces the same value, although a tied best move can differ if the first best move 
is retained. In alpha-beta search, ordering influences how soon useful bounds are 
discovered and can alter the number of cutoffs, while preserving the root value 
under the algorithm's assumptions [17].

ORDER(retained_moves, rank): 
    calculate a rank key for each retained move 
    sort by the chosen key with a deterministic tie breaker 
    return the same moves in the new order

2.8 Minimax search 
2.8.1 Recurrence and contract 
Minimax assumes two alternating decision-makers. MAX chooses a move to 
maximize a score from the root player's perspective; MIN chooses to minimize it. 
Its input is the current board, the side to move, a nonnegative depth d in plies, the 
last move when available, a candidate policy and an evaluator. The output is a value

and, at the root, a selected move, or no move for an already finished game. State 
includes the mutable working board, remaining depth, root perspective and 
recursion stack. Search must begin from a board compatible with the chosen rules, 
or validate it separately. 
Define U(s,R) for terminal states, E(s,R) for a nonterminal horizon, and transition 
T(s,a). With a fixed deterministic candidate function A, the depth-limited value is 
V(s,d) = U(s,R) if s is terminal; 
V(s,0) = E(s,R) if s is not terminal; 
V(s,d) = max[a∈A(s)] V(T(s,a),d−1) if MAX moves; 
V(s,d) = min[a∈A(s)] V(T(s,a),d−1) if MIN moves. 
An empty generated set for a nonterminal board must have a specified behavior. 
The documented value routine returns zero for an empty list, while candidate 
fallback is intended to avoid this on a nonfull valid position. That fallback 
convention should not be silently reinterpreted as a win or as a comprehensive 
validation of arbitrary positions [6].

recursive search kernel configurable as either full-tree Minimax or Alpha-Beta

2.8.2 Proof, example and complexity 
Use induction on d. For terminal nodes or d=0 the procedure returns exactly the 
corresponding definition. Assume recursive results equal V for depth d−1 and that 
each apply/undo restores the parent. At a MAX node the loop's best value after j 
children is the maximum of the first j child values; at completion it is the maximum 
over A. The MIN case is symmetric. Each recursive call reduces d, so a finite 
candidate list guarantees termination. This proves evaluation of the specified finite 
tree if transition, terminal detection, evaluation and candidate generation satisfy 
their contracts; it does not prove the evaluator predicts the outcome of an 
unrestricted game. 
In an abstract depth-two tree, MAX has actions A and B; MIN's leaves under A 
have values 3 and 5, and under B have values 2 and 9. MIN returns 3 for A and 2 
for B; MAX chooses A with 3. This two-ply trace illustrates how alternating MAX 
and MIN backups propagate exact horizon utility values to the root decision. 
If the maximum number of generated moves is b at each level, the full tree has 
O(b^d) nodes for b>1; actual branching may vary by state, cap and terminal events. 
Depth-first exploration uses O(d) stack frames plus the live candidate lists, 
conservatively O(db) move entries and a working board of O(N²), not storage for 
the whole tree. Each node also incurs candidate-generation or evaluation costs, 
which can be substantial. If the terminal is reached sooner, recursion stops early. 
Benefits and trade-offs of Minimax: it provides an exact game-theoretic baseline 
over the generated finite tree with O(db + N²) memory, but its exponential O(b^d) 
time complexity restricts unpruned search to shallow depths.

2.9 Alpha-beta pruning 
2.9.1 Bounds and pseudocode 
Alpha-beta pruning computes the same root value as minimax on the same finite 
deterministic tree under a consistent utility and candidate policy, while sometimes 
skipping subtrees. alpha is the best lower bound MAX can already secure in the 
current ancestor context; beta is the best upper bound MIN can already secure. At a 
MAX node, update alpha after observing a child; at a MIN node, update beta. When 
alpha ≥ beta, the remaining siblings cannot improve the relevant ancestor's decision. 
Knuth and Moore analyze alpha-beta and the effects of move ordering under stated 
assumptions [17].

2.10 Iterative deepening and budgets 
Iterative deepening performs complete searches at depths 1, 2, … until reaching a 
configured maximum or a budget interrupts an iteration. Its input is a root position, 
a maximum depth and a budget. Its output should distinguish the best result from 
the most recently completed iteration, the completed depth, and the reason for 
stopping. The working board, search counters, and any table or ordering hints must 
obey the respective implementation's lifecycle. An incomplete iteration's partially 
explored best move is not the same as a completed minimax result for that depth. 
// Algorithm 2.12 (CaroGame/src/game/bot/search.ts) — ITERATIVE(B, 
maximum_depth, budget): 
    last_complete ← NONE 
    for depth from 1 to maximum_depth: 
        if budget is exhausted: break 
        result ← SEARCH_AT_DEPTH(B, depth, budget) 
        if result was interrupted: break 
        last_complete ← result 
    return last_complete, completed depth, stop reason 
The invariant after iteration d is that last_complete corresponds to a whole 
completed search at d under that iteration's search contract. It follows inductively 
because the result is replaced only after the iteration returns normally. A separate 
abort-safe restoration guarantee is required: interruption in a child must unwind all 
applied moves. If depth one returns A, depth two returns B and depth three aborts, 
the completed result is B at depth two. If no iteration completes, a caller must 
explicitly handle the absence of a completed result; a fallback candidate is useful 
but should be labeled as such. 
Repeated shallow searches consume work, although the deepest full iteration can 
dominate for a sufficiently large, regular branching factor. Each iteration has the 
complexity of its selected search; total time is the sum over attempted depths plus 
ordering and bookkeeping. No hard real-time guarantee follows from this scheme. 
A search interrupted only at periodic checks can exceed its nominal wall-clock 
deadline before the next check, especially if individual operations are expensive. 
The legacy TypeScript findBestMove uses performance.now(), a deadline and a 
periodic node check, and catches its search-abort sentinel. It initializes a fallback 
from the first candidate before any depth is completed; its completed-depth field

2.11 Zobrist hashing and incremental state 
2.11.1 Definition and update 
A transposition can arise when different sequences of moves lead to the same board 
and relevant side to move. Comparing all cells at each cache access costs O(N²), so 
a compact hash can serve as an index. Zobrist's method assigns a pseudorandom 
word to each (cell, player) pair and combines the keys for occupied cells with 
exclusive OR (XOR) [19]. One also needs a side-to-move key if the same 
occupancy can be evaluated with different players to move. The hash is a compact 
fingerprint, not mathematical proof that two states are identical. 
Define Z[x,y,p] as a fixed random word for a stone, and S as a fixed side key. Under 
one convention,

adds its key with XOR. If the transition changes the side, XOR S as well. Undo 
repeats the same XOR operations in reverse. The essential identity is (h XOR z) 
XOR z = h.

same stone key Z(m,p) and turning key S on both make and undo restores the exact

The hash invariant is incremental_hash = FULL_HASH(current board, current

accounts for adding that feature, and XORing the side key exactly accounts for a 
side change. Repeating those operations removes the features on undo. This proof 
assumes the same keys, actual transition semantics, and no omitted state features 
relevant to the hash contract. It does not eliminate collisions.

2.12 Transposition table: entries, bounds and context 
2.12.1 Meaning of stored values 
A transposition table (TT) maps a position fingerprint to a previously computed 
search result. A typical entry stores a hash or verification key, remaining search 
depth, value, bound type and a suggested best move. The move may help order later 
search even if the stored score is unusable. A cache lookup is sound only when its 
represented search problem is compatible with the current one, its depth is 
sufficient under the selected contract, and its bound justifies the requested cutoff or 
exact result.

assumptions. Equality is treated conservatively at the boundary. For instance, with 
window [3,8], a returned 2 is an upper bound, 5 is exact and 9 is a lower bound. 
Consequently, a stored LOWER bound triggers an immediate cutoff whenever 
entry.score ≥ β, and an UPPER bound triggers a cutoff whenever entry.score ≤ α.

2.12.2 Why reuse can be wrong 
A useful invariant is: whenever a TT score is reused, it is valid for the current 
position, depth interpretation, perspective, rule set, evaluation and move-generation 
context, and its bound permits the intended conclusion. An exact compatible entry 
may answer a query; a lower or upper bound is usable only in its permitted 
direction. If any premise is false, the stored number can change the decision. A full 
hash comparison narrows ordinary index collisions but still does not guarantee that 
different game states cannot share a fingerprint. 
The historical reference report documents a concrete context hazard. It records one 
same-root warm reuse, then a probe after playing a move and changing root player: 
a fresh table returned score 0, whereas reuse of the prior table returned 19,800. Its 
hash omitted several contextual factors, including root perspective, and the report 
does not claim a patch. These are results of a particular native reference probe, not a 
measurement or defect proven in the current browser engine [21]. The report also 
notes that mate scores depend on ply from the root; a cached value reused at 
another ply may require normalization or a sufficiently narrow reuse scope. Rules, 
evaluation weights, side, candidate radius/cap, ordering semantics, terminal 
metadata and requested depth can likewise matter. A board fingerprint by itself does 
not certify those conditions. 
The legacy TypeScript uses parallel fixed-size arrays indexed by a modulo 
operation on one hash half and compares both halves before using a slot. It stores 
depth, score, flag and best move. This is a different storage and replacement design 
from the reference's hash map [11], [8]. The existence of a depth check does not 
resolve every context hazard; in particular, project-wide claims require inspecting 
lifecycle, perspective and score conventions. A cached move hint should be 
checked against current legal candidates before application. A new game, changed 
rules, new evaluator or changed root is a reason to reassess or clear a cache unless 
compatibility is proved. 
Expected lookup can be O(1) for an appropriate hash table, but collisions, table 
implementation and replacement behavior affect actual costs. Space is proportional 
to the allocated slots or stored entries plus keys, buckets and overhead. Initial 
hash-map capacity is not a strict maximum, and the native size of one entry is not 
the total memory of the container. Benefits and trade-offs of transposition tables: 
O(1) expected hash lookup avoids re-searching transposed subtrees and supplies 
best-move ordering hints, at the trade-off of O(M) table memory, potential 64-bit

2.13 Quiescence search in the legacy TypeScript bot 
A fixed-depth search can stop at an unstable position: a static evaluator may prefer 
a move just before an immediate tactical reply. Quiescence extends selected tactical 
continuations beyond the ordinary horizon so that the evaluator is applied after a 
limited forcing sequence. This is a selective model and has its own horizon; it 
cannot eliminate every tactical error. The relevant implementation is the legacy 
TypeScript bot, not a feature established for the current WASM engine [11]. 
Inputs and state. The legacy routine receives the board, alpha and beta bounds, 
current ply and a quiescence depth. It works from the perspective of the side to 
move, uses negamax sign reversal, increments a node counter and checks for abort. 
Its state includes board cells, side, hash and cached pattern counts. Its output is a 
bounded score for the selected forcing continuation, or an abort propagated to the 
caller. It first checks whether either side has a five pattern. It then calculates 
standPat, applies a beta cutoff if that static score is at least beta, raises alpha if 
appropriate, and stops at quiescence depth five. Otherwise it generates forcing 
candidates, orders them and recurses after a move with (-beta,-alpha); each 
recursive branch uses try/finally to undo [11].

    count node; check budget or deadline

    if side to move has a five: return MATE - ply 
    standPat ← EVALUATE_FROM_SIDE_TO_MOVE(B) 
    if standPat ≥ beta: return beta 
    alpha ← max(alpha, standPat) 
    if qDepth ≥ 5: return alpha

        finally: UNMAKE(B,m) 
        if v ≥ beta: return beta 
        alpha ← max(alpha,v)

The sign change reflects the negamax convention for an evaluation whose 
perspective changes with the side to move. The procedure returns beta on a 
fail-high and alpha otherwise, so its return can be a bound rather than an exact 
unrestricted game value. Its loop invariant is that alpha is at least the stand-pat score 
and all examined forcing continuations, subject to the window and fail-hard 
convention; the board must equal the incoming state before every sibling. The depth 
limit guarantees termination even when forcing candidates continue to exist. It also 
creates a new horizon. 
For a simplified numeric example, suppose the window is [−10,10], stand-pat is 2, 
and the first searched forcing move returns 6 after sign reversal. Alpha rises to 6. If 
another move returns 12, the routine returns beta, 10, as a fail-high bound. This 
does not assert that 10 is the exact minimax value. In a real position, the forcing 
generator's definition and threat patterns decide which moves are included. The 
legacy code considers outcomes such as five, open four and four for either side 
when identifying forcing moves. These categories arise from its own bitmask

Easy (d = 0, Random across all empty cells) provides a non-tactical baseline for

(d = 2 to 5, Chebyshev radius r = 2) engage multi-ply Alpha-Beta look-ahead.

4, 5) while the soft candidate cap tightens inversely (c = 15, 12, 10, 8). Because an 
adversarial tree with branching factor c and depth d scales as O(c^d) in the worst 
case (and O(c^(d/2)) under ideal Alpha-Beta ordering), keeping c = 15 at d = 5 
would expand up to 15^5 = 759,375 nodes per turn. Tightening the soft cap to c = 8 
bounds the worst-case tree to 8^5 = 32,768 nodes (and ~2,000–5,000 nodes with 
Alpha-Beta pruning), keeping Web Worker latency within interactive browser 
budgets (47, 252, 551, and 1,418 visited nodes in 1.1–3.0 ms on the benchmarked 
midgame fixture). Benefits and trade-offs: this inverse (d, c) scaling delivers 
smooth skill progression and responsive UI performance while the soft tactical cap 
max(c, 1, |T|) and frontend tactical prepass guarantee that zero immediate 1-ply 
wins or blocks are ever dropped; the trade-off is that deeper tiers (Expert, Master)

2.16 Synthesis and limits of the algorithmic claims 
The algorithms in this chapter have different responsibilities. Win detection decides 
the stated terminal rule; board mutation maintains a position; random and 
rule-based choices provide baselines; the evaluator assigns an approximate horizon 
value; candidate generation restricts the moves explored; ordering permutes the 
retained moves; minimax evaluates the resulting tree; alpha-beta skips provably 
irrelevant branches of that same tree; iterative deepening manages progressive 
search; and hashing plus a transposition table aim to reuse compatible earlier work. 
Quiescence extends a selected class of tactical moves at a horizon, but its own 
assumptions and depth limit remain. 
Each algorithmic layer enforces a distinct invariant within the overall decision 
pipeline: 4-axis ray scanning detects Freestyle terminal lines in O(K) time; in-place 
apply/undo preserves board state across recursive branches in O(1) time; 
Chebyshev spatial generation and the soft tactical cap bound the branching factor 
while retaining 100% of immediate 1-ply threats; move ordering prioritizes 
high-value branches; Alpha-Beta pruning eliminates provably suboptimal subtrees

while preserving the exact Minimax root value; and Zobrist XOR hashing with 
bound-typed transposition tables accelerates repeated state lookups. 
The recorded research tests and experiments are useful because they specify 
fixtures, configurations and counters, including negative cases and restoration 
checks. Together, the native algorithmic benchmarks, Node WASM parity checks, 
and browser Web Worker telemetry provide complementary multi-level validation 
[8]. For a reproducible claim about a particular application build, the report must

each reported counter. The following chapters can then describe the system 
integration and evidence without turning theory into an unmeasured product

3.4 Board state, history and legal transition contract 
The frontend GameState stores one value per cell and an ordered move history. A 
move records its player, cell and index; history is also the input used to reconstruct 
a fresh Rust game for a search. These two uses require consistency. If a board cell 
changed without a corresponding history update, the display could show one 
position while the engine searched another. The transition contract therefore relates 
the occupied-cell set to the history sequence rather than treating them as 
independent data. [14] 
The board has N = 15 and N² = 225 cells. A frontend cell is (row, col); Rust entry 
points use (x,y) with x = col and y = row. The row-major linear index is row × N + 
col. The normal pointer route applies floor, producing integer cell coordinates, and 
checks that they lie in 0 through 14. The WASM result adapter separately validates 
both integer-ness and bounds before mapping a result to a frontend cell. The core 
isBoardCell function itself checks numeric bounds but does not test 
Number.isInteger; direct fractional inputs therefore require an additional guard. A 
public API should not rely exclusively on the renderer to supply integers, because 
tests or other callers can enter through other routes. [27] 
The playMove behaviour rejects an occupied cell before mutation, records the 
accepted move and evaluates the supplied rule. The higher controller supplies the 
current player and enforces pause, phase and AI-turn guards. This division is 
significant: a low-level board operation may not know which UI phase is active, 
while the controller should not duplicate the geometric win scan. The report 
therefore describes the legal move as a composed contract rather than attributing 
every guard to one function. [28] [2] 
The history sequence is not merely a move counter. It preserves alternation and the 
exact order needed for hydration. A full board without a winner is declared a draw 
after the win test. That order matters on the last empty cell: a winning final 
placement must remain a win rather than being classified as a draw merely because 
the board is now full. The controller's finishMove uses this ordering. [2]

3.6 Asynchronous request protocol and cancellation 
An AI action captures a new turn token, the round identifier and difficulty before 
setting thinking state. The request contains a copied move history. The transport 
wrapper adds its own message identifier so the correct pending promise receives the 
corresponding Worker response. The returned domain result carries its 
request/round identity, difficulty, move and statistics. The message identifier, AI 
request identifier and round identifier serve related but different scopes; they should 
not be collapsed into a single undocumented counter. [2] [3] [26] 
On completion, the controller compares the captured token with its current token, 
checks pause and the returned round identifier, and repeats the phase, mode and 
current-player conditions. Only then does it clear thinking state, save feedback and 
pass the proposed O move through the same domain move behaviour used 
elsewhere. A rejected returned move produces an error instead of being painted 
directly. A missing move in an active round is also an error. This keeps the 
authoritative board inside the domain path. [2] 
A concrete race illustrates the mechanism. Suppose request A is searching round 8. 
The person invokes a New game before A finishes. The controller increments its 
token, clears state and changes the round. Even if A's response was already queued, 
its captured token no longer matches. The promise resolution cannot insert A's 
move into the new board. Meanwhile, cancelPending rejects pending transport 
promises and terminates the old Worker, so future requests construct a new one. 
The token guard and resource cancellation address different parts of the race. [2] 
[26] 
The rejection path is also scoped. A caught error changes feedback only when the 
captured token still equals the current token. Thus cancellation of an old request 
should not overwrite the error display of a newer turn. The Worker wrapper ignores 
messages from a worker object that is no longer its current worker, and ignores 
message identifiers absent from its pending map. These guards are source 
mechanisms; whether all possible races are covered remains a test question.

3.7 Coordinate transformation and gesture interpretation 
The scene works with a camera translation (cx,cy), a positive zoom z and cell size S 
= 56. For a screen position expressed in the scene's coordinate system, the inverse 
transform is worldX = (screenX − cx)/z and worldY = (screenY − cy)/z; the 
selected column and row are floor(worldX/S) and floor(worldY/S). Conversion 
back to a cell's world origin multiplies its column and row by S. A centre point for 
drawing a stone is obtained by adding half a cell in the renderer, rather than 
changing the indexing contract. [29] 
 
Figure 3.3. Inverse camera transform before board bounds checking 
Source: CaroGame/src/board/spatial/CoordinateTransform.ts [29]. 
The floor operation is important near boundaries. A negative world coordinate must 
remain out of bounds; rounding it toward a nearby valid cell could turn a margin tap 
into a move. For example, with camera x = 20, zoom = 0.5 and screen x = 19, the 
world x is −2 and the column is −1. The subsequent bounds check rejects it. With 
screen x = 230, world x is 420 and the column is 7. The same calculation on y 
yields the row. The report uses scene screen coordinates; client-page coordinates 
must first be converted by the event/rendering system that supplies them. 
The input controller has idle, pressed and dragging states and a configured drag 
threshold of six screen units. A press stores the last pointer. Each move computes 
displacement from the last stored pointer; a sufficiently large displacement while 
pressed changes the state to dragging, and dragging produces a pan delta. On

release, a valid cell tap is emitted only if the gesture remains pressed. The 
last-pointer update means the implemented threshold is checked against the last 
event displacement, not a guaranteed accumulated distance from the initial press. 
This detail is preserved here so the explanation does not promise a different gesture 
recognizer from the source. [30] 
The scene treats pointer-up outside through the same handler and suppresses event 
processing while paused. It fits the board to the viewport using the minimum of

separation lets the same rule and history logic work under different viewport sizes, 
although a desktop viewport simulation does not establish physical-touch

3.8 Search-result contract and presentation of telemetry 
The Rust result validator expects integer x/y coordinates in bounds, a finite score, 
the requested difficulty, one of the known strategy names and nonnegative 
safe-integer counters. Those counters include visited nodes, leaf evaluations, 
cutoffs, ordering evaluations, generated candidates and completed depth. An older 
binary returning only a coordinate pair fails this contract. This is preferable to 
silently displaying a nominal depth beside a result whose engine work was never 
instrumented. [27] [9] 
The adapter maps the fields into application terminology and explicitly labels the 
source as Rust. Its elapsed timer starts before construction and history hydration, 
includes ai_move and free, and ends after cleanup. It excludes module loading and 
message delivery. A displayed duration therefore has a defined scope: it is not a 
complete user-perceived round trip and is not a measurement of only the recursive 
search. The tactical route instead labels its source as tactical, reports zero Rust 
search counters and a null score. Zero counters on that route mean Rust search was 
bypassed, not that a nontrivial Rust tree required no work. [3] [27] 
Completed depth is the depth reported for the finished computation. A 
configuration table is a requested policy, while completed depth is output telemetry. 
Neither alone proves that a higher depth is supported or that every node at that 
depth was examined under a full-legal move set. Candidate pruning, terminal leaves 
and the chosen strategy all affect the actual search. The interface should preserve 
these distinctions when showing details to a player or evaluator.

4.2 Accepted move processing 
At the action boundary, GameController.playCell first rejects a paused state. It starts 
a round when appropriate, rejects an ended match and prevents a human action 
while AI is thinking or while O owns the turn in AI mode. The controller then calls 
playMove with the current player and proposed cell. A nonaccepted result returns 
immediately without modifying board or history. However, from setup or ready, 
startRound runs before cell validation: a rejected direct call can advance the internal 
phase and round identifier without a notification. Normal pointer input filters 
out-of-bounds cells before this call; stronger atomic rejection at the controller 
boundary remains a verification and improvement item. For an accepted result, it 
processes a win or draw, otherwise alternates the player, notifies subscribers and 
starts AI only when the match is still playing in AI mode with O to move. [2] [28] 
The sequence is deliberate. Notification occurs after the accepted domain change, 
so the interface receives a coherent snapshot. The AI request is based on the 
updated history, not on a speculative screen state. Rule evaluation occurs through 
the supplied FreestyleGomokuWinRule. The scene never paints a permanent stone

merely because a pointer event arrived; it renders the state returned through the 
controller. This permits the same move contract to reject an occupied cell 
consistently in the UI and in tests. 
Undo is implemented by history reversal. In local two-player mode it removes one 
ply. In AI mode, if the last recorded player is O, it removes two plies; otherwise it 
removes one. Before reversal it invalidates AI work and clears search feedback. It 
then determines the current player from the remaining last move, asks the match 
controller to resume after Undo and notifies. Popping two plies when the AI has 
already replied returns the board directly to the human player's decision turn while 
preserving chronological history integrity. [2]

4.4 Board rendering and interface synchronization

The implementation can be traced from a controller action through domain state and 
into display, or from a search request through copied history, a Worker, a 
Rust/WASM object and a validated response. The critical invariants are legal 
board/history correspondence, move restoration during search, consistent rule 
interpretation, correct coordinate conversion and current-turn applicability at 
commit. Each has a responsible module and can be tested at its boundary rather 
than inferred from a single large integration result. 
The published tree makes substantial work inspectable: the application source and 
contracts, generated Rust/WASM package, Rust baselines and harnesses, research 
artifacts and presentation programs. It also leaves specific reproducibility limits for 
the exact modified engine and reference dependency used in some historical 
measurements. These limits do not remove the algorithms from the report. They 
determine how confidently an implementation-specific claim can be made and 
which source or evidence type should accompany it. Chapter 5 applies that

5.4.2 Candidate caps, ordering and tactical completeness 
Candidate generation reduces the set of considered moves by selecting empty cells 
near existing stones. This can reduce branching but changes the search problem. 
The reference cap_loss.json supplies a concrete risk: in the synthetic win fixture at 
radius one, 20 uncapped candidates include two immediate winning endpoints (7,2) 
and (7,7), but a cap of six omits both. At depth one, the uncapped score is 9,999,999 
and the capped score is 99,990. This is not an Alpha-Beta error: it is a difference in 
which moves are admitted before the search. It demonstrates why an ordering or 
cap policy must be evaluated against tactical membership, and why a value equality 
proof applies only after the move set is fixed. [16] 
The later 23 October engine record reports twelve tactical-completion retention 
checks for its own candidate policy. These results concern another implementation 
and cannot erase the reference counterexample. Conversely, a failure of that 
reference cap does not establish that the later engine's soft cap fails. A useful future 
experiment would separate candidate generation, tactical retention, ranking and 
pruning in an ablation, using the same positions and reporting both selected move 
quality and total work.

5.4.3 Hash, table scope and interrupted search 
The reference verification record reports 3,998 forward and 3,998 undo hash 
checks, plus four terminal hash-axis checks. Its table semantics record reports three 
bound variants and observed exact, lower and upper entries. These checks concern 
the inspected corpus and implementation. A native entry size of 12 bytes is 
recorded, but the underlying hash map is not a fixed 8 MB table; reservation or 
native object size alone does not establish total memory consumption. The record 
states that rule configuration and root perspective are not included in the key and 
mate-ply normalization is absent. Those facts constrain safe reuse. [49] 
The cache-scope probe makes the constraint tangible. For a clustered fixture at 
radius one and cap eight, a warm table at the same root returns the same score of 0 
as the initial search, with nine nodes and eight hits in the probe. After a move 
changes the root context, the recorded cold score is 0 and the warm score is 19,800. 
The record characterizes cross-root reuse of root-relative entries as unsupported. A 
conservative implementation must start with a fresh table or identify all evaluation 
and rule context in its namespace; the example does not prove that every warm 
reuse is unsafe. [21] 
The budget artifact tests restoration during interruption. A direct budget of ten is 
exhausted and restores the root. In the iterative case, a budget of fifty is exhausted 
after a completed depth of two; 40 aggregate nodes are reported, and the record 
explicitly says that aggregate excludes the aborted iteration. It is therefore incorrect 
to describe 40 as the complete work consumed by all attempted iterations. The last 
completed result remains meaningful only when incomplete iteration state is not 
presented as a completed deeper result. [50]

5.6 Presentation examples and evidence quality 
The present application combines explanatory components, assets, a figure 
inspector and a Python code visualizer. It should be treated as a teaching and 
presentation artifact, separate from the game's actual Worker. In the pattern 
example, the code iterates over rows, even though its description mentions four 
axes; it is consequently a horizontal demonstration, not proof that the example 
scans vertical and diagonal lines. The heuristic example uses its own fixed weights 
and defensive multiplier. The Chebyshev example calculates candidates for an 
embedded toy board. These examples help explain a concept but do not 
automatically reproduce the current Rust engine's results. [38] 
The fourth Python example embeds historical statistics rather than reading a fresh 
run. A comparison between a decision time and a theoretical 16.67 ms frame 
interval cannot establish a real browser frame rate: rendering, scheduling, Worker 
communication and measurement context also matter. Descriptions and hard-coded 
figures in presentation components should be traced back to actual data before 
being reused in a technical conclusion. Where an asset has no traceable dataset, its 
visual content is illustrative rather than an additional measurement. [38] [51] [40] 
5.7 Threats to validity and interpretation 
Internal validity. Search comparisons require the same position, depth, terminal 
rules, evaluation perspective and candidate set. Otherwise an apparent improvement 
can arise from searching a different tree. A table that ignores rule or perspective 
context can return a stale value. An aborted iteration must be counted separately 
from completed work. These issues are directly motivated by the cap-loss, 
cache-scope and budget probes. 
Measurement validity. The native experiments distinguish recursive nodes, leaf 
evaluations, ranking evaluations, cutoffs and time. Treating one counter as a 
substitute for all computation can reverse the apparent conclusion, as the clustered 
ordered example shows. Three sequential timing repeats and lack of randomized 
order, CPU isolation or uncertainty intervals support descriptive comparisons only. 
Native timer scope, Worker hydration and search, and browser round-trip duration 
are different quantities.

External validity. The fixtures cover controlled and seeded boards but not the full 
space of legal games. Tactical test positions may be synthetic. A 100-game 
Rule-Based versus Random result is narrow, and it does not calibrate six difficulty 
levels against human skill. Node execution and headless-browser synthetic input do 
not establish physical touchscreen, Wink host, deployment or production behaviour. 
Reproducibility and provenance. The public repository includes raw records, 
harnesses, source excerpts and cryptographic hashes. Appendix B summarizes the 
verification artifacts and scope across each subsystem. A reproducible follow-up 
should archive exact source, build configuration, dependencies, tool versions, 
random seed, raw runs and a measurement protocol together under one immutable 
revision.

CHAPTER 6. CONCLUSION AND FUTURE WORK 
6.1 Work completed and contribution 
The project combines a playable Caro application with an educational sequence on 
representation, rules, heuristic evaluation and adversarial search. The application 
repository provides the user interface and game-side code; the weekly material 
documents the development sequence from initial proposal to search and advanced 
techniques. The presentation project supplies visual and executable teaching 
examples. Separate research artifacts provide controlled search data and record 
experimental boundaries. These products have different purposes and should not be 
treated as one executable engine. [1] [52] 
The technical contribution is the mapping from game decisions to data structures 
and algorithms. A board state supports legal placement, directional line checks, 
history and rollback. A heuristic gives a bounded estimate for nonterminal 
positions, while terminal outcomes take precedence. Minimax specifies alternating 
decisions; Alpha-Beta can discard branches that cannot alter the selected-tree value. 
Candidate generation restricts the search space, and ordering changes traversal 
order. The reference experiments further evaluate incremental Zobrist hashing, 
transposition-table bounds, and iterative-deepening budgets on controlled native 
benchmarks. The application and reference implementations must each be described 
through their own source and evidence. [44] [8] 
The 23 October native record reports agreement and restoration on its finite corpus, 
and the separate Node and browser artifacts exercise selected integration paths. The 
reference data shows a substantial node reduction in one paired example and also 
shows that ordering can consume enough additional evaluation work to remove the 
elapsed-time benefit. The cap-loss and cross-root cache probes expose concrete 
correctness risks. These findings are more useful than a single headline speedup 
because they identify both the assumptions under which the method works and the 
conditions that require more care. 
6.2 Limitations 
First, while the engine's soft tactical cap preserves all immediate 1-ply winning and 
blocking moves, tightening the non-tactical candidate cap at higher depths (from 15 
at Hard to 8 at Master) trades broad positional exploration for deeper 5-ply tactical 
calculation. 
71 


=== PAGE 81 ===
Second, the active WebAssembly engine uses stateless fixed-depth Alpha-Beta 
search per turn without a persistent cross-turn transposition table or wall-clock 
iterative deepening, and empirical evaluation is currently scoped to controlled 
benchmark fixtures and automated bot-versus-bot matches rather than large-scale 
human tournament play. [41] [44] [8] [40] 
Third, the static heuristic evaluator scans maximal contiguous runs and therefore 
relies on multi-ply search recursion and the tactical candidate assessor to recognize 
gapped formations (such as XX_XX) or multi-axis forks, motivating the future 
enhancements outlined below. 
6.3 Future development 
1. Publish a reproducible source bundle. Include the exact current Rust engine, 
reference library, manifests, lockfiles, harnesses, recorded hashes and build 
instructions under immutable revisions. Record any local modifications instead of 
presenting an earlier baseline as the measured source. Provide a script that 
compares binary hashes and states the platform and toolchain. 
2. Expand rule and tactical testing. Add board-edge and long-line cases, occupied 
and out-of-range inputs, full-board draws, simultaneous threats, undo after terminal 
states and independently checked randomized move sequences. Compare 
TypeScript and WebAssembly outcomes under an explicit terminal-turn convention. 
Each new rule variant needs its own contract and oracle. 
3. Measure candidates and order policies separately. Use a fixed corpus of reachable 
positions, include known immediate wins and blocks, compare all-legal and 
selective search, and report missed tactics, decision quality, ranking evaluations, 
nodes and elapsed time. Separate soft-cap tactical retention from a hard cap; record 
ties and ordering cost. 
4. Harden and test table reuse. Specify the key namespace for rules, evaluation 
weights, root perspective and mate distance; validate exact/lower/upper entry 
semantics at varying depths and windows. Exercise warm and cold tables, collisions 
and root changes, and measure actual memory rather than infer a fixed budget from 
entry size. 
5. Improve interruption and telemetry. Define whether counters include aborted 
iterations and whether a depth means requested or completed depth. Test 
cancellation, reset, stale replies, Worker failure and restoration, with an explicit 
72 


=== PAGE 82 ===
last-completed-result policy. Propagate real measured statistics consistently through 
the UI. 
6. Evaluate user-facing behaviour. Run repeatable browser tests with real input, 
more viewport sizes and target devices; test the actual host integration separately. 
Measure end-to-end latency and frame timing in the intended environment, with 
enough repetitions and disclosed methodology. A human usability or difficulty 
study requires participants, protocol and consent before results can be claimed. 
7. Synchronize the educational presentation. Mark illustrative code and figures, link 
measured charts to their source data and update outdated labels. Ensure that a 
four-direction description corresponds to code that actually scans four directions, or 
labels a horizontal example accurately. Keep narrative claims distinct from 
executed results.

The historical chronology is organised by the folders rather than by an unsupported 
claim that every later algorithm was integrated into the shipped game. Weeks 1–3 
frame the problem, board and UI; Week 4 examines local patterns and baseline 
bots; Weeks 5–6 develop adversarial search and pruning; Weeks 7–8 focus on 
candidate selection and traversal order; Weeks 9–10 discuss hashing, table reuse 
and interrupted iterative search. The dated evidence in research must be used to 
establish which experiment actually ran and when. [52] [8] 
Weekly deliverables and completion targets. The ten-week schedule below 
summarizes the progression of problem modeling, core engine implementation, 
adversarial search optimization, and empirical verification across W01–W10. 
W01: Define board, actors, Freestyle scope and source boundaries; deliver the 
problem model and stated assumptions. 
W02: Specify coordinate and state operations; demonstrate valid/invalid moves, 
win and draw checks on named fixtures. 
W03: Describe UI ownership and match lifecycle; trace move, Undo, Reset and 
stale-request handling through their owners. 
W04: Describe run patterns, evaluation and Random/Rule-based baselines; give a 
reproducible worked evaluation and identify the implementation. 
W05: Specify Minimax recurrence, depth, apply/undo invariant and a traced 
example; identify the tested candidate set. 
W06: Specify Alpha-Beta bounds and cutoff; compare root scores to Minimax 
under the same fixed search context. 
W07: Specify radius, soft cap, immediate-tactic retention and six configurations; 
distinguish selection from filtering limits. 
W08: Compare ordering with identical membership; record value, node and 
ranking-work definitions rather than assuming a speedup. 
W09: Describe Zobrist updates and TT bounds; verify restoration and disclose 
collision, root-context and mate-score reuse hazards. 
W10: Specify iterative deepening and budget interruption; show last completed 
result and restoration, and mark integration or tournament evaluation pending 
without execution evidence.

npm test

cd present
