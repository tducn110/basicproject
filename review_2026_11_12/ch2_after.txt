CHAPTER 2. ALGORITHMS AND DATA STRUCTURES
2.1 Scope, evidence, and notation
This chapter develops the board representation, terminal rule, evaluation function and search algorithms used in the Caro project. The current frontend and its Worker adapter are examined alongside two research implementations: the modified Rust engine recorded in the 23 October source snapshot [6], and the separate native reference engine [8]. The active application calls a vendored WebAssembly package through the request interface and Worker adapter [3], [9], [26]. These sources have different roles: frontend source establishes request and commit behavior, Rust source explains the recorded algorithm, and binary execution establishes the behavior of the tested package.
The repository also retains a TypeScript bot under src/game/bot. It is referred to as the legacy bot because AIController sends ordinary requests to GomokuWasmEngine and uses a separate tactical check for the four higher difficulty levels. Iterative deepening, quiescence search and transposition-table examples in this chapter come from that legacy implementation [3], [11]. Experiments on the separate Rust reference engine are identified as native reference results [8].
The notation throughout uses an N × N board with N = 15 and winning length K = 5 unless stated otherwise. Coordinates (x,y) mean column and row, respectively, with both in 0…14. In frontend code the equivalent coordinate is (row,col) = (y,x). A ply is one placed stone. Let B denote a board, p the side to move, opp(p) the other side, and m a legal move. The transition T(B,p,m) places p at m; it is defined only if the cell is empty and the game permits a move. Let A(B,p) be the moves the selected search policy actually generates, which may be a strict subset of the legal empty cells. A root player R is the player whose advantage is represented by a larger score. These distinctions matter because a proof about the generated search tree cannot establish a claim about every legal move if the generation policy has already excluded some moves.
The formulations and pseudocode state the input, transition rule and assumptions of each algorithm. Worked examples illustrate their operation; measurements are presented separately in Chapter 5. Depth-limited search follows the distinction between look-ahead and static horizon evaluation described by Shannon [12].
2.2 Board representation and legal updates
2.2.1 Matrix, index conversion, and state ownership
A position contains 225 cells, each empty, X or O. For a logical matrix B[y][x], row-major conversion is i = 15y + x, with inverse x = i mod 15 and y = floor(i/15). The center (7,7) therefore has index 112, and (14,14) has index 224. In the modified Rust source, Board stores a 15 × 15 array of repr(u8) cells and a move counter. Its cell values are Empty = 0, Black = 1 and White = 2; the array occupies 225 bytes, while the complete Board also contains the counter and any alignment padding [6], [13]. The frontend GameState instead stores occupied coordinates in a Map and maintains ordered move history [14]. The legacy BotBoard uses a one-dimensional array padded with boundary sentinels. These representations support different operations: direct Rust cell access, frontend match history, and incremental line analysis in the legacy bot.
In the modified Rust snapshot, Board::place checks bounds, rejects an empty stone or occupied cell, writes the stone and increments move_count. Board::undo rejects an invalid or empty coordinate, then clears the occupied cell and decrements the counter [6]. These operations maintain the position. Turn alternation, move history and terminal lockout belong to the Rust Game wrapper and the frontend match controller, rather than to Board::place itself [2].
Board mutation and match progression have separate owners. Board holds the cells and move count; Game and the frontend controller maintain turn, result and history. Search explores hypothetical moves on a working board, while the match commits only the selected move. The modified Rust search clones the root board once and applies and undoes moves within that copy [6]. This avoids a complete board copy for each child, although candidate generation still allocates move lists at internal nodes.

2.2.2 Apply and undo
Inputs and output. APPLY(B,m,p) takes the working board, a coordinate and a nonempty player; it returns success or failure. UNDO(B,m) takes the coordinate of a previously applied move and returns whether removal was possible. The stronger search precondition is that undo is paired with the most recent successful hypothetical move on that branch. An individual undo that merely removes an occupied cell does not enforce the whole history discipline.
// Algorithm 2.1 (modified Rust source in [6]) — APPLY(B, (x,y), p):
    if x or y is outside the board, or p is empty: return failure
    if B[y][x] is not empty: return failure
    B[y][x] ← p
    B.move_count ← B.move_count + 1
    return success

UNDO(B, (x,y)):
    if (x,y) is outside the board or B[y][x] is empty: return failure
    B[y][x] ← empty
    B.move_count ← B.move_count - 1
    return success

VISIT_CHILD(B, p, m):
    require APPLY(B, m, p) succeeds
    try: value ← VISIT(B, opp(p), m)
    finally: require UNDO(B, m) succeeds
    return value
The try/finally structure in this explanatory pseudocode requires restoration after a return, cutoff or supported abort. An implementation must provide equivalent cleanup for every exit it supports. A matching apply/undo restores the cell and count in O(1) time; hashes, cached patterns, turn and other mutable fields must be restored separately by their owners. The modified Rust kernel uses structured returns without a deadline-abort path, whereas the legacy TypeScript search uses try/finally when it can throw a search-abort sentinel.
Invariant and argument. Immediately before exploring each sibling, the working state must equal the state at the parent node. A successful apply changes exactly the selected empty cell and increments the count. Its matching undo clears that same cell and decrements the count; therefore these fields equal their former values. By induction over nested calls, assuming each recursive child restores every state field it owns, the parent sees the same state for the next sibling. The induction depends on legal matching calls; it is not guaranteed if an exception bypasses undo or a different move is removed.
For example, let X occupy (7,7), O occupy (8,7), and move_count be two. Applying X at (7,8) sets that cell and raises the count to three; undoing the same move restores both fields. Clearing the cell without decrementing the counter would make fullness checks unreliable. With direct indexing, each cell/count update takes O(1) time and O(1) auxiliary space; copying an N × N board takes O(N²). The archived native experiment records 820 successful working-board restoration checks, including repeated search configurations. This is the finite test result used in Chapter 5 [43].

2.3 Freestyle win detection
The frontend win rule treats a contiguous line of at least five stones as a win, including an overline of six or more. It checks four axes through the last move, with both directions on each axis. It does not require exactly five or impose an additional two-blocked-ends condition [4]. The term Caro is used for the application, but this particular rule is specified explicitly because games with similar names may use other winning conditions.
The procedure receives a valid board and the last placed coordinate m. It returns the winning player and collected winning cells, or no result. It assumes the preceding position was unfinished, so any newly created winning line passes through m. An arbitrary imported position instead requires a full-board result check at the search root. Under the frontend state contract, an empty last-move coordinate yields no winner [4].
For directions D = {(1,0), (0,1), (1,1), (1,-1)}, let f_d and b_d count consecutive stones equal to the stone at m in the positive and negative direction. A win through the last move occurs exactly when some 1 + f_d + b_d ≥ K. To decide whether the threshold is reached, scanning at most K−1 matching cells in each direction is sufficient: any additional cells cannot change a negative result to a positive result after K−1 matching cells already exist on one side.
// Algorithm 2.2 (CaroGame/src/game/core/WinRules.ts) — WIN_AT(B, m, K):
    if m is out of bounds or B[m] is empty: return NONE
    p ← B[m]
    for d in [(1,0),(0,1),(1,1),(1,-1)]:
        cells ← [m]
        for sign in [+1,-1]:
            for step from 1 to K-1:
                q ← m + sign * step * d
                if q is outside or B[q] ≠ p: break
                append q to cells
        if length(cells) ≥ K: return (p, cells)
    return NONE
The scan invariant is that every collected cell is on the selected axis, adjacent to the preceding segment and occupied by p. Stopping at the first boundary or different cell prevents joining disconnected sequences. If a contiguous run through m has length at least K, either its collected positive and negative portions together reach K−1 neighbors or a single portion does, so the check succeeds. Conversely, K collected stones form a contiguous same-player segment through m, establishing the stated rule. The returned display collection may be truncated to K−1 stones per side; it is sufficient to prove a win but is not necessarily the full maximal overline.
For X X [X] X X on a row, with the bracketed cell placed last, each side contributes two stones and 1 + 2 + 2 = 5. For X X X [X] X X, the run exceeds five and is still a win. A gap or board edge stops the corresponding scan. With K = 5, the frontend examines at most 4 × 2 × 4 = 32 neighboring positions, giving O(K) time and O(K) space for the collected cells. These bounds are constant for the configured winning length. A full-board scan checks every occupied starting point and has a different cost; the report does not infer an elapsed-time speedup from the operation count alone.

2.4 Baselines: random play and rule-based play
2.4.1 Random baseline
A random baseline selects a legal move without comparing future replies. In the modified Rust snapshot, Easy first rejects an empty player or terminal board, enumerates empty cells, and selects an index using a seeded 64-bit mixer modulo the list length. It evaluates the chosen move afterwards to populate the result; that evaluation does not influence selection [6].
// Algorithm 2.3 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — RANDOM_MOVE(B, p, seed):
    if p is empty or B is terminal: return NONE
    L ← all legal empty cells in B
    if L is empty: return NONE
    i ← SEEDED_INTEGER(seed) mod length(L)
    return L[i]
The seed is part of the input because the mixer is deterministic. The output is a member of L or no move. A board with one stone has 224 empty cells, while a one-element list always returns its sole coordinate. Terminal handling precedes modulo selection, so a full board cannot cause division by zero. Index selection takes O(1) after enumeration. Modulo reduction does not in general produce an exactly uniform distribution over arbitrary list lengths.
Gathering all cells takes O(N²) time and O(N²) space in the worst case; selection after that is O(1). A post-selection evaluation has its own cost. A fixed seed makes the selection reproducible under the same generator and ordering, not necessarily across different implementations or changed inputs. A random policy does not promise to notice an immediate win or threat.
2.4.2 Immediate tactics and one-ply heuristic
The modified Rust Normal policy selects an immediate win when one is available, then an immediate blocking coordinate, and otherwise the highest-valued one-ply candidate. Candidate assessment supplies the win and block markers [6]. The frontend has a separate tactical resolver for Hard, Very Hard, Expert and Master; Easy and Normal bypass it. A frontend tactical result identifies its source as tactical and reports zero Rust nodes, because it returns before a WASM request [3], [10].
// Algorithm 2.4 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — RULE_BASED(B, p, policy):
    if B is terminal or p is invalid: return NONE
    C ← SELECT_CANDIDATES(B, p, policy)
    if an m in C wins immediately for p: return m
    if an m in C is an immediate winning cell for opp(p): return m
    best_move ← NONE; best_score ← -infinity
    for m in C:
        APPLY(B,m,p)
        try:
            score ← TERMINAL_OR_EVALUATE(B,p,m)
        finally:
            UNDO(B,m)
        if best_move is NONE or score > best_score:
            best_move ← m; best_score ← score
    return best_move, best_score
The decision invariant after processing the first j non-tactical candidates is that best_score is the greatest observed value among those j moves and the board is restored. A separate invariant places the win and block checks before the one-ply loop. Thus the routine picks the best score among the evaluated candidates when neither tactical condition applies. Correctness of the tactical marker itself depends on the assessment recognizing the corresponding winning geometry and on the move being included in C.
For a concrete threat, suppose X occupies row 0, columns 0–3, column 4 is empty, and O is to move. The left endpoint lies outside the board; placing O at (4,0) blocks the only immediate completion along this row. If the same four consecutive X stones are in the interior with both endpoints empty, there are two distinct winning cells. A single O move can occupy one cell, not both. Retaining both choices avoids losing information but does not establish that either saves the game. Similarly, an immediate winning move for O takes priority over blocking if both are available under the algorithm's ordering.
If k candidates are generated, one-ply evaluation costs roughly O(k × evaluation-cost), in addition to candidate generation and ordering. A constant-time local win scan does not make the whole rule-based procedure constant time. A nonterminal board with no generated move requires a defined fallback or no-move response; terminal handling must precede any selection. A short tactical prepass is not a substitute for searching through arbitrary combinations.

2.5 Static evaluation and terminal utility
2.5.1 Evaluation of nonterminal positions
A search with finite depth can stop before a winner exists. Its evaluator assigns an approximate score to that horizon position. In the documented modified Rust snapshot, evaluate scans maximal contiguous runs in four directions, adds the root player's run weights, subtracts the opponent's, and adds or subtracts a center preference. The snapshot counts a run once per axis by skipping a cell when the previous cell on the same axis has the same color. It then clamps the final heuristic to a range below terminal scores [6].
Let R_p(B) be maximal runs of p over the four axes, len(r) their length and open(r) their number of empty endpoints. Let c(x,y)=max(0,14−|x−7|−|y−7|) and C(B,p) be p's sum of c minus the opponent's. The descriptive formula is
E_raw(B,p) = Σ[r∈R_p(B)] w(len(r),open(r)) − Σ[r∈R_opp(B)] w(len(r),open(r)) + C(B,p).
The archived evaluator assigns weights of 1,000,000 to a run of at least five; 50,000 or 5,000 to a four with two or one open ends; 5,000 or 500 to a three; and 200 or 50 to a two. A run of five or more receives the same weight even with closed ends. Other cases receive zero [15]. These manually chosen weights favour longer, open formations, while the center term adds a smaller positional preference. They are heuristic parameters, rather than a proof that a named threat always outweighs every combination of shorter runs.
// Algorithm 2.5 (modified Rust evaluator in [6]; run weights in [15]) — EVALUATE(B, p):
    score ← 0
    for each occupied cell s:
        for d in the four axes:
            if preceding cell along d has the same color: continue
            (length, open_ends) ← scan maximal same-color run
            value ← WEIGHT(length, open_ends)
            if B[s] is p: score ← score + value
            else: score ← score - value
        score ← score + center contribution signed by color
    return CLAMP(score, -H, H)
After each visited run start, score contains the signed run contributions processed so far and the center contributions of previously visited occupied cells. The preceding-cell guard skips interior stones of the same run. Every maximal run therefore contributes once per axis, even when it contains several stones.
For a board containing only X at (7,7), no length-two-or-longer run contributes, and the center term gives E(B,X) = 14. Adding X at (8,7) creates an open horizontal two worth 200; the center terms are 14 and 13, giving 227. For a run shorter than five, changing an empty endpoint to an occupied endpoint changes its open-end classification and corresponding weight. A board boundary also closes an endpoint.
Scanning maximal runs in four directions takes O(N²) time and O(1) auxiliary space beyond the board: each occupied cell belongs to at most one maximal run per direction. This evaluator counts contiguous runs. A split formation such as XX_XX is represented as separate runs at the horizon, although candidate assessment can identify the empty gap as a winning completion. Thus horizon evaluation and tactical move assessment capture different properties of the position.

2.5.2 Terminal states and the score hierarchy
Terminal outcomes are checked before the depth cutoff. In the modified Rust snapshot, M = 100,000,000 and q is the ply distance from the root, capped at 225. A root win returns M − q, a root loss returns −M + q, and a draw returns zero. Nonterminal evaluations are clamped to the closed interval [−H,H], where H = M − 225 − 1 = 99,999,774 [6].
// Algorithm 2.6 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — TERMINAL_UTILITY(winner, full, root, ply):
    q ← min(ply, 225)
    if winner = root: return M - q
    if winner is the opponent: return -M + q
    if full: return 0
    return NONE
The clamp ensures every nonterminal heuristic lies between −H and H. Since M−225 = 99,999,775 > H, even the slowest represented win exceeds a nonterminal score; similarly a loss is below every nonterminal score. A win at q=2 receives 99,999,998 and a win at q=4 receives 99,999,996, so maximizing prefers the earlier win. Conversely, if a loss is unavoidable, increasing q makes its negative score less severe and thus delays the loss. This preference follows from the formula; it is conditional on the search actually reaching and correctly identifying those terminal outcomes. The winner must be decided before a full-board draw when the last empty cell completes a line.
2.6 Candidate generation and a soft tactical cap
2.6.1 Spatial neighborhood
Considering every empty cell creates a large branching factor. A candidate policy can instead choose empty cells close to existing stones. For cells a and b, Chebyshev distance is d∞(a,b)=max(|a_x−b_x|, |a_y−b_y|). With radius r, a spatial candidate is an empty cell within distance r of at least one occupied cell. The empty board has a special center choice, and a full board has no move. The exact selection, fallback and ranking below describe the archived modified-engine policy, not the legacy bot's different forcing-move generator [6].
// Algorithm 2.7 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — RAW_CANDIDATES(B, r):
    if B is full: return []
    if B has no stones: return [center]
    seen ← N × N false array; C ← []
    for each occupied cell s in B:
        for each q in the radius-r square around s clipped to the board:
            if B[q] is empty and not seen[q]:
                seen[q] ← true
                append q to C
    return C
For a stone at (7,7), radius one gives a 3 × 3 square with eight empty candidates; radius two gives a 5 × 5 square with 24. With the single stone at (0,0), the radius-two square is clipped to a 3 × 3 corner and yields eight candidates. Multiple stones may nominate the same cell, but seen prevents duplicates. If a radius produces no raw candidates on a nonfull board, the documented selection code falls back to legal moves, avoiding an occupied placeholder. An empty player and a full board return no candidates [6].
Each appended coordinate is in bounds, empty and previously unseen. Conversely, every empty cell in a visited neighborhood is appended on its first encounter. This establishes membership in the radius policy. With m occupied cells, board scanning and neighborhood enumeration take O(N² + m(2r + 1)²) time before assessment; the seen matrix and move list use O(N²) space. The policy reduces the set searched, but can exclude legal moves outside the chosen neighborhood.

2.6.2 Tactical preservation and membership
For each raw move, the documented select_candidates assesses whether it wins for the moving side, blocks an immediate opponent win, and assigns a quick ranking score. Sorting prioritizes a win, then a block, then descending score, with row-major coordinates used to break ties. If a cap is configured, the ranked list is truncated at max(cap,1,tactical_count), so every assessed immediate winning or blocking coordinate remains even if the number of such coordinates exceeds the cap. After selecting membership, disabling move ordering sorts the retained set by coordinate rather than changing its members [6].
// Algorithm 2.8 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — SELECT_CANDIDATES(B, p, policy):
    if p is empty or B is full: return empty set
    raw ← RAW_CANDIDATES(B, policy.radius)
    if raw is empty and B is not full: raw ← LEGAL_MOVES(B)
    ranked ← ASSESS each move for win, block, and quick score
    sort ranked by win first, block second, score descending, coordinate
    tactical_count ← count of entries marked win OR block
    if policy.cap exists:
        retain first max(policy.cap, 1, tactical_count) entries
    if ordering is disabled: sort retained entries by coordinate
    return retained entries and assessment metadata
Let C be the raw set, T its marked tactical subset, and c the configured cap normalized to at least one. The selected set is the union of T and enough highest-ranked non-tactical members to reach c when possible. If |T|=2 and c=1, both tactical moves remain, so this is a soft cap, not an absolute maximum. The proof depends on tactical entries being ordered before every non-tactical entry and on every relevant move first being in raw. It does not show that all useful multi-ply tactical moves are preserved, or that a move excluded by the spatial policy is later recovered by the cap.
For k raw candidates, bounded directional assessment takes O(kK), sorting takes O(k log k), and move storage takes O(k), in addition to neighborhood generation. Let C be the raw set, T its assessed win-or-block subset, and c the normalized cap. Selection retains T plus the highest-ranked non-tactical moves needed to reach c, when available. Its total size is min(|C|, max(c, |T|)); it can exceed c. The separate native reference experiment in cap_loss.json illustrates the danger of a hard cap: cap 6 retained six of twenty candidates and omitted both winning endpoints. That result concerns the reference policy, while the modified policy preserves every assessed member of T [16].
2.7 Move ordering versus move selection
A search traverses the retained moves in an order. Ordering permutes an already chosen set; filtering or capping changes its membership and therefore the tree itself. In a complete minimax evaluation of the same deterministic tree, any permutation produces the same value, although a tied best move can differ if the first best move is retained. In alpha-beta search, ordering influences how soon useful bounds are discovered and can alter the number of cutoffs, while preserving the root value under the algorithm's assumptions [17].
// Algorithm 2.9 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — ORDER(retained_moves, rank):
    calculate a rank key for each retained move
    sort by the chosen key with a deterministic tie breaker
    return the same moves in the new order
If A, B and C have quick scores 10, 50 and 30, score order is B, C, A, whereas coordinate order may be A, B, C. Ranking B first does not establish that it is the best searched move. Minimax still evaluates every retained child; alpha-beta may reach a useful cutoff sooner. Sorting k moves takes O(k log k), plus key computation and O(k) move storage in the described implementation. Whether the saved search work outweighs ranking cost is measured in Chapter 5.
The documented candidate selection uses fast local information for ranking; the historical reference experiment uses its own evaluation and ordering behavior [6], [8]. Comparisons should hold the board, depth, scoring, candidate membership and terminal rules fixed, changing only ordering. Equal values but different tied moves can both be consistent. A comparison that changes both cap and ordering cannot isolate ordering's effect.

2.8 Minimax search
2.8.1 Recurrence and contract
Minimax assumes two alternating decision-makers. MAX chooses a move to maximize a score from the root player's perspective; MIN chooses to minimize it. Its input is the current board, the side to move, a nonnegative depth d in plies, the last move when available, a candidate policy and an evaluator. The output is a value and, at the root, a selected move, or no move for an already finished game. State includes the mutable working board, remaining depth, root perspective and recursion stack. Search must begin from a board compatible with the chosen rules, or validate it separately.
Let U(s,R,q) be terminal utility at root distance q, and E(s,R) the nonterminal horizon evaluation. Transition T(s,a) places the side-to-move stone and changes the turn. For a fixed candidate function A and rule/evaluation configuration, the depth-limited value is
V(s,d,q) = U(s,R,q) if s is terminal;
V(s,0,q) = E(s,R) if s is not terminal;
V(s,d,q) = max[a∈A(s)] V(T(s,a),d−1,q+1) if MAX moves;
V(s,d,q) = min[a∈A(s)] V(T(s,a),d−1,q+1) if MIN moves.
An empty generated set for a nonterminal board must have a specified behavior. The documented value routine returns zero for an empty list, while candidate fallback is intended to avoid this on a nonfull valid position. That fallback convention should not be silently reinterpreted as a win or as a comprehensive validation of arbitrary positions [6].
// Algorithm 2.10 (research/current_2026_10_23/SOURCE_EXCERPTS.md) — MINIMAX(B, player, root, depth, last, ply):
    t ← TERMINAL_UTILITY(winner from WIN_AT(B,last), IS_FULL(B), root, ply)
    if t exists: return t
    if depth = 0: return EVALUATE(B,root)
    moves ← SELECT_CANDIDATES(B,player)
    if moves is empty: return 0   // documented convention for this case
    best ← -infinity if player = root else +infinity
    for m in moves:
        require APPLY(B,m,player)
        try: v ← MINIMAX(B,opp(player),root,depth-1,m,ply+1)
        finally: require UNDO(B,m)
        if player = root: best ← max(best,v)
        else: best ← min(best,v)
    return best
The root routine validates an existing result, searches each retained root move, stores a best action and restores the board after each branch. Recursive checks use the just-played coordinate, because a newly formed line passes through that move. The modified Rust implementation uses one recursive kernel whose configuration enables plain minimax or alpha-beta pruning while retaining the same candidate policy and evaluator [6].
2.8.2 Proof, example and complexity
Use induction on d. For terminal nodes or d=0 the procedure returns exactly the corresponding definition. Assume recursive results equal V for depth d−1 and that each apply/undo restores the parent. At a MAX node the loop's best value after j children is the maximum of the first j child values; at completion it is the maximum over A. The MIN case is symmetric. Each recursive call reduces d, so a finite candidate list guarantees termination. This proves evaluation of the specified finite tree if transition, terminal detection, evaluation and candidate generation satisfy their contracts; it does not prove the evaluator predicts the outcome of an unrestricted game.
In an abstract depth-two tree, MAX has actions A and B; MIN's leaves under A have values 3 and 5, and under B have values 2 and 9. MIN returns 3 for A and 2 for B; MAX chooses A with 3. This two-ply trace illustrates how alternating MAX and MIN backups propagate exact horizon utility values to the root decision.
For branching factor at most b > 1 and depth d, the complete generated tree has O(b^d) nodes. Branching varies with position, candidate policy and terminal events. Depth-first search stores O(d) stack frames, up to O(db) live move entries, and an O(N²) working board. Candidate generation and horizon evaluation add per-node costs, so O(b^d) describes the node growth rather than a complete elapsed-time model.

2.9 Alpha-beta pruning
2.9.1 Bounds and pseudocode
Alpha-beta pruning computes the same root value as minimax on the same finite deterministic tree under a consistent utility and candidate policy, while sometimes skipping subtrees. alpha is the best lower bound MAX can already secure in the current ancestor context; beta is the best upper bound MIN can already secure. At a MAX node, update alpha after observing a child; at a MIN node, update beta. When alpha ≥ beta, the remaining siblings cannot improve the relevant ancestor's decision. Knuth and Moore analyze alpha-beta and the effects of move ordering under stated assumptions [17].
// Algorithm 2.11 (modified Rust search kernel in [6]) — ALPHABETA(B, player, root, depth, last, ply, alpha, beta):
    t ← TERMINAL_UTILITY(winner from WIN_AT(B,last), IS_FULL(B), root, ply)
    if t exists: return t
    if depth = 0: return EVALUATE(B,root)
    moves ← SELECT_CANDIDATES(B,player)
    if moves is empty: return 0
    best ← -infinity if player = root else +infinity
    for m in moves:
        require APPLY(B,m,player)
        try: v ← ALPHABETA(B,opp(player),root,depth-1,m,ply+1,alpha,beta)
        finally: require UNDO(B,m)
        if player = root:
            best ← max(best,v); alpha ← max(alpha,best)
        else:
            best ← min(best,v); beta ← min(beta,best)
        if alpha ≥ beta: break
    return best
Here restoration occurs before a cutoff is tested. The caller starts with an unbounded window when it needs a root result. A value returned from an internally cut-off node may represent a bound rather than an exact independent value. This distinction becomes essential when such results are cached. The code excerpt increments a cutoff counter at a break; that event count is not the total number of theoretical descendant nodes omitted [6].
2.9.2 Worked cutoff and correctness boundary
In the preceding depth-two tree, searching A first returns 3 and raises the root alpha to 3. At B, MIN encounters 2 first and lowers beta to 2. Since beta ≤ alpha, MIN already has an option no greater than 2, so B cannot improve MAX's available value of 3. The remaining leaf, illustrated as 9, can be skipped. The root still selects A with value 3. Another traversal order may produce fewer cutoffs while retaining the same root value.
Alpha and beta summarize bounds supplied by previously examined alternatives and ancestors. When they cross, the remaining siblings cannot improve the relevant ancestor's choice. Combined with the minimax and restoration invariants, this preserves the root value on the same finite tree [17]. The archived modified-engine corpus records 408 minimax/alpha-beta pairs, and the separate native reference corpus records 112 pairs with equal root scores. These totals include repeated configurations; they are finite experiment results, presented with their node counts in Chapter 5 [8], [41], [43].
The worst case remains O(b^d) nodes. For a uniform tree with perfect ordering, the ideal minimum leaf count is b^ceil(d/2) + b^floor(d/2) − 1; for even depth this has the familiar O(b^(d/2)) growth [17]. Neither bound is an elapsed-time prediction, because node costs and branching vary. Memory remains depth-first: O(d) stack frames and up to O(db) live move entries, in addition to the board. Equality cutoffs preserve the root value, although tie selection and visited-node counts can depend on traversal order.

2.10 Iterative deepening and budgets
Iterative deepening performs complete searches at depths 1, 2, … until reaching a configured maximum or a budget interrupts an iteration. Its input is a root position, a maximum depth and a budget. Its output should distinguish the best result from the most recently completed iteration, the completed depth, and the reason for stopping. The working board, search counters, and any table or ordering hints must obey the respective implementation's lifecycle. An incomplete iteration's partially explored best move is not the same as a completed minimax result for that depth.
// Algorithm 2.12 (completed-iteration scheme illustrated by [11]) — ITERATIVE(B, maximum_depth, budget):
    last_complete ← NONE
    for depth from 1 to maximum_depth:
        if budget is exhausted: break
        result ← SEARCH_AT_DEPTH(B, depth, budget)
        if result was interrupted: break
        last_complete ← result
    return last_complete, completed depth, stop reason
The invariant after iteration d is that last_complete corresponds to a whole completed search at d under that iteration's search contract. It follows inductively because the result is replaced only after the iteration returns normally. A separate abort-safe restoration guarantee is required: interruption in a child must unwind all applied moves. If depth one returns A, depth two returns B and depth three aborts, the completed result is B at depth two. If no iteration completes, a caller must explicitly handle the absence of a completed result; a fallback candidate is useful but should be labeled as such.
Repeated shallow searches consume work, although the deepest full iteration can dominate for a sufficiently large, regular branching factor. Each iteration has the complexity of its selected search; total time is the sum over attempted depths plus ordering and bookkeeping. No hard real-time guarantee follows from this scheme. A search interrupted only at periodic checks can exceed its nominal wall-clock deadline before the next check, especially if individual operations are expensive.
The legacy TypeScript findBestMove uses a performance.now() deadline, checks it at the first search node and every 32 nodes, and catches a dedicated abort sentinel. It initializes a fallback candidate before an iteration completes and reports depth zero if the first iteration aborts. Recursive search uses try/finally to undo moves during unwinding [11]. The historical Rust reference instead uses a node budget, and its aggregate excludes work inside an aborted iteration [8]. The modified Rust engine uses the fixed tier depths shown in Table 2.1 [6]. These are separate budget and counter conventions.

2.11 Zobrist hashing and incremental state
2.11.1 Definition and update
A transposition can arise when different sequences of moves lead to the same board and relevant side to move. Comparing all cells at each cache access costs O(N²), so a compact hash can serve as an index. Zobrist's method assigns a pseudorandom word to each (cell, player) pair and combines the keys for occupied cells with exclusive OR (XOR) [19]. One also needs a side-to-move key if the same occupancy can be evaluated with different players to move. The hash is a compact fingerprint, not mathematical proof that two states are identical.
Define Z[x,y,p] as a fixed random word for a stone, and S as a fixed side key. Under one convention,
H(B,p) = XOR Z[x,y,color] over occupied cells, XOR S if p is the designated second side.
All keys must remain fixed for the lifetime of the table. Applying a move of p at m adds its key with XOR. If the transition changes the side, XOR S as well. Undo repeats the same XOR operations in reverse. The essential identity is (h XOR z) XOR z = h.
// Algorithm 2.13 (Zobrist scheme illustrated by the legacy board in [20]) — FULL_HASH(B, player):
    h ← 0
    for each occupied cell m with stone color c: h ← h XOR Z[m,c]
    if player is designated second side: h ← h XOR S
    return h

UPDATE_HASH(h, m, p, side_changed):
    h ← h XOR Z[m,p]
    if side_changed: h ← h XOR S
    return h
For a four-bit example, let h = 1010 and the inserted stone key be 0110, temporarily omitting the side key. Applying XOR gives 1100; applying XOR with 0110 again restores 1010. The same identity applies to each half of the legacy bot's 64-bit fingerprint. XORing both the stone key and side key on make and undo restores the hash in O(1) time; restoring cached line counts has its own cost.
The hash invariant is incremental_hash = FULL_HASH(current board, current side). It holds initially if computed from the board; XORing the stone's key exactly accounts for adding that feature, and XORing the side key exactly accounts for a side change. Repeating those operations removes the features on undo. This proof assumes the same keys, actual transition semantics, and no omitted state features relevant to the hash contract. It does not eliminate collisions.
The legacy board stores the fingerprint as two 32-bit halves and uses a seeded table of stone and side keys. Make and undo also update pattern counts and stoneCount [20]. These fields must all return to their preceding values; the hash alone is not a complete restoration check. In the separate native reference, a winning move can leave to_move unchanged, so the side-key update follows that implementation's actual turn transition [8].
A full recomputation scans O(N²) cells; one incremental XOR update uses O(1) time. The key table has O(N²) entries for a fixed number of players; the board and any pattern caches have their own space costs. A finite hash collision remains possible even when incremental and recomputed hashes agree on every tested position. A table may verify a full key or full state, or otherwise accept a defined collision risk. A player key alone also does not encode rules, search depth, evaluator, root perspective or a candidate policy.

2.12 Transposition table: entries, bounds and context
2.12.1 Meaning of stored values
A transposition table (TT) maps a position fingerprint to a previously computed search result. A typical entry stores a hash or verification key, remaining search depth, value, bound type and a suggested best move. The move may help order later search even if the stored score is unusable. A cache lookup is sound only when its represented search problem is compatible with the current one, its depth is sufficient under the selected contract, and its bound justifies the requested cutoff or exact result.
For an original search window [α₀,β₀], a common classification is: result v ≤ α₀ is an upper bound; v ≥ β₀ is a lower bound; and α₀ < v < β₀ is exact, subject to the search's assumptions. Equality is treated conservatively at the boundary. For instance, with window [3,8], a returned 2 is an upper bound, 5 is exact and 9 is a lower bound. Consequently, a stored LOWER bound triggers an immediate cutoff whenever entry.score ≥ β, and an UPPER bound triggers a cutoff whenever entry.score ≤ α.
// Algorithm 2.14 (general TT contract; legacy implementation in [11]) — PROBE(key, required_depth, alpha, beta, context):
    entry ← table.lookup(key)
    if entry missing or key/context is incompatible: return MISS
    hint ← entry.best_move if it is legal in this position else NONE
    if entry.depth < required_depth: return HINT_ONLY(hint)
    if entry.bound = EXACT: return VALUE(entry.score, hint)
    if entry.bound = LOWER and entry.score ≥ beta:
        return VALUE(entry.score, hint)
    if entry.bound = UPPER and entry.score ≤ alpha:
        return VALUE(entry.score, hint)
    return HINT_ONLY(hint)

STORE(key, depth, score, alpha_original, beta_original, best_move):
    if score ≤ alpha_original: bound ← UPPER
    else if score ≥ beta_original: bound ← LOWER
    else: bound ← EXACT
    store key, depth, score, bound, best_move according to replacement policy
The probe is sound only when the key, search context, score convention and depth interpretation are compatible. Checking depth, bound type and move legality alone does not establish all of these conditions. Classification uses the original search window, and storage and retrieval must agree about fail-hard or fail-soft returns. A conventional entry.depth ≥ required_depth test accepts deeper results; strict equality with a particular depth-limited horizon requires an additional depth-reuse contract.
2.12.2 Why reuse can be wrong
A useful invariant is: whenever a TT score is reused, it is valid for the current position, depth interpretation, perspective, rule set, evaluation and move-generation context, and its bound permits the intended conclusion. An exact compatible entry may answer a query; a lower or upper bound is usable only in its permitted direction. If any premise is false, the stored number can change the decision. A full hash comparison narrows ordinary index collisions but still does not guarantee that different game states cannot share a fingerprint.
The native reference records a context-reuse failure: after a clustered depth-4 search, same-root warm reuse returns the same score of 0, but after playing a move and changing the root player, a fresh table returns 0 and the reused table returns 19,800 [21]. The stored scores are root-relative, and the key omits that perspective as well as other configuration fields. This is a result from the reference engine. It motivates matching cache lifetime to the search context. Ply-relative mate scores also require normalization or a restricted reuse scope when stored values can be reached at a different root distance.
The legacy TypeScript table uses fixed-size parallel arrays. A slot is indexed from the low hash half, then both halves are compared before its depth, flag and score are considered. The stored move is used as an ordering hint [11]. The native reference instead uses a hash map [8]. These storage choices do not establish compatibility between search contexts. A hint must refer to a legal retained move before it influences move application, and cache lifetime must match the interpretation of its stored scores.
Expected lookup is O(1) for a suitably configured hash table; actual access cost depends on indexing, collisions and replacement. Memory is proportional to allocated slots or entries, together with container overhead. A hash map's initial capacity is not a maximum, and the size of one entry is not the container's total allocation. A TT can save repeated search work and supply move hints, at the cost of memory and the need to preserve compatible score and state semantics.

2.13 Quiescence search in the legacy TypeScript bot
A fixed-depth horizon can fall immediately before a forcing reply, causing a static evaluation to overrate the position. Quiescence search extends selected tactical continuations beyond that horizon. The legacy TypeScript bot implements this extension with a separate depth limit and forcing-move generator [11]. Its result describes that selective continuation tree.
Inputs and state. The legacy routine receives the board, alpha and beta bounds, current ply and a quiescence depth. It works from the perspective of the side to move, uses negamax sign reversal, increments a node counter and checks for abort. Its state includes board cells, side, hash and cached pattern counts. Its output is a bounded score for the selected forcing continuation, or an abort propagated to the caller. It first checks whether either side has a five pattern. It then calculates standPat, applies a beta cutoff if that static score is at least beta, raises alpha if appropriate, and stops at quiescence depth five. Otherwise it generates forcing candidates, orders them and recurses after a move with (-beta,-alpha); each recursive branch uses try/finally to undo [11].
// Algorithm 2.15 (CaroGame/src/game/bot/search.ts) — QUIESCENCE(B, alpha, beta, ply, qDepth):
    count node; check budget or deadline
    if previous player has a five: return -MATE + ply
    if side to move has a five: return MATE - ply
    standPat ← EVALUATE_FROM_SIDE_TO_MOVE(B)
    if standPat ≥ beta: return beta
    alpha ← max(alpha, standPat)
    if qDepth ≥ 5: return alpha
    moves ← GENERATE_FORCING_CANDIDATES(B)
    order moves by their quick score
    for m in moves:
        MAKE(B,m)
        try: v ← -QUIESCENCE(B,-beta,-alpha,ply+1,qDepth+1)
        finally: UNMAKE(B,m)
        if v ≥ beta: return beta
        alpha ← max(alpha,v)
    return alpha
The sign change reflects the negamax convention for an evaluation whose perspective changes with the side to move. The procedure returns beta on a fail-high and alpha otherwise, so its return can be a bound rather than an exact unrestricted game value. Its loop invariant is that alpha is at least the stand-pat score and all examined forcing continuations, subject to the window and fail-hard convention; the board must equal the incoming state before every sibling. The depth limit guarantees termination even when forcing candidates continue to exist. It also creates a new horizon.
For a simplified numeric example, suppose the window is [−10,10], stand-pat is 2, and the first searched forcing move returns 6 after sign reversal. Alpha rises to 6. If another move returns 12, the routine returns beta, 10, as a fail-high bound. This does not assert that 10 is the exact minimax value. In a real position, the forcing generator's definition and threat patterns decide which moves are included. The legacy code considers outcomes such as five, open four and four for either side when identifying forcing moves. These categories arise from its own bitmask pattern evaluator, which differs from the snapshot's contiguous-run evaluator [11], [20].
Stand-pat evaluation supplies the initial bound without placing a stone. Because Gomoku requires a move, this is a modelling assumption rather than a legal pass; an immediate cutoff in a forced-defense position need not equal an all-legal-replies result. The forcing set and the five-level extension limit define the selective horizon. With at most f > 1 forcing moves per level and q extra levels, a coarse bound is O(f^q) nodes and O(qf) stored move entries, plus per-node generation, ordering and evaluation costs. If f = 1, node growth is O(q).
2.14 Legacy bitmask patterns and incremental line counts
The legacy TypeScript bot classifies a line segment with a bitmask: one denotes the player's stone and zero an empty cell, while an opposing stone ends the segment. Its evaluator precomputes categories for segment lengths up to 15 using tests for existing fives and empty cells that would complete a five. The categories are FIVE, OPEN_FOUR, FOUR, OPEN_THREE, BROKEN_THREE and NONE. They follow this classifier's completion-count rules and differ from the modified Rust evaluator's contiguous-run weights [20], [53].
// Algorithm 2.16 (legacy pattern evaluator in [53]) — CLASSIFY_SEGMENT(mask, length):
    if mask contains five consecutive 1 bits: return FIVE
    wins ← number of zero positions which become a five when set
    if wins ≥ 2: return OPEN_FOUR
    if wins = 1: return FOUR
    threats ← number of zero positions which, when set,
              leave at least two immediate winning positions
    if threats ≥ 2: return OPEN_THREE
    if threats = 1: return BROKEN_THREE
    return NONE

COUNT_LINE(B, p, start, step, length):
    split the line wherever an opponent stone occurs
    encode p and empty cells of each segment as a mask
    for each segment of length at least 5:
        increment the bucket returned by CLASSIFY_SEGMENT
    return counts
For the five-cell segment XX_XX, setting the middle zero creates five consecutive bits, giving one winning completion and the FOUR category. A segment with two distinct winning completion cells is OPEN_FOUR if no five is already present. The category is computed for the whole segment, with the precedence in Algorithm 2.16; an opposing stone or board boundary ends that segment [53].
The board's incremental update subtracts old counts for the four lines crossing a changed cell, makes the move, then adds counts for the new versions of those lines. Undo performs the inverse around clearing the cell. The invariant is that accumulated per-player counts equal a fresh sum of classifications for the board, assuming the untouched lines are unchanged and the four affected lines are correctly identified. Each changed cell lies on exactly one line of each axis, so only those lines need recomputation. This is a proof sketch for the update scheme, not a proof that the classifier expresses every strategically meaningful formation.
The legacy evaluatePosition scans board lines and sums the category weights from the requested perspective. Other routines consult the incrementally maintained counts. With fixed-time pattern-table lookup per segment, a full scan over four axes takes O(N²) time; recomputing the four affected lines takes O(N) per player. The table is initialized for lengths up to 15, so this implementation requires that limit to be reviewed before using a larger board. Its cached counts remain consistent only when every move and undo follows the update procedure [20], [53].

2.16 Synthesis and limits of the algorithmic claims
The algorithms in this chapter have different responsibilities. Win detection decides the stated terminal rule; board mutation maintains a position; random and rule-based choices provide baselines; the evaluator assigns an approximate horizon value; candidate generation restricts the moves explored; ordering permutes the retained moves; minimax evaluates the resulting tree; alpha-beta skips provably irrelevant branches of that same tree; iterative deepening manages progressive search; and hashing plus a transposition table aim to reuse compatible earlier work. Quiescence extends a selected class of tactical moves at a horizon, but its own assumptions and depth limit remain.
The current decision path uses frontend tactical checks and a Worker-hosted WASM request. The modified Rust source explains board updates, Freestyle detection, candidate generation, horizon evaluation and fixed-depth alpha-beta. The legacy bot supplies the iterative-deepening, hashing, transposition-table and quiescence examples. Their contracts are examined independently: candidate selection defines the searched tree; ordering changes its traversal; and alpha-beta preserves minimax's root value for that same tree under the stated assumptions.
Chapter 5 evaluates the recorded implementations using native search experiments, WASM parity checks and browser Worker observations. Each result is interpreted with its own position, configuration, platform and counter definition. The theoretical arguments in this chapter establish properties of specified algorithms; the experiments assess those properties on the recorded finite fixtures [8], [43], [45], [46].
