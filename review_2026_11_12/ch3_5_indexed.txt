[78005 body] 3.1 Actors, use cases and functional requirements
[78055 body] The primary actor is a person using the web application. The person can play against another person on the same board or select a computer opponent. [84560 body] 3.2 Non-functional requirements and acceptance boundaries
[84618 body] Correctness means preserving legal state transitions, the agreed rule and the relation between board cells and history. Maintainability means keeping rule evaluation, rendering, input conversion and asynchronous search behind identifiable interfaces. Responsiveness motivates the Worker boundary for substantial search, while correct cancellation requires more than moving work off the main thread. Reproducibility requires a source revision, binary identity, configuration and measurement procedure rather than a screenshot containing a duration.
[85166 body] Executing the Rust/WebAssembly search inside a dedicated Web Worker isolates multi-ply tree expansion from the main browser thread, preserving responsive PixiJS canvas rendering and deterministic request cancellation across all six difficulty tiers.
[85416 body] 3.3 Architecture and ownership
[85447 body] The system has five principal responsibilities. React owns interface composition and subscribes to a controller snapshot. GameController owns the game-facing action boundary, current-player choice, AI-turn lifecycle and notification. The core owns board cells, legal-move history and rule evaluation. Pixi owns the visual board and converts gestures through an input/coordinate layer. The AI adapter owns search dispatch and Worker resources; it proposes a move but does not directly mutate the authoritative application board. [22] [2] [24] [14]

[86101 body] This ownership arrangement gives a clear dependency direction. The scene reports a cell action to the application/controller. The controller changes domain state and publishes a snapshot. The scene receives a list of stones, last move and winning cells for rendering. A visual object is not a second authoritative board. The AI path receives copied history and returns a result through the controller, which repeats the relevant validity checks before committing it.
[86568 body] A snapshot contains the match record, current player, thinking and pause flags, board stones, history, last move, last AI result and error. The controller copies move records and their cell coordinates when creating it. Subscribers read a stable cached snapshot until a notification creates a new one. This matters for React subscriptions: returning a newly constructed object on every read could produce unnecessary updates or unstable identity, whereas mutating a previously delivered object could conceal a change. The observed implementation uses an explicit cached value and listener set. [2]
[87166 body] Web Workers provide a standard way to execute scripts independently from interface scripts, but that standard does not automatically establish this project's lifecycle safety. Here the Worker wrapper is responsible for transport and pending promises, while the game controller is responsible for deciding whether a result remains valid for the current round. These are complementary responsibilities. Terminating a worker can stop obsolete work; checking the current token prevents an already-resolved obsolete response from being committed. [25] [26]
[87718 body] 3.4 Board state, history and legal transition contract
[87773 body] The frontend GameState stores one value per cell and an ordered move history. A move records its player, cell and index; history is also the input used to reconstruct a fresh Rust game for a search. These two uses require consistency. If a board cell changed without a corresponding history update, the display could show one position while the engine searched another. The transition contract therefore relates the occupied-cell set to the history sequence rather than treating them as independent data. [14]
[88283 body] The board has N = 15 and N² = 225 cells. A frontend cell is (row, col); Rust entry points use (x,y) with x = col and y = row. The row-major linear index is row × N + col. The normal pointer route applies floor, producing integer cell coordinates, and checks that they lie in 0 through 14. The WASM result adapter separately validates both integer-ness and bounds before mapping a result to a frontend cell. The core isBoardCell function itself checks numeric bounds but does not test Number.isInteger; direct fractional inputs therefore require an additional guard. A public API should not rely exclusively on the renderer to supply integers, because tests or other callers can enter through other routes. [27]
[88994 body] The playMove behaviour rejects an occupied cell before mutation, records the accepted move and evaluates the supplied rule. The higher controller supplies the current player and enforces pause, phase and AI-turn guards. This division is significant: a low-level board operation may not know which UI phase is active, while the controller should not duplicate the geometric win scan. The report therefore describes the legal move as a composed contract rather than attributing every guard to one function. [28] [2]
[89508 body] The history sequence is not merely a move counter. It preserves alternation and the exact order needed for hydration. A full board without a winner is declared a draw after the win test. That order matters on the last empty cell: a winning final placement must remain a win rather than being classified as a draw merely because the board is now full. The controller's finishMove uses this ordering. [2]
[89911 body] 3.5 Match phases and state transitions
[89950 body] MatchController defines setup, ready, playing and game-over. Its initial state is ready, local two-player mode, normal difficulty and round identifier zero. Calling playCell from setup or ready invokes startRound, which increments the round identifier, clears the old outcome and enters playing. An accepted win or full-board draw changes the match to game-over. The thinking flag belongs to the AI request lifecycle; it is not a fifth value in the phase enumeration. [23] [2]
[90427 body] 
[90429 body] Figure 3.2. Match phases and the separate AI waiting flag
[90487 body] Source: CaroGame/src/game/behaviors/match/MatchController.ts [23].
[90554 body] New game increments the round identifier and enters setup. Selecting a mode or difficulty first clears old game work and then places the match in ready. Replay may enter playing directly when the previous phase is playing or game-over. Undo calls resumeAfterUndo, increases the round identifier and chooses playing if stones remain, otherwise ready. These distinctions explain why a state diagram must name actual events instead of using a single unspecified Reset arrow.
[91026 body] Pause is orthogonal to the match phase. A paused playing round remains a playing round whose input and current AI work are suspended or invalidated. On resume, the controller checks whether it is still an AI match, still playing and still O's turn before requesting again. If pause were represented as a new board with an implicit player reset, the resumed game could diverge from its history. The source keeps the board and phase while handling the lifecycle separately. [2]
[91502 body] A state-machine invariant can now be stated. A result may commit only when its request belongs to the active AI turn and round, the application is unpaused, the phase is playing, the mode is AI and O is the current player. None of these predicates is replaced by the fact that a promise resolved successfully. Success describes the completed computation; the predicates describe whether that computation is still applicable.
[91927 body] 3.6 Asynchronous request protocol and cancellation
[91978 body] An AI action captures a new turn token, the round identifier and difficulty before setting thinking state. The request contains a copied move history. The transport wrapper adds its own message identifier so the correct pending promise receives the corresponding Worker response. The returned domain result carries its request/round identity, difficulty, move and statistics. The message identifier, AI request identifier and round identifier serve related but different scopes; they should not be collapsed into a single undocumented counter. [2] [3] [26]
[92535 body] On completion, the controller compares the captured token with its current token, checks pause and the returned round identifier, and repeats the phase, mode and current-player conditions. Only then does it clear thinking state, save feedback and pass the proposed O move through the same domain move behaviour used elsewhere. A rejected returned move produces an error instead of being painted directly. A missing move in an active round is also an error. This keeps the authoritative board inside the domain path. [2]
[93055 body] A concrete race illustrates the mechanism. Suppose request A is searching round 8. The person invokes a New game before A finishes. The controller increments its token, clears state and changes the round. Even if A's response was already queued, its captured token no longer matches. The promise resolution cannot insert A's move into the new board. Meanwhile, cancelPending rejects pending transport promises and terminates the old Worker, so future requests construct a new one. The token guard and resource cancellation address different parts of the race. [2] [26]
[93624 body] The rejection path is also scoped. A caught error changes feedback only when the captured token still equals the current token. Thus cancellation of an old request should not overwrite the error display of a newer turn. The Worker wrapper ignores messages from a worker object that is no longer its current worker, and ignores message identifiers absent from its pending map. These guards are source mechanisms; whether all possible races are covered remains a test question.
[94100 body] 3.7 Coordinate transformation and gesture interpretation
[94157 body] The scene works with a camera translation (cx,cy), a positive zoom z and cell size S = 56. For a screen position expressed in the scene's coordinate system, the inverse transform is worldX = (screenX − cx)/z and worldY = (screenY − cy)/z; the selected column and row are floor(worldX/S) and floor(worldY/S). Conversion back to a cell's world origin multiplies its column and row by S. A centre point for drawing a stone is obtained by adding half a cell in the renderer, rather than changing the indexing contract. [29]
[94677 body] 
[94679 body] Figure 3.3. Inverse camera transform before board bounds checking
[94745 body] Source: CaroGame/src/board/spatial/CoordinateTransform.ts [29].
[94809 body] The floor operation is important near boundaries. A negative world coordinate must remain out of bounds; rounding it toward a nearby valid cell could turn a margin tap into a move. For example, with camera x = 20, zoom = 0.5 and screen x = 19, the world x is −2 and the column is −1. The subsequent bounds check rejects it. With screen x = 230, world x is 420 and the column is 7. The same calculation on y yields the row. The report uses scene screen coordinates; client-page coordinates must first be converted by the event/rendering system that supplies them.
[95372 body] The input controller has idle, pressed and dragging states and a configured drag threshold of six screen units. A press stores the last pointer. Each move computes displacement from the last stored pointer; a sufficiently large displacement while pressed changes the state to dragging, and dragging produces a pan delta. On release, a valid cell tap is emitted only if the gesture remains pressed. The last-pointer update means the implemented threshold is checked against the last event displacement, not a guaranteed accumulated distance from the initial press. This detail is preserved here so the explanation does not promise a different gesture recognizer from the source. [30]
[96055 body] The scene treats pointer-up outside through the same handler and suppresses event processing while paused. It fits the board to the viewport using the minimum of available width and height ratios, with different padding for a narrow viewport. The camera's translation and scale are then applied to the world container. This separation lets the same rule and history logic work under different viewport sizes, although a desktop viewport simulation does not establish physical-touch behaviour. [24]
[96553 body] 3.8 Search-result contract and presentation of telemetry
[96610 body] The Rust result validator expects integer x/y coordinates in bounds, a finite score, the requested difficulty, one of the known strategy names and nonnegative safe-integer counters. Those counters include visited nodes, leaf evaluations, cutoffs, ordering evaluations, generated candidates and completed depth. An older binary returning only a coordinate pair fails this contract. This is preferable to silently displaying a nominal depth beside a result whose engine work was never instrumented. [27] [9]
[97116 body] The adapter maps the fields into application terminology and explicitly labels the source as Rust. Its elapsed timer starts before construction and history hydration, includes ai_move and free, and ends after cleanup. It excludes module loading and message delivery. A displayed duration therefore has a defined scope: it is not a complete user-perceived round trip and is not a measurement of only the recursive search. The tactical route instead labels its source as tactical, reports zero Rust search counters and a null score. Zero counters on that route mean Rust search was bypassed, not that a nontrivial Rust tree required no work. [3] [27]
[97765 body] Completed depth is the depth reported for the finished computation. A configuration table is a requested policy, while completed depth is output telemetry. Neither alone proves that a higher depth is supported or that every node at that depth was examined under a full-legal move set. Candidate pruning, terminal leaves and the chosen strategy all affect the actual search. The interface should preserve these distinctions when showing details to a player or evaluator.

[100118 body] The application package declares React 19, React DOM, Pixi 7.4, TypeScript, Vite, Vitest, i18next and related integration packages. [100497 body] The source folders reflect the design boundaries. app contains the game controller. game/core supplies state, bounds, coordinates and rules. game/behaviors implements move and match transitions. game/ai defines the service and tactical route, while game/wasm provides the worker, adapter, typed contract and generated engine package. board/input, board/spatial and board/render separate gestures, transforms and drawing. pixi integrates them into a scene; React components provide controls and feedback around the canvas. [1]
[101023 body] Within CaroGame/src, the modular separation between domain logic (game/core, game/behaviors), asynchronous AI dispatch (game/ai, game/wasm), and hardware-accelerated rendering (board/*, pixi/CaroScene.ts) keeps the core rules decoupled from the presentation layer. [31] [24] [32]
[101303 body] 4.2 Accepted move processing
[101332 body] At the action boundary, GameController.playCell first rejects a paused state. It starts a round when appropriate, rejects an ended match and prevents a human action while AI is thinking or while O owns the turn in AI mode. The controller then calls playMove with the current player and proposed cell. A nonaccepted result returns immediately without modifying board or history. However, from setup or ready, startRound runs before cell validation: a rejected direct call can advance the internal phase and round identifier without a notification. Normal pointer input filters out-of-bounds cells before this call; stronger atomic rejection at the controller boundary remains a verification and improvement item. For an accepted result, it processes a win or draw, otherwise alternates the player, notifies subscribers and starts AI only when the match is still playing in AI mode with O to move. [2] [28]
[102237 body] The sequence is deliberate. Notification occurs after the accepted domain change, so the interface receives a coherent snapshot. The AI request is based on the updated history, not on a speculative screen state. Rule evaluation occurs through the supplied FreestyleGomokuWinRule. The scene never paints a permanent stone merely because a pointer event arrived; it renders the state returned through the controller. This permits the same move contract to reject an occupied cell consistently in the UI and in tests.
[102752 body] Undo is implemented by history reversal. In local two-player mode it removes one ply. In AI mode, if the last recorded player is O, it removes two plies; otherwise it removes one. Before reversal it invalidates AI work and clears search feedback. It then determines the current player from the remaining last move, asks the match controller to resume after Undo and notifies. Popping two plies when the AI has already replied returns the board directly to the human player's decision turn while preserving chronological history integrity. [2]
[103295 body] 4.3 AI dispatch, Worker execution and WASM hydration
[103348 body] AIController.requestMove assigns a request identifier and inspects the difficulty. Easy and Normal bypass the TypeScript tactical shortcut so they actually execute the Rust Random and Rule-based policies. Higher tiers ask the tactical resolver for an immediate forced action for O. If one exists, the controller resolves a typed result with tactical source, null score and explicitly zero Rust counters. Otherwise it copies the entire accepted history and delegates to the WASM engine wrapper. This distinction is visible in the result contract and should remain visible in experimental interpretation. [3] [10]

[103962 body] Figure 4.1. Tactical and Rust routes converge at the guarded commit

[104080 body] The wrapper creates a module Worker lazily, registers a pending promise under a transport identifier and posts a search message. worker.ts loads the generated engine module and invokes the shared executeWasmSearch function. Sharing this adapter with non-Worker tests reduces the chance that a test exercises a different coordinate or telemetry mapping from the browser route; it does not replace a real-Worker test. When a result message returns, the wrapper resolves the matching pending entry. A structured Worker error rejects it. [33] [27]
[104624 body] Hydration creates a fresh Rust Game object and replays each history move as (col,row). Each replay call must succeed. If any move cannot be applied, the adapter throws an error identifying the move rather than searching a partially reconstructed board. After hydration, it calls ai_move with the mapped difficulty identifier, validates the returned object and maps (x,y) back to (row,col). A finally block frees the game even if hydration, search or result validation fails. This is an explicit resource lifecycle, not an assumption that JavaScript garbage collection releases every Rust allocation promptly. [27]
[105238 body] The generated package includes JavaScript glue, TypeScript declarations and the .wasm binary. The Rust implementation is therefore a real part of the application route. The JavaScript file is a binding layer rather than a readable replacement for all Rust search code. The archived Rust source and source excerpts explain the relevant algorithms, while the binary hash and adapter records connect the tested package to the recorded experiments. A complete rebuild claim additionally needs the exact modified Rust source and build inputs. [34] [7] [6]
[105789 body] 4.4 Board rendering and interface synchronization
[105839 body] CaroScene creates a transparent, antialiased Pixi application associated with the supplied canvas. It builds a world container with separate grid, highlight/effect and stone layers. The scene stores the latest render stones, last move and winning-cell set supplied by syncState; these are rendering inputs derived from the controller, not independent move authority. The camera subscription reapplies translation/scale and refreshes the visible board. A ticker callback checks whether the viewport dimensions have changed and refits when necessary. [24]
[106393 body] The separation of layers explains the update path. A grid renderer draws board geometry. A stone renderer maps player/cell records to visual pieces. A highlight renderer displays the last move and winning cells. Input goes through the gesture controller and coordinate transform before onCellClick reports row and column. This organization permits tests to reason about bounds and camera math without requiring every rule test to instantiate Pixi graphics. Conversely, a core test cannot demonstrate that a visual stone is correctly positioned in a real browser.
[106956 body] The React application subscribes to controller state and synchronizes the scene when relevant snapshot fields change. It wires user controls to controller actions, supplies selection values and renders feedback/error states. It also coordinates hosting lifecycle inputs where configured. This layer is responsible for component effects and teardown; the scene's destroy path releases camera subscription, listeners, render layers and the Pixi application. The AI service's destroy method separately terminates its Worker resources. Explicit ownership avoids making a canvas object responsible for unrelated background computation. [22] [24] [26]
[107602 body] The interface includes translation resources for its supported labels and search details. Those resources map keys to displayed text; they do not change difficulty semantics or engine telemetry. An elapsed label, a completed-depth label and a strategy/source label should all refer to the current AI result. Undo, reset or a mode change clears stale feedback in the controller, ensuring that an old score is not displayed as though it belonged to the new board. [35] [2]

[109759 body] 4.6 Python/Pyodide execution and four instructional programs
[109820 body] The presentation's Python runner loads or reuses a Pyodide instance. It captures stdout and stderr, loads packages inferred from imports when supported and executes code through runPythonAsync. The returned string is displayed to the reader, while caught errors become visible output. Pyodide executes Python in a browser environment based on WebAssembly; its presence does not mean the game AI is implemented in Python. The game engine's Rust/WASM path and the teaching runner are separate consumers of web execution technology. [37] [38] [39]
[110365 body] The runner caches an instance and queues callbacks for simultaneous loading. These mechanisms explain how its intended reuse works. They do not establish robust recovery from every loading failure: the code paths and pending callbacks require their own review and tests. In particular, an educational execution panel should report loading/execution failure clearly and should not transform a failure into a fabricated successful numerical result. The report describes the observed implementation without silently claiming a more complete runtime manager.
[110920 body] 4.6.1 Pattern scanner
[110942 body] The first program constructs a 15 × 15 NumPy board with four X stones horizontally and three O stones vertically. Its detection function inspects contiguous horizontal runs and classifies five, open four, closed four, open three and closed three according to endpoint availability. Therefore, the printed horizontal open-four result is meaningful for that example, while the mere presence of a vertical O line does not demonstrate that this function scans it. The code does not implement the full four-axis production win scan or a complete seven-pattern taxonomy. [38]
[111512 body] The input contract is a small integer matrix and a selected player. Its output is a dictionary of counts. A run should be counted once by identifying its beginning, extending to its end and checking endpoints without leaving the matrix. The example illustrates how an algorithm can transform board data into features; it does not prove that every printed instructional label accurately describes its scope. Broken threats such as XX.XX require additional pattern logic beyond counting contiguous occupied runs.

[112050 body] The second program calculates a score from manually supplied pattern counts and a demonstration weight dictionary. The instructional attack/defence cases yield 94,000 and −7,000 under those inputs and its defensive factor. These are arithmetic outcomes of the supplied feature counts, not results obtained by asking the production Rust evaluator to scan a live board. A negative value means the particular weighted formula favours the opponent under that convention; it does not independently establish a forced loss. Terminal utility and tactical completion checks remain separate mechanisms, as specified in Chapter 2.

[115106 body] The implementation can be traced from a controller action through domain state and into display, or from a search request through copied history, a Worker, a Rust/WASM object and a validated response. [129327 body] 5.4.2 Candidate caps, ordering and tactical completeness
[129384 body] Candidate generation reduces the set of considered moves by selecting empty cells near existing stones. This can reduce branching but changes the search problem. The reference cap_loss.json supplies a concrete risk: in the synthetic win fixture at radius one, 20 uncapped candidates include two immediate winning endpoints (7,2) and (7,7), but a cap of six omits both. At depth one, the uncapped score is 9,999,999 and the capped score is 99,990. This is not an Alpha-Beta error: it is a difference in which moves are admitted before the search. It demonstrates why an ordering or cap policy must be evaluated against tactical membership, and why a value equality proof applies only after the move set is fixed. [16]
[130101 body] The later 23 October engine record reports twelve tactical-completion retention checks for its own candidate policy. These results concern another implementation and cannot erase the reference counterexample. Conversely, a failure of that reference cap does not establish that the later engine's soft cap fails. A useful future experiment would separate candidate generation, tactical retention, ranking and pruning in an ablation, using the same positions and reporting both selected move quality and total work.

[135729 body] 5.7 Threats to validity and interpretation
[135772 body] Internal validity. Search comparisons require the same position, depth, terminal rules, evaluation perspective and candidate set. Otherwise an apparent improvement can arise from searching a different tree. A table that ignores rule or perspective context can return a stale value. An aborted iteration must be counted separately from completed work. These issues are directly motivated by the cap-loss, cache-scope and budget probes.
[136207 body] Measurement validity. The native experiments distinguish recursive nodes, leaf evaluations, ranking evaluations, cutoffs and time. Treating one counter as a substitute for all computation can reverse the apparent conclusion, as the clustered ordered example shows. Three sequential timing repeats and lack of randomized order, CPU isolation or uncertainty intervals support descriptive comparisons only. Native timer scope, Worker hydration and search, and browser round-trip duration are different quantities.
[136718 body] External validity. The fixtures cover controlled and seeded boards but not the full space of legal games. Tactical test positions may be synthetic. A 100-game Rule-Based versus Random result is narrow, and it does not calibrate six difficulty levels against human skill. Node execution and headless-browser synthetic input do not establish physical touchscreen, Wink host, deployment or production behaviour.
[137127 body] Reproducibility and provenance. The public repository includes raw records, harnesses, source excerpts and cryptographic hashes. Appendix B summarizes the verification artifacts and scope across each subsystem. A reproducible follow-up should archive exact source, build configuration, dependencies, tool versions, random seed, raw runs and a measurement protocol together under one immutable revision.
