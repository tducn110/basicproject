[295..1625] body NORMAL_TEXT This project develops a web application for Caro on a 15 × 15 board under Freestyle rules and uses the game to study adversarial search. The application combines a React interface, a PixiJS board and a Rust engine compiled to WebAssembly, with search executed in a Web Worker. The report explains board representation, legal moves, win detection, heuristic evaluation, candidate selection, Minimax and Alpha-Beta pruning. It also examines hashing, transposition tables, quiescence and iterative deepening in separate reference and legacy implementations. The recorded native engine experiment contains 816 search measurements, including 408 paired Minimax and Alpha-Beta comparisons and 820 state-restoration checks. Separate records examine agreement between the JavaScript adapter and the WebAssembly binary, browser Worker responses and selected interface interactions. The reference experiments show that fewer visited nodes can coincide with longer execution time when move ranking adds work. They also identify immediate tactics lost by a hard candidate cap and an incorrect score caused by reusing cached entries after the root player changes. These results connect search algorithms to an interactive application and show why candidate policy, state restoration and cache context must be specified alongside search depth.

[11820..12426] body NORMAL_TEXT Caro is a two-player placement game in which a small set of rules produces a large adversarial decision space. A player places one stone on an empty cell, attempts to complete a winning line and must anticipate the opponent's reply. The board representation is simple enough to implement explicitly, while the number of possible move sequences makes exhaustive search impractical beyond shallow depths. This combination makes the project suitable for studying data structures, recursive search, evaluation functions, pruning and the relationship between algorithmic results and an interactive application.
[12426..13035] body NORMAL_TEXT The project includes a playable web application and a separate website for explaining its algorithms. React provides the interface, PixiJS renders the board, and GameController coordinates accepted moves, match state and AI requests. Move selection combines a TypeScript tactical check with a Rust/WebAssembly search executed in a Worker. The repository also contains an earlier TypeScript search module, native benchmark programs and weekly project reports. The application, benchmarks and teaching examples share the game domain but execute through different entry points [1], [2], [3], [4], [5], [6], [7].
[13035..13497] body NORMAL_TEXT The practical problem is to select a legal move while preserving the state of an interactive match. Search must leave its input board unchanged, follow the selected win rule and return a result that belongs to the active round. Reset, Undo and asynchronous computation make these requirements part of the algorithm integration. The report therefore studies move quality together with the controller checks that determine whether an AI response can be committed.
[13497..13535] body HEADING_2 1.2 Objectives and research questions
[13535..14004] body NORMAL_TEXT The first objective is to define the game rules and state transitions. The second objective is to describe move selection through its inputs, evaluation policy, candidate set, recursive decisions, state restoration and computational cost [8].
[14004..14492] body NORMAL_TEXT The third objective is to explain how the algorithms connect to the application: board ownership, guarded move commitment, history replay into WebAssembly and rejection of stale responses. The fourth objective is to evaluate search under controlled conditions. The experiments compare Minimax with Alpha-Beta on the same candidate tree, separate move-ranking work from recursive search visits, and examine whether selective candidate policies retain immediate winning and blocking moves.
[14492..15012] body NORMAL_TEXT Four research questions guide the report. RQ1 concerns deterministic board updates and Freestyle win detection. RQ2 concerns how heuristic evaluation, candidate selection and adversarial recursion produce a move. RQ3 examines the effects of pruning, ordering and caching on search results and computational work. RQ4 concerns state consistency when native search components are used through an asynchronous browser interface. Chapter 5 relates each question to the corresponding implementation and experimental records.

[19896..19948] body HEADING_3 2.2.1 Matrix, index conversion, and state ownership
[19948..20793] body NORMAL_TEXT A position contains 225 cells, each empty, X or O. For a logical matrix B[y][x], row-major conversion is i = 15y + x, with inverse x = i mod 15 and y = floor(i/15). The center (7,7) therefore has index 112, and (14,14) has index 224. In the modified Rust source, Board stores a 15 × 15 array of repr(u8) cells and a move counter. Its cell values are Empty = 0, Black = 1 and White = 2; the array occupies 225 bytes, while the complete Board also contains the counter and any alignment padding [10], [17]. The frontend GameState instead stores occupied coordinates in a Map and maintains ordered move history [18]. The legacy BotBoard uses a one-dimensional array padded with boundary sentinels. These representations support different operations: direct Rust cell access, frontend match history, and incremental line analysis in the legacy bot.
[20793..21251] body NORMAL_TEXT In the modified Rust snapshot, Board::place checks bounds, rejects an empty stone or occupied cell, writes the stone and increments move_count. Board::undo rejects an invalid or empty coordinate, then clears the occupied cell and decrements the counter [10]. These operations maintain the position. Turn alternation, move history and terminal lockout belong to the Rust Game wrapper and the frontend match controller, rather than to Board::place itself [2].
[21251..21749] body NORMAL_TEXT Board mutation and match progression have separate owners. Board holds the cells and move count; Game and the frontend controller maintain turn, result and history. Search explores hypothetical moves on a working board, while the match commits only the selected move. The modified Rust search clones the root board once and applies and undoes moves within that copy [10]. This avoids a complete board copy for each child, although candidate generation still allocates move lists at internal nodes.

[23475..24083] body NORMAL_TEXT Invariant and argument. Immediately before exploring each sibling, the working state must equal the state at the parent node. A successful apply changes exactly the selected empty cell and increments the count. Its matching undo clears that same cell and decrements the count; therefore these fields equal their former values. By induction over nested calls, assuming each recursive child restores every state field it owns, the parent sees the same state for the next sibling. The induction depends on legal matching calls; it is not guaranteed if an exception bypasses undo or a different move is removed.
[24083..24663] body NORMAL_TEXT For example, let X occupy (7,7), O occupy (8,7), and move_count be two. With direct indexing, each cell/count update takes O(1) time and O(1) auxiliary space; copying an N × N board takes O(N²). The archived native experiment records 820 successful working-board restoration checks, including repeated search configurations. This is the finite test result used in Chapter 5 [19].

[24790..24818] body HEADING_2 2.3 Freestyle win detection
[24818..25263] body NORMAL_TEXT The frontend win rule treats a contiguous line of at least five stones as a win, including an overline of six or more. It checks four axes through the last move, with both directions on each axis. It does not require exactly five or impose an additional two-blocked-ends condition [8]. The term Caro is used for the application, but this particular rule is specified explicitly because games with similar names may use other winning conditions.
[25263..25690] body NORMAL_TEXT The procedure receives a valid board and the last placed coordinate m. It returns the winning player and collected winning cells, or no result. It assumes the preceding position was unfinished, so any newly created winning line passes through m. An arbitrary imported position instead requires a full-board result check at the search root. Under the frontend state contract, an empty last-move coordinate yields no winner [8].

[122949..122992] body HEADING_2 5.7 Threats to validity and interpretation
[122992..123427] body NORMAL_TEXT Internal validity. Search comparisons require the same position, depth, terminal rules, evaluation perspective and candidate set. Otherwise an apparent improvement can arise from searching a different tree. A table that ignores rule or perspective context can return a stale value. An aborted iteration must be counted separately from completed work. These issues are directly motivated by the cap-loss, cache-scope and budget probes.
[123427..123938] body NORMAL_TEXT Measurement validity. The native experiments distinguish recursive nodes, leaf evaluations, ranking evaluations, cutoffs and time. Treating one counter as a substitute for all computation can reverse the apparent conclusion, as the clustered ordered example shows. Three sequential timing repeats and lack of randomized order, CPU isolation or uncertainty intervals support descriptive comparisons only. Native timer scope, Worker hydration and search, and browser round-trip duration are different quantities.
[123938..124346] body NORMAL_TEXT External validity. The fixtures cover controlled and seeded boards but not the full space of legal games. Tactical test positions may be synthetic. A 100-game Rule-Based versus Random result is narrow, and it does not calibrate six difficulty levels against human skill. Node execution and headless-browser synthetic input do not establish physical touchscreen, Wink host, deployment or production behavior.
[124346..124864] body NORMAL_TEXT Reproducibility and provenance. The repository supplies raw measurements, harnesses, source excerpts and binary hashes. The 12 November follow-up matched 36 available engine, reference, harness and lock files to their archived hashes and reproduced the non-timing search results. The native source trees available in the local workspace are not all tracked in the examined application repository. Chapter 6 addresses publication of a complete source-and-build package; Appendix B records the present artifact mapping.

[124902..124938] body HEADING_2 6.1 Work completed and contribution
[124938..125399] body NORMAL_TEXT The project implements a Caro web application and a teaching website for board representation, Freestyle rules, heuristic evaluation and adversarial search. The application connects a React interface and PixiJS board to a Rust/WebAssembly search Worker. The teaching website provides visual explanations and executable Python examples. Weekly reports and native research artifacts document the algorithmic development and its experimental evaluation [1], [53].
[125399..126059] body NORMAL_TEXT The main contribution is an implementation-level account of how game decisions depend on representation and search policy. Board updates, history and rollback support recursive exploration. Terminal utility takes precedence over the static heuristic. Minimax defines alternating decisions, and Alpha-Beta pruning preserves the value of the same selected search tree while omitting branches that cannot change it. Candidate filtering changes the tree itself; ordering changes the sequence in which its moves are examined. The reference experiments extend this analysis to Zobrist hashing, transposition-table bounds and interrupted iterative search [11], [13].
[126059..126752] body NORMAL_TEXT The recorded native engine experiment reports 408 Minimax/Alpha-Beta comparisons with matching values and 820 successful restoration checks. Separate adapter and browser records exercise the connection between search and the application. In the reference experiments, move ordering reduced visited nodes on some positions, but its additional evaluation work could outweigh the saving in elapsed time. A hard candidate cap discarded immediate wins in one fixture, and cache reuse after a root-player change produced an incorrect score in another. These results show that search depth and node count alone are insufficient to assess correctness or efficiency [19], [31], [32], [49], [22], [27].
[126752..126768] body HEADING_2 6.2 Limitations
[126768..127340] body NORMAL_TEXT The active search is selective. Its soft tactical cap retains immediate winning and blocking completions, but deeper positional moves remain subject to the candidate limit. The configured limit falls from 15 at Hard to 8 at Master as depth rises from two to five plies. The static evaluator scores contiguous runs; gapped formations and intersecting threats depend on tactical assessment and deeper search. Persistent transposition tables and iterative-deepening budgets are studied in separate implementations rather than used by the active Rust search [10], [29], [13].
[127340..127932] body NORMAL_TEXT The implementation review also identifies boundary cases for further correction. GameController starts a round before validating the first direct move request, and the core coordinate predicate checks bounds without requiring integer indices. The normal pointer path supplies integer cells, while Worker responses have a separate integer check. Drag detection compares consecutive pointer positions, which can miss a slow drag made of small steps. In the teaching website, a failed or missing Pyodide loader can leave initialization state or waiting callers unresolved [2], [35], [37], [43].
[127932..128514] body NORMAL_TEXT The measurements cover a finite corpus and specific native or browser environments. The published snapshot includes the application and its binary, but the complete modified Rust engine and the caro-core-reference dependency are absent from that Git tree, limiting reproduction from a fresh clone. Historical timing and bot-match summaries also have narrower provenance than the controlled research records. Physical-device interaction, live host integration, human usability and calibrated playing strength remain subjects for further evaluation [1], [13], [46], [24], [11], [52].
[128514..128537] body HEADING_2 6.3 Future development
[128537..128921] body NORMAL_TEXT Reproducibility is the first development priority. A complete release should include the modified engine and reference library together with their manifests, lockfiles, experiment harnesses and build commands. Each experiment should identify the source revision, toolchain, platform and binary hash. The earlier baseline should remain available for comparison under its own identity.
[128921..129389] body NORMAL_TEXT Input validation and lifecycle handling should be strengthened at their owning boundaries. The core should require integer coordinates and validate a move before advancing the match phase. Gesture classification should use displacement from the initial press, and the Pyodide loader should settle all waiting requests and permit retry after failure. Regression cases should include invalid first moves, fractional inputs, slow drags and failed runtime initialization.
[129389..129843] body NORMAL_TEXT Further search evaluation should separate candidate selection from move ordering. A fixed corpus of reachable positions can compare all-legal search with radius and cap policies, including known wins, blocks and intersecting threats. Useful outputs include missed tactics, chosen moves, root values, ranking evaluations, recursive visits and elapsed time. Multiple seeds and explicit tie handling would make the comparison less dependent on one fixture.
[129843..130275] body NORMAL_TEXT Persistent caching requires a defined compatibility context. Future work should include rules, evaluation weights, root perspective and mate-distance treatment in the cache design, then test exact, lower and upper bounds across depths and search windows. Warm-table and cold-table comparisons should include root changes and collisions. Memory measurements should include map capacity and allocation overhead as well as entry size.
[130275..130640] body NORMAL_TEXT An anytime search could combine iterative deepening with cancellation and an explicit last-completed-result policy. Its telemetry should distinguish requested depth from completed depth and count work spent in aborted iterations. Tests should cover Reset, Undo, stale replies and Worker failure while confirming that interrupted search restores the input position.
[130640..131090] body NORMAL_TEXT Application evaluation should extend to physical target devices and the intended host environment. Repeated measurements of response latency and frame timing would complement the present automated checks. A participant study could examine control usability and perceived difficulty, while a multi-seed tournament against stated opponents could assess playing strength. Both require a documented protocol before their results can support conclusions.
[131090..131524] body NORMAL_TEXT The teaching website should remain synchronized with the implementations it explains. Illustrative programs need explicit scope, especially where a horizontal example accompanies a four-direction rule description. Charts should link to the data and generation procedure that produced them. This would let readers move from an explanation to the corresponding source or experiment without confusing a demonstration with a measurement.
