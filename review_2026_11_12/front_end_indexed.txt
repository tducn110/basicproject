[289..298] body NORMAL_TEXT ABSTRACT
[298..1072] body NORMAL_TEXT This project studies the design and implementation of a Caro web application together with a set of adversarial-search experiments and teaching materials. The report specifies a 15 × 15 Freestyle game, the board and move-history contracts, and the algorithms used to select and evaluate moves. It explains random and rule-based baselines, contiguous-run heuristics, tactical checks, Chebyshev candidate generation, soft candidate caps, Minimax and Alpha-Beta. It also treats iterative deepening, Zobrist hashing, transposition-table bounds, quiescence and incremental pattern counting in their corresponding reference or legacy implementations. Each algorithm is presented with its inputs, state, decision procedure, invariants, complexity, worked examples and limitations.
[1072..1598] body NORMAL_TEXT The application combines React interface components, a Pixi board, an authoritative controller and a Worker-based Rust/WebAssembly route. Request identity, round identity, cancellation, coordinate conversion and telemetry validation preserve the connection between a proposed AI move and the round in which it may be committed. The separate presentation website provides interactive explanations and Python/Pyodide examples. Its demonstrations are analysed individually rather than treated as measurements of the game engine.
[1598..2213] body NORMAL_TEXT Evaluation distinguishes published native experiments, binary/adapter parity, actual browser Worker observations, selected UI interactions and historical cross-language benchmarks. GitHub references identify immutable source and evidence snapshots. The analysis includes negative findings such as tactical moves discarded by a reference candidate cap, increased timing despite fewer searched nodes, and unsafe table reuse across a changed context. The resulting report connects algorithmic principles to concrete implementation while stating the boundaries of finite tests, source availability and reproducibility.
[2213..2323] body NORMAL_TEXT Keywords: Caro; Gomoku; Minimax; Alpha-Beta; candidate generation; Rust; WebAssembly; game-state consistency.

[7547..7577] body HEADING_2 1.1 Background and motivation
[7577..8183] body NORMAL_TEXT Caro is a two-player placement game in which a small set of rules produces a large adversarial decision space. A player places one stone on an empty cell, attempts to complete a winning line and must anticipate the opponent's reply. The board representation is simple enough to implement explicitly, while the number of possible move sequences makes exhaustive search impractical beyond shallow depths. This combination makes the project suitable for studying data structures, recursive search, evaluation functions, pruning and the relationship between algorithmic results and an interactive application.
[8183..8871] body NORMAL_TEXT The project develops both a playable web application and material for explaining its algorithms. In the application, React supplies the surrounding interface, Pixi renders the board and a controller coordinates accepted moves, match state and AI requests. The AI path combines a TypeScript tactical check with a Worker-based WebAssembly engine. The repository also preserves a TypeScript search implementation, native Rust benchmark programs, baseline Rust engine code, weekly research reports and a separate presentation website. These modules form a cohesive architecture spanning interactive gameplay, WebAssembly search execution, and reproducible algorithmic benchmarks. [1] [2] [3]
[8871..9431] body NORMAL_TEXT The practical problem is to return a legal and useful move while maintaining coherent application state. A search that produces a high score is insufficient if it changes the caller's board, uses an incompatible win rule, blocks interaction unnecessarily or commits a result after the user has reset the round. The report therefore considers both the mathematical search problem and the application boundary at which a result becomes a move. It also distinguishes an observed counter from a configured limit and a native experiment from a browser measurement.
[9431..9469] body HEADING_2 1.2 Objectives and research questions
[9469..10071] body NORMAL_TEXT The first objective is to specify the actual game rules and state transitions. A 15 × 15 board and a five-stone target do not uniquely define a Caro variant. The application's Freestyle rule accepts a contiguous line of at least five stones, including longer lines. Its implementation is explained from the last-move scan, with the assumptions under which that local test is valid. The second objective is to specify the AI algorithms precisely: their inputs, outputs, recurrence or decision policy, candidate membership, state mutation and restoration, stopping conditions and computational cost. [4]
[10071..10649] body NORMAL_TEXT The third objective is to connect those algorithms to the implementation. The report identifies which component owns the board, who may commit a move, how history is replayed into the Rust/WASM object and how stale responses are rejected. The fourth objective is to evaluate the published experiment records without turning limited measurements into universal claims. In particular, it asks whether Minimax and Alpha-Beta agree on the same selected tree, whether ordering reduces total work or only visited nodes, and whether a cap can discard an immediate tactical completion.
[10649..11318] body NORMAL_TEXT These objectives lead to four research questions. RQ1 asks how legal board state and the Freestyle win condition can be represented and checked deterministically. RQ2 asks how evaluation, candidate generation and adversarial recursion produce a move, and which assumptions preserve correctness. RQ3 asks how pruning, ordering and caching affect the measured search, including counterexamples and context hazards. RQ4 asks how the native and browser components preserve a consistent game when requests are asynchronous. The evaluation chapter answers each question using the corresponding source implementation, mathematical invariants, and empirical benchmark records.

[137568..137604] body HEADING_2 6.1 Work completed and contribution
[137604..138210] body NORMAL_TEXT The project combines a playable Caro application with an educational sequence on representation, rules, heuristic evaluation and adversarial search. The application repository provides the user interface and game-side code; the weekly material documents the development sequence from initial proposal to search and advanced techniques. The presentation project supplies visual and executable teaching examples. Separate research artifacts provide controlled search data and record experimental boundaries. These products have different purposes and should not be treated as one executable engine. [1] [52]
[138210..138984] body NORMAL_TEXT The technical contribution is the mapping from game decisions to data structures and algorithms. A board state supports legal placement, directional line checks, history and rollback. A heuristic gives a bounded estimate for nonterminal positions, while terminal outcomes take precedence. Minimax specifies alternating decisions; Alpha-Beta can discard branches that cannot alter the selected-tree value. Candidate generation restricts the search space, and ordering changes traversal order. The reference experiments further evaluate incremental Zobrist hashing, transposition-table bounds, and iterative-deepening budgets on controlled native benchmarks. The application and reference implementations must each be described through their own source and evidence. [44] [8]
[138984..139590] body NORMAL_TEXT The 23 October native record reports agreement and restoration on its finite corpus, and the separate Node and browser artifacts exercise selected integration paths. The reference data shows a substantial node reduction in one paired example and also shows that ordering can consume enough additional evaluation work to remove the elapsed-time benefit. The cap-loss and cross-root cache probes expose concrete correctness risks. These findings are more useful than a single headline speedup because they identify both the assumptions under which the method works and the conditions that require more care.
[139590..139606] body HEADING_2 6.2 Limitations
[139606..139875] body NORMAL_TEXT First, while the engine's soft tactical cap preserves all immediate 1-ply winning and blocking moves, tightening the non-tactical candidate cap at higher depths (from 15 at Hard to 8 at Master) trades broad positional exploration for deeper 5-ply tactical calculation.
[139875..140235] body NORMAL_TEXT Second, the active WebAssembly engine uses stateless fixed-depth Alpha-Beta search per turn without a persistent cross-turn transposition table or wall-clock iterative deepening, and empirical evaluation is currently scoped to controlled benchmark fixtures and automated bot-versus-bot matches rather than large-scale human tournament play. [41] [44] [8] [40]
[140235..140509] body NORMAL_TEXT Third, the static heuristic evaluator scans maximal contiguous runs and therefore relies on multi-ply search recursion and the tactical candidate assessor to recognize gapped formations (such as XX_XX) or multi-axis forks, motivating the future enhancements outlined below.
[140509..140532] body HEADING_2 6.3 Future development
[140532..140911] body NORMAL_TEXT 1. Publish a reproducible source bundle. Include the exact current Rust engine, reference library, manifests, lockfiles, harnesses, recorded hashes and build instructions under immutable revisions. Record any local modifications instead of presenting an earlier baseline as the measured source. Provide a script that compares binary hashes and states the platform and toolchain.
[140911..141283] body NORMAL_TEXT 2. Expand rule and tactical testing. Add board-edge and long-line cases, occupied and out-of-range inputs, full-board draws, simultaneous threats, undo after terminal states and independently checked randomized move sequences. Compare TypeScript and WebAssembly outcomes under an explicit terminal-turn convention. Each new rule variant needs its own contract and oracle.
[141283..141635] body NORMAL_TEXT 3. Measure candidates and order policies separately. Use a fixed corpus of reachable positions, include known immediate wins and blocks, compare all-legal and selective search, and report missed tactics, decision quality, ranking evaluations, nodes and elapsed time. Separate soft-cap tactical retention from a hard cap; record ties and ordering cost.
[141635..141970] body NORMAL_TEXT 4. Harden and test table reuse. Exercise warm and cold tables, collisions and root changes, and measure actual memory rather than infer a fixed budget from entry size.
[141970..142300] body NORMAL_TEXT 5. Improve interruption and telemetry. Define whether counters include aborted iterations and whether a depth means requested or completed depth. Test cancellation, reset, stale replies, Worker failure and restoration, with an explicit last-completed-result policy. Propagate real measured statistics consistently through the UI.
[142300..142703] body NORMAL_TEXT 6. Evaluate user-facing behaviour. Run repeatable browser tests with real input, more viewport sizes and target devices; test the actual host integration separately. Measure end-to-end latency and frame timing in the intended environment, with enough repetitions and disclosed methodology. A human usability or difficulty study requires participants, protocol and consent before results can be claimed.
[142703..143049] body NORMAL_TEXT 7. Synchronize the educational presentation. Mark illustrative code and figures, link measured charts to their source data and update outdated labels.
