ABSTRACT 
This project develops a web application for Caro on a 15 × 15 board under 
Freestyle rules and uses the game to study adversarial search. The application 
combines a React interface, a PixiJS board and a Rust engine compiled to 
WebAssembly, with search executed in a Web Worker. The report explains board 
representation, legal moves, win detection, heuristic evaluation, candidate selection, 
Minimax and Alpha-Beta pruning. It also examines hashing, transposition tables, 
quiescence 
and 
iterative 
deepening 
in 
separate 
reference 
and 
legacy 
implementations. The recorded native engine experiment contains 816 search 
measurements, including 408 paired Minimax and Alpha-Beta comparisons and 820 
state-restoration checks. Separate records examine agreement between the 
JavaScript adapter and the WebAssembly binary, browser Worker responses and 
selected interface interactions. The reference experiments show that fewer visited 
nodes can coincide with longer execution time when move ranking adds work. 
They also identify immediate tactics lost by a hard candidate cap and an incorrect 
score caused by reusing cached entries after the root player changes. These results 
connect search algorithms to an interactive application and show why candidate 
policy, state restoration and cache context must be specified alongside search depth. 
Keywords: Caro; adversarial search; Alpha-Beta pruning; selective search; 
WebAssembly.

CHAPTER 1. INTRODUCTION 
1.1 Background and motivation 
Caro is a two-player placement game in which a small set of rules produces a large 
adversarial decision space. A player places one stone on an empty cell, attempts to 
complete a winning line and must anticipate the opponent's reply. The board 
representation is simple enough to implement explicitly, while the number of 
possible move sequences makes exhaustive search impractical beyond shallow 
depths. This combination makes the project suitable for studying data structures, 
recursive search, evaluation functions, pruning and the relationship between 
algorithmic results and an interactive application. 
The project includes a playable web application and a separate website for 
explaining its algorithms. React provides the interface, PixiJS renders the board, 
and GameController coordinates accepted moves, match state and AI requests. 
Move selection combines a TypeScript tactical check with a Rust/WebAssembly 
search executed in a Worker. The repository also contains an earlier TypeScript 
search module, native benchmark programs and weekly project reports. The 
application, benchmarks and teaching examples share the game domain but execute 
through different entry points [1], [2], [3], [4], [5], [6], [7]. 
The practical problem is to select a legal move while preserving the state of an 
interactive match. Search must leave its input board unchanged, follow the selected 
win rule and return a result that belongs to the active round. Reset, Undo and 
asynchronous computation make these requirements part of the algorithm 
integration. The report therefore studies move quality together with the controller 
checks that determine whether an AI response can be committed. 
1.2 Objectives and research questions 
The first objective is to define the game rules and state transitions. The application 
uses a 15 × 15 board and the Freestyle win condition: a contiguous line of at least 
five stones wins, including longer lines. The report explains the last-move scan and 
the assumptions that make it sufficient. The second objective is to describe move 
selection through its inputs, evaluation policy, candidate set, recursive decisions, 
state restoration and computational cost [8]. 
The third objective is to explain how the algorithms connect to the application: 
board ownership, guarded move commitment, history replay into WebAssembly 
and rejection of stale responses. The fourth objective is to evaluate search under

2.2 Board representation and legal updates 
2.2.1 Matrix, index conversion, and state ownership 
A position contains 225 cells, each empty, X or O. For a logical matrix B[y][x], 
row-major conversion is i = 15y + x, with inverse x = i mod 15 and y = floor(i/15). 
The center (7,7) therefore has index 112, and (14,14) has index 224. In the modified 
Rust source, Board stores a 15 × 15 array of repr(u8) cells and a move counter. Its 
cell values are Empty = 0, Black = 1 and White = 2; the array occupies 225 bytes, 
while the complete Board also contains the counter and any alignment padding 
[10], [17]. The frontend GameState instead stores occupied coordinates in a Map 
and maintains ordered move history [18]. The legacy BotBoard uses a 
one-dimensional array padded with boundary sentinels. These representations 
support different operations: direct Rust cell access, frontend match history, and 
incremental line analysis in the legacy bot. 
In the modified Rust snapshot, Board::place checks bounds, rejects an empty stone 
or occupied cell, writes the stone and increments move_count. Board::undo rejects 
an invalid or empty coordinate, then clears the occupied cell and decrements the 
counter [10]. These operations maintain the position. Turn alternation, move history 
and terminal lockout belong to the Rust Game wrapper and the frontend match 
controller, rather than to Board::place itself [2]. 
Board mutation and match progression have separate owners. Board holds the cells 
and move count; Game and the frontend controller maintain turn, result and history. 
Search explores hypothetical moves on a working board, while the match commits 
only the selected move. The modified Rust search clones the root board once and 
applies and undoes moves within that copy [10]. This avoids a complete board copy 
for each child, although candidate generation still allocates move lists at internal 
nodes.

2.2.2 Apply and undo 
Inputs and output. APPLY(B,m,p) takes the working board, a coordinate and a 
nonempty player; it returns success or failure. UNDO(B,m) takes the coordinate of 
a previously applied move and returns whether removal was possible. The stronger 
search precondition is that undo is paired with the most recent successful 
hypothetical move on that branch. An individual undo that merely removes an 
occupied cell does not enforce the whole history discipline.

// Algorithm 2.1 (modified Rust source in [6]) — APPLY(B, (x,y), p): 
    if x or y is outside the board, or p is empty: return failure 
    if B[y][x] is not empty: return failure 
    B[y][x] ← p 
    B.move_count ← B.move_count + 1 
    return success 
 
UNDO(B, (x,y)): 
    if (x,y) is outside the board or B[y][x] is empty: return failure 
    B[y][x] ← empty 
    B.move_count ← B.move_count - 1 
    return success 
 
VISIT_CHILD(B, p, m): 
    require APPLY(B, m, p) succeeds 
    try: value ← VISIT(B, opp(p), m) 
    finally: require UNDO(B, m) succeeds 
    return value 
The try/finally structure in this explanatory pseudocode requires restoration after a 
return, cutoff or supported abort. An implementation must provide equivalent 
cleanup for every exit it supports. A matching apply/undo restores the cell and 
count in O(1) time; hashes, cached patterns, turn and other mutable fields must be 
restored separately by their owners. The modified Rust kernel uses structured 
returns without a deadline-abort path, whereas the legacy TypeScript search uses 
try/finally when it can throw a search-abort sentinel. 
Invariant and argument. Immediately before exploring each sibling, the working 
state must equal the state at the parent node. A successful apply changes exactly the 
selected empty cell and increments the count. Its matching undo clears that same 
cell and decrements the count; therefore these fields equal their former values. By 
induction over nested calls, assuming each recursive child restores every state field 
it owns, the parent sees the same state for the next sibling. The induction depends 
on legal matching calls; it is not guaranteed if an exception bypasses undo or a 
different move is removed.

2.3 Freestyle win detection 
The frontend win rule treats a contiguous line of at least five stones as a win, 
including an overline of six or more. It checks four axes through the last move, with 
both directions on each axis. It does not require exactly five or impose an additional 
two-blocked-ends condition [8]. The term Caro is used for the application, but this 
particular rule is specified explicitly because games with similar names may use 
other winning conditions. 
The procedure receives a valid board and the last placed coordinate m. It returns the 
winning player and collected winning cells, or no result. It assumes the preceding 
position was unfinished, so any newly created winning line passes through m. An 
arbitrary imported position instead requires a full-board result check at the search 
root. Under the frontend state contract, an empty last-move coordinate yields no 
winner [8]. 
For directions D = {(1,0), (0,1), (1,1), (1,-1)}, let f_d and b_d count consecutive 
stones equal to the stone at m in the positive and negative direction. A win through 
7 


=== PAGE 16 ===
the last move occurs exactly when some 1 + f_d + b_d ≥ K. To decide whether the 
threshold is reached, scanning at most K−1 matching cells in each direction is 
sufficient: any additional cells cannot change a negative result to a positive result 
after K−1 matching cells already exist on one side. 
// Algorithm 2.2 (CaroGame/src/game/core/WinRules.ts) — WIN_AT(B, m, 
K): 
    if m is out of bounds or B[m] is empty: return NONE 
    p ← B[m] 
    for d in [(1,0),(0,1),(1,1),(1,-1)]: 
        cells ← [m] 
        for sign in [+1,-1]: 
            for step from 1 to K-1: 
                q ← m + sign * step * d 
                if q is outside or B[q] ≠ p: break 
                append q to cells 
        if length(cells) ≥ K: return (p, cells) 
    return NONE 
The scan invariant is that every collected cell is on the selected axis, adjacent to the 
preceding segment and occupied by p. Stopping at the first boundary or different 
cell prevents joining disconnected sequences. If a contiguous run through m has 
length at least K, either its collected positive and negative portions together reach 
K−1 neighbors or a single portion does, so the check succeeds. Conversely, K 
collected stones form a contiguous same-player segment through m, establishing 
the stated rule. The returned display collection may be truncated to K−1 stones per 
side; it is sufficient to prove a win but is not necessarily the full maximal overline. 
For X X [X] X X on a row, with the bracketed cell placed last, each side contributes 
two stones and 1 + 2 + 2 = 5. For X X X [X] X X, the run exceeds five and is still a 
win. A gap or board edge stops the corresponding scan. With K = 5, the frontend 
examines at most 4 × 2 × 4 = 32 neighboring positions, giving O(K) time and O(K) 
space for the collected cells. These bounds are constant for the configured winning 
length. A full-board scan checks every occupied starting point and has a different 
cost; the report does not infer an elapsed-time speedup from the operation count 
alone.

2.4 Baselines: random play and rule-based play 
2.4.1 Random baseline 
A random baseline selects a legal move without comparing future replies. In the 
modified Rust snapshot, Easy first rejects an empty player or terminal board, 
enumerates empty cells, and selects an index using a seeded 64-bit mixer modulo 
the list length. It evaluates the chosen move afterwards to populate the result; that 
evaluation does not influence selection [10]. 
// Algorithm 2.3 (research/current_2026_10_23/SOURCE_EXCERPTS.md) 
— RANDOM_MOVE(B, p, seed): 
    if p is empty or B is terminal: return NONE 
    L ← all legal empty cells in B 
    if L is empty: return NONE 
    i ← SEEDED_INTEGER(seed) mod length(L) 
    return L[i] 
9 


=== PAGE 18 ===
The seed is part of the input because the mixer is deterministic. The output is a 
member of L or no move. A board with one stone has 224 empty cells, while a 
one-element list always returns its sole coordinate. Terminal handling precedes 
modulo selection, so a full board cannot cause division by zero. Index selection 
takes O(1) after enumeration. Modulo reduction does not in general produce an 
exactly uniform distribution over arbitrary list lengths. 
Gathering all cells takes O(N²) time and O(N²) space in the worst case; selection 
after that is O(1). A post-selection evaluation has its own cost. A fixed seed makes 
the selection reproducible under the same generator and ordering, not necessarily 
across different implementations or changed inputs. A random policy does not 
promise to notice an immediate win or threat. 
2.4.2 Immediate tactics and one-ply heuristic 
The modified Rust Normal policy selects an immediate win when one is available, 
then an immediate blocking coordinate, and otherwise the highest-valued one-ply 
candidate. Candidate assessment supplies the win and block markers [10]. The 
frontend has a separate tactical resolver for Hard, Very Hard, Expert and Master; 
Easy and Normal bypass it. A frontend tactical result identifies its source as tactical 
and reports zero Rust nodes, because it returns before a WASM request [3], [20]. 
// Algorithm 2.4 (research/current_2026_10_23/SOURCE_EXCERPTS.md) 
— RULE_BASED(B, p, policy): 
    if B is terminal or p is invalid: return NONE 
    C ← SELECT_CANDIDATES(B, p, policy) 
    if an m in C wins immediately for p: return m 
    if an m in C is an immediate winning cell for opp(p): return m 
    best_move ← NONE; best_score ← -infinity 
    for m in C: 
        APPLY(B,m,p) 
        try: 
            score ← TERMINAL_OR_EVALUATE(B,p,m) 
        finally: 
            UNDO(B,m) 
        if best_move is NONE or score > best_score: 
            best_move ← m; best_score ← score 
    return best_move, best_score 
10 


=== PAGE 19 ===
The decision invariant after processing the first j non-tactical candidates is that 
best_score is the greatest observed value among those j moves and the board is 
restored. A separate invariant places the win and block checks before the one-ply 
loop. Thus the routine picks the best score among the evaluated candidates when 
neither tactical condition applies. Correctness of the tactical marker itself depends 
on the assessment recognizing the corresponding winning geometry and on the 
move being included in C. 
For a concrete threat, suppose X occupies row 0, columns 0–3, column 4 is empty, 
and O is to move. The left endpoint lies outside the board; placing O at (4,0) blocks 
the only immediate completion along this row. If the same four consecutive X 
stones are in the interior with both endpoints empty, there are two distinct winning 
cells. A single O move can occupy one cell, not both. Retaining both choices avoids 
losing information but does not establish that either saves the game. Similarly, an 
immediate winning move for O takes priority over blocking if both are available 
under the algorithm's ordering. 
If k candidates are generated, one-ply evaluation costs roughly O(k × 
evaluation-cost), in addition to candidate generation and ordering. A constant-time 
local win scan does not make the whole rule-based procedure constant time. A 
nonterminal board with no generated move requires a defined fallback or no-move 
response; terminal handling must precede any selection. A short tactical prepass is 
not a substitute for searching through arbitrary combinations.

2.5 Static evaluation and terminal utility 
2.5.1 Evaluation of nonterminal positions 
A search with finite depth can stop before a winner exists. Its evaluator assigns an 
approximate score to that horizon position. In the documented modified Rust 
snapshot, evaluate scans maximal contiguous runs in four directions, adds the root 
player's run weights, subtracts the opponent's, and adds or subtracts a center 
preference. The snapshot counts a run once per axis by skipping a cell when the 
previous cell on the same axis has the same color. It then clamps the final heuristic 
to a range below terminal scores [10]. 
Let R_p(B) be maximal runs of p over the four axes, len(r) their length and open(r) 
their number of empty endpoints. Let c(x,y)=max(0,14−|x−7|−|y−7|) and C(B,p) be 
p's sum of c minus the opponent's. The descriptive formula is

EVALUATE(B, p):

After each visited run start, score contains the signed run contributions processed so

preceding-cell guard skips interior stones of the same run. Every maximal run 
therefore contributes once per axis, even when it contains several stones.

2.6 Candidate generation and a soft tactical cap 
2.6.1 Spatial neighborhood 
Considering every empty cell creates a large branching factor. A candidate policy 
can instead choose empty cells close to existing stones. For cells a and b, 
Chebyshev distance is d∞(a,b)=max(|a_x−b_x|, |a_y−b_y|). With radius r, a spatial 
candidate is an empty cell within distance r of at least one occupied cell. The empty 
board has a special center choice, and a full board has no move. The exact selection, 
fallback and ranking below describe the archived modified-engine policy, not the 
legacy bot's different forcing-move generator [10]. 
// Algorithm 2.7 (research/current_2026_10_23/SOURCE_EXCERPTS.md) 
— RAW_CANDIDATES(B, r): 
    if B is full: return []

                seen[q] ← true 
                append q to C 
    return C

board return no candidates [10].

2.7 Move ordering versus move selection 
A search traverses the retained moves in an order. Ordering permutes an already 
chosen set; filtering or capping changes its membership and therefore the tree itself. 
In a complete Minimax evaluation of the same deterministic tree, any permutation 
produces the same value, although a tied best move can differ if the first best move

=== PAGE 26 ===
is retained. In Alpha-Beta search, ordering influences how soon useful bounds are 
discovered and can alter the number of cutoffs, while preserving the root value 
under the algorithm's assumptions [23]. 
// Algorithm 2.9 (research/current_2026_10_23/SOURCE_EXCERPTS.md) 
— ORDER(retained_moves, rank): 
    calculate a rank key for each retained move 
    sort by the chosen key with a deterministic tie breaker 
    return the same moves in the new order 
If A, B and C have quick scores 10, 50 and 30, score order is B, C, A, whereas 
coordinate order may be A, B, C. Ranking B first does not establish that it is the 
best searched move. Minimax still evaluates every retained child; Alpha-Beta may 
reach a useful cutoff sooner. Sorting k moves takes O(k log k), plus key 
computation and O(k) move storage in the described implementation. Whether the 
saved search work outweighs ranking cost is measured in Chapter 5. 
The documented candidate selection uses fast local information for ranking; the

2.8 Minimax search 
2.8.1 Recurrence and contract 
Minimax assumes two alternating decision-makers. MAX chooses a move to 
maximize a score from the root player's perspective; MIN chooses to minimize it. 
Its input is the current board, the side to move, a nonnegative depth d in plies, the 
last move when available, a candidate policy and an evaluator. The output is a value 
and, at the root, a selected move, or no move for an already finished game. State 
includes the mutable working board, remaining depth, root perspective and 
recursion stack. Search must begin from a board compatible with the chosen rules, 
or validate it separately. 
Let U(s,R,q) be terminal utility at root distance q, and E(s,R) the nonterminal 
horizon evaluation. Transition T(s,a) places the side-to-move stone and changes the 
turn. For a fixed candidate function A and rule/evaluation configuration, the 
depth-limited value is 
V(s,d,q) = U(s,R,q) if s is terminal; 
V(s,0,q) = E(s,R) if s is not terminal; 
V(s,d,q) = max[a∈A(s)] V(T(s,a),d−1,q+1) if MAX moves; 
V(s,d,q) = min[a∈A(s)] V(T(s,a),d−1,q+1) if MIN moves. 
An empty generated set for a nonterminal board must have a specified behavior. 
The documented value routine returns zero for an empty list, while candidate 
fallback is intended to avoid this on a nonfull valid position. That fallback 
convention should not be silently reinterpreted as a win or as a comprehensive 
validation of arbitrary positions [10].

The root routine validates an existing result, searches each retained root move, 
stores a best action and restores the board after each branch. Recursive checks use 
the just-played coordinate, because a newly formed line passes through that move. 
The modified Rust implementation uses one recursive kernel whose configuration 
enables plain Minimax or Alpha-Beta pruning while retaining the same candidate 
policy and evaluator [10]. 
2.8.2 Proof, example and complexity 
Use induction on d. For terminal nodes or d=0 the procedure returns exactly the 
corresponding definition. Assume recursive results equal V for depth d−1 and that 
each apply/undo restores the parent. At a MAX node the loop's best value after j 
children is the maximum of the first j child values; at completion it is the maximum 
over A. The MIN case is symmetric. Each recursive call reduces d, so a finite 
candidate list guarantees termination. This proves evaluation of the specified finite 
tree if transition, terminal detection, evaluation and candidate generation satisfy 
their contracts; it does not prove the evaluator predicts the outcome of an 
unrestricted game.

2.9 Alpha-Beta pruning 
2.9.1 Bounds and pseudocode 
Alpha-Beta pruning computes the same root value as Minimax on the same finite 
deterministic tree under a consistent utility and candidate policy, while sometimes 
skipping subtrees. alpha is the best lower bound MAX can already secure in the 
current ancestor context; beta is the best upper bound MIN can already secure. At a 
MAX node, update alpha after observing a child; at a MIN node, update beta. When 
alpha ≥ beta, the remaining siblings cannot improve the relevant ancestor's decision. 
Knuth and Moore analyze Alpha-Beta and the effects of move ordering under stated 
assumptions [23].

2.10 Iterative deepening and budgets 
Iterative deepening performs complete searches at depths 1, 2, … until reaching a 
configured maximum or a budget interrupts an iteration. Its input is a root position, 
a maximum depth and a budget. Its output should distinguish the best result from 
the most recently completed iteration, the completed depth, and the reason for 
stopping. The working board, search counters, and any table or ordering hints must 
23 


=== PAGE 32 ===
obey the respective implementation's lifecycle. An incomplete iteration's partially 
explored best move is not the same as a completed Minimax result for that depth. 
// Algorithm 2.12 (completed-iteration scheme illustrated by [11]) — 
ITERATIVE(B, maximum_depth, budget): 
    last_complete ← NONE 
    for depth from 1 to maximum_depth: 
        if budget is exhausted: break 
        result ← SEARCH_AT_DEPTH(B, depth, budget) 
        if result was interrupted: break 
        last_complete ← result 
    return last_complete, completed depth, stop reason 
The invariant after iteration d is that last_complete corresponds to a whole 
completed search at d under that iteration's search contract. It follows inductively 
because the result is replaced only after the iteration returns normally. A separate 
abort-safe restoration guarantee is required: interruption in a child must unwind all 
applied moves. If depth one returns A, depth two returns B and depth three aborts, 
the completed result is B at depth two. If no iteration completes, a caller must 
explicitly handle the absence of a completed result; a fallback candidate is useful 
but should be labeled as such. 
Repeated shallow searches consume work, although the deepest full iteration can 
dominate for a sufficiently large, regular branching factor. Each iteration has the 
complexity of its selected search; total time is the sum over attempted depths plus 
ordering and bookkeeping. No hard real-time guarantee follows from this scheme. 
A search interrupted only at periodic checks can exceed its nominal wall-clock 
deadline before the next check, especially if individual operations are expensive. 
The legacy TypeScript findBestMove uses a performance.now() deadline, checks it 
at the first search node and every 32 nodes, and catches a dedicated abort sentinel. 
It initializes a fallback candidate before an iteration completes and reports depth 
zero if the first iteration aborts. Recursive search uses try/finally to undo moves 
during unwinding [15]. The historical Rust reference instead uses a node budget, 
and its aggregate excludes work inside an aborted iteration [13]. The modified Rust 
engine uses the fixed tier depths shown in Table 2.1 [10]. These are separate budget 
and counter conventions.

2.11 Zobrist hashing and incremental state 
2.11.1 Definition and update 
A transposition can arise when different sequences of moves lead to the same board 
and relevant side to move. Comparing all cells at each cache access costs O(N²), so 
a compact hash can serve as an index. Zobrist's method assigns a pseudorandom 
word to each (cell, player) pair and combines the keys for occupied cells with 
exclusive OR (XOR) [25]. One also needs a side-to-move key if the same 
occupancy can be evaluated with different players to move. The hash is a compact 
fingerprint, not mathematical proof that two states are identical. 
Define Z[x,y,p] as a fixed random word for a stone, and S as a fixed side key. Under 
one convention, 
H(B,p) = XOR Z[x,y,color] over occupied cells, XOR S if p is the designated 
second side. 
All keys must remain fixed for the lifetime of the table. Applying a move of p at m 
adds its key with XOR. If the transition changes the side, XOR S as well. Undo 
repeats the same XOR operations in reverse. The essential identity is (h XOR z) 
XOR z = h.

2.12 Transposition table: entries, bounds and context 
2.12.1 Meaning of stored values 
A transposition table (TT) maps a position fingerprint to a previously computed 
search result. A typical entry stores a hash or verification key, remaining search 
depth, value, bound type and a suggested best move. The move may help order later 
search even if the stored score is unusable. A cache lookup is sound only when its 
represented search problem is compatible with the current one, its depth is 
sufficient under the selected contract, and its bound justifies the requested cutoff or 
exact result. 
For an original search window [α₀,β₀], a common classification is: result v ≤ α₀ is an 
upper bound; v ≥ β₀ is a lower bound; and α₀ < v < β₀ is exact, subject to the search's 
assumptions. Equality is treated conservatively at the boundary. For instance, with 
window [3,8], a returned 2 is an upper bound, 5 is exact and 9 is a lower bound. 
Consequently, a stored LOWER bound triggers an immediate cutoff whenever 
entry.score ≥ β, and an UPPER bound triggers a cutoff whenever entry.score ≤ α.

    if entry.bound = EXACT: return VALUE(entry.score, hint) 
    if entry.bound = LOWER and entry.score ≥ beta: 
        return VALUE(entry.score, hint) 
    if entry.bound = UPPER and entry.score ≤ alpha: 
        return VALUE(entry.score, hint) 
    return HINT_ONLY(hint)

    if score ≤ alpha_original: bound ← UPPER 
    else if score ≥ beta_original: bound ← LOWER 
    else: bound ← EXACT

The probe is sound only when the key, search context, score convention and depth 
interpretation are compatible. Checking depth, bound type and move legality alone 
does not establish all of these conditions. Classification uses the original search 
window, and storage and retrieval must agree about fail-hard or fail-soft returns. A 
conventional entry.depth ≥ required_depth test accepts deeper results; strict equality 
with a particular depth-limited horizon requires an additional depth-reuse contract. 
2.12.2 Why reuse can be wrong 
A useful invariant is: whenever a TT score is reused, it is valid for the current 
position, depth interpretation, perspective, rule set, evaluation and move-generation 
context, and its bound permits the intended conclusion. An exact compatible entry 
may answer a query; a lower or upper bound is usable only in its permitted 
direction. If any premise is false, the stored number can change the decision. A full 
hash comparison narrows ordinary index collisions but still does not guarantee that 
different game states cannot share a fingerprint.

and changing the root player, a fresh table returns 0 and the reused table returns

The legacy TypeScript table uses fixed-size parallel arrays. A slot is indexed from 
the low hash half, then both halves are compared before its depth, flag and score are 
considered. The stored move is used as an ordering hint [15]. The native reference 
instead uses a hash map [13]. These storage choices do not establish compatibility 
between search contexts. A hint must refer to a legal retained move before it 
influences move application, and cache lifetime must match the interpretation of its 
stored scores. 
Expected lookup is O(1) for a suitably configured hash table; actual access cost 
depends on indexing, collisions and replacement. Memory is proportional to 
allocated slots or entries, together with container overhead. A hash map's initial 
capacity is not a maximum, and the size of one entry is not the container's total 
allocation. A TT can save repeated search work and supply move hints, at the cost 
of memory and the need to preserve compatible score and state semantics.

2.13 Quiescence search in the legacy TypeScript bot 
A fixed-depth horizon can fall immediately before a forcing reply, causing a static 
evaluation to overrate the position. Quiescence search extends selected tactical 
continuations beyond that horizon. The legacy TypeScript bot implements this 
extension with a separate depth limit and forcing-move generator [15]. Its result 
describes that selective continuation tree. 
Inputs and state. The legacy routine receives the board, alpha and beta bounds, 
current ply and a quiescence depth. It works from the perspective of the side to 
move, uses negamax sign reversal, increments a node counter and checks for abort. 
Its state includes board cells, side, hash and cached pattern counts. Its output is a 
bounded score for the selected forcing continuation, or an abort propagated to the 
caller. It first checks whether either side has a five pattern. It then calculates 
standPat, applies a beta cutoff if that static score is at least beta, raises alpha if 
appropriate, and stops at quiescence depth five. Otherwise it generates forcing 
candidates, orders them and recurses after a move with (-beta,-alpha); each 
recursive branch uses try/finally to undo [15].

perspective changes with the side to move. The procedure returns beta on a 
fail-high and alpha otherwise, so its return can be a bound rather than an exact 
unrestricted game value. Its loop invariant is that alpha is at least the stand-pat score 
and all examined forcing continuations, subject to the window and fail-hard 
convention; the board must equal the incoming state before every sibling. The depth 
limit guarantees termination even when forcing candidates continue to exist. It also 
creates a new horizon.

and the first searched forcing move returns 6 after sign reversal. Alpha rises to 6. If 
another move returns 12, the routine returns beta, 10, as a fail-high bound. This 
does not assert that 10 is the exact Minimax value. In a real position, the forcing 
generator's definition and threat patterns decide which moves are included. The 
legacy code considers outcomes such as five, open four and four for either side 
when identifying forcing moves. These categories arise from its own bitmask

2.16 Synthesis and limits of the algorithmic claims 
The algorithms in this chapter have different responsibilities. Win detection decides 
the stated terminal rule; board mutation maintains a position; random and 
rule-based choices provide baselines; the evaluator assigns an approximate horizon 
value; candidate generation restricts the moves explored; ordering permutes the 
retained moves; Minimax evaluates the resulting tree; Alpha-Beta skips provably 
irrelevant branches of that same tree; iterative deepening manages progressive 
search; and hashing plus a transposition table aim to reuse compatible earlier work. 
Quiescence extends a selected class of tactical moves at a horizon, but its own 
assumptions and depth limit remain. 
The current decision path uses frontend tactical checks and a Worker-hosted WASM 
request. The modified Rust source explains board updates, Freestyle detection, 
candidate generation, horizon evaluation and fixed-depth Alpha-Beta. The legacy 
bot supplies the iterative-deepening, hashing, transposition-table and quiescence 
examples. Their contracts are examined independently: candidate selection defines 
the searched tree; ordering changes its traversal; and Alpha-Beta preserves 
Minimax's root value for that same tree under the stated assumptions. 
Chapter 5 evaluates the recorded implementations using native search experiments, 
WASM parity checks and browser Worker observations. Each result is interpreted 
with its own position, configuration, platform and counter definition. The 
theoretical arguments in this chapter establish properties of specified algorithms; 
the experiments assess those properties on the recorded finite fixtures [13], [19], 
[31], [32].

3.2 Non-functional requirements and acceptance boundaries 
Correctness means preserving legal state transitions, the agreed rule and the relation 
between board cells and history. Maintainability means keeping rule evaluation, 
rendering, input conversion and asynchronous search behind identifiable interfaces. 
Responsiveness motivates the Worker boundary for substantial search, while correct 
cancellation requires more than moving work off the main thread. Reproducibility 
requires a source revision, binary identity, configuration and measurement 
procedure rather than a screenshot containing a duration. 
The Rust/WASM route runs inside a dedicated Web Worker, separating its 
synchronous search from the main thread that handles React and Pixi. Cancellation 
terminates the Worker, while controller guards determine whether a completed 
response still belongs to the active turn. Easy and Normal use Rust baseline 
policies; the four higher tiers use fixed-depth Alpha-Beta unless the TypeScript 
tactical resolver supplies an immediate move.

3.4 Board state, history and legal transition contract 
The frontend GameState stores one value per cell and an ordered move history. A 
move records its player, cell and index; history is also the input used to reconstruct 
a fresh Rust game for a search. These two uses require consistency. If a board cell 
changed without a corresponding history update, the display could show one 
position while the engine searched another. The transition contract therefore relates 
the occupied-cell set to the history sequence rather than treating them as 
independent data [18]. 
The board has N = 15 and N² = 225 cells. Frontend coordinates are (row, column); 
Rust uses (x, y), where x = column and y = row. A row-major linear index is row × 
N + column. The pointer transform applies floor before checking board bounds. 
The WASM result adapter checks integer coordinates and bounds before converting 
them to a frontend cell [30], [35]. 
The playMove operation checks bounds and occupancy, commits an accepted move 
to cells and history, and evaluates the supplied win rule. GameController supplies 
the current player and checks pause, phase and AI-turn availability. Geometric win 
detection remains in the rule object, while match and request lifecycle checks 
remain in the controller [2], [36]. 
The history sequence is not merely a move counter. It preserves alternation and the 
exact order needed for hydration. A full board without a winner is declared a draw 
after the win test. That order matters on the last empty cell: a winning final 
placement must remain a win rather than being classified as a draw merely because 
the board is now full. The controller's finishMove uses this ordering [2]. 
3.5 Match phases and state transitions

ready, local two-player mode, normal difficulty and round identifier zero. Calling 
playCell from setup or ready invokes startRound, which increments the round 
identifier, clears the old outcome and enters playing. An accepted win or full-board 
draw changes the match to game-over. The thinking flag belongs to the AI request 
lifecycle; it is not a fifth value in the phase enumeration [33], [2].

3.6 Asynchronous request protocol and cancellation 
An AI action captures a new turn token, the round identifier and difficulty before 
setting thinking state. The request contains a copied move history. The transport 
wrapper adds its own message identifier so the correct pending promise receives the

3.8 Search-result contract and presentation of telemetry 
The Rust result validator requires in-bounds integer x and y coordinates, a finite 
score, matching difficulty, a recognized strategy and nonnegative safe-integer 
counters. The counters report visited nodes, leaf evaluations, cutoffs, ordering 
evaluations, generated candidates and completed depth. A coordinate-only result or 
another incompatible payload raises a contract error [14], [30]. 
The adapter maps the fields into application terminology and explicitly labels the 
source as Rust. Its elapsed timer starts before construction and history hydration, 
includes ai_move and free, and ends after cleanup. It excludes module loading and 
message delivery. A displayed duration therefore has a defined scope: it is not a 
complete user-perceived round trip and is not a measurement of only the recursive 
search. The tactical route instead labels its source as tactical, reports zero Rust 
search counters and a null score. Zero counters on that route mean Rust search was 
bypassed, not that a nontrivial Rust tree required no work [3], [30]. 
Configured depth describes the requested policy; completed depth is returned 
telemetry. Candidate selection, terminal states and the selected strategy determine 
the work represented by that result. The interface therefore presents depth alongside 
strategy, source and counters rather than using a difficulty label as a measurement.

the match remains playing in AI mode with O to move. Chapter 6 discusses the 
ordering of the initial phase transition and cell validation [2], [36]. 
The sequence is deliberate. Notification occurs after the accepted domain change, 
so the interface receives a coherent snapshot. The AI request is based on the 
updated history, not on a speculative screen state. Rule evaluation occurs through 
the supplied FreestyleGomokuWinRule. The scene never paints a permanent stone 
merely because a pointer event arrived; it renders the state returned through the 
controller. This permits the same move contract to reject an occupied cell 
consistently in the UI and in tests. 
Undo is implemented by history reversal. In local two-player mode it removes one 
ply. In AI mode, if the last recorded player is O, it removes two plies; otherwise it 
removes one. Before reversal it invalidates AI work and clears search feedback. It 
then determines the current player from the remaining last move, asks the match 
controller to resume after Undo and notifies. Popping two plies when the AI has 
already replied returns the board directly to the human player's decision turn while 
preserving chronological history integrity [2].

5.4.2 Candidate caps, ordering and tactical completeness 
Candidate generation reduces the set of considered moves by selecting empty cells 
near existing stones. This can reduce branching but changes the search problem. 
The reference cap_loss.json supplies a concrete risk: in the synthetic win fixture at 
radius one, 20 uncapped candidates include two immediate winning endpoints (7,2) 
and (7,7), but a cap of six omits both. At depth one, the uncapped score is 9,999,999 
and the capped score is 99,990. This is not an Alpha-Beta error: it is a difference in 
which moves are admitted before the search. It demonstrates why an ordering or 
cap policy must be evaluated against tactical membership, and why a value equality 
proof applies only after the move set is fixed [22]. 
The 23 October engine uses a different candidate policy, with a soft cap that retains 
immediate tactical completions. Its record includes twelve tactical-completion 
retention checks. The reference counterexample and the later retention checks 
therefore describe different policies. A controlled comparison must keep candidate 
membership fixed before attributing a change in work to ordering or Alpha-Beta 
pruning.

5.7 Threats to validity and interpretation 
Internal validity. Search comparisons require the same position, depth, terminal 
rules, evaluation perspective and candidate set. Otherwise an apparent improvement 
can arise from searching a different tree. A table that ignores rule or perspective 
context can return a stale value. An aborted iteration must be counted separately 
from completed work. These issues are directly motivated by the cap-loss, 
cache-scope and budget probes. 
Measurement validity. The native experiments distinguish recursive nodes, leaf 
evaluations, ranking evaluations, cutoffs and time. Treating one counter as a 
substitute for all computation can reverse the apparent conclusion, as the clustered 
ordered example shows. Three sequential timing repeats and lack of randomized 
order, CPU isolation or uncertainty intervals support descriptive comparisons only. 
Native timer scope, Worker hydration and search, and browser round-trip duration 
are different quantities. 
External validity. The fixtures cover controlled and seeded boards but not the full 
space of legal games. Tactical test positions may be synthetic. A 100-game 
Rule-Based versus Random result is narrow, and it does not calibrate six difficulty 
levels against human skill. Node execution and headless-browser synthetic input do 
not establish physical touchscreen, Wink host, deployment or production behavior. 
Reproducibility and provenance. The repository supplies raw measurements, 
harnesses, source excerpts and binary hashes. The 12 November follow-up matched 
36 available engine, reference, harness and lock files to their archived hashes and 
reproduced the non-timing search results. The native source trees available in the 
local workspace are not all tracked in the examined application repository. Chapter 
6 addresses publication of a complete source-and-build package; Appendix B 
records the present artifact mapping. 
CHAPTER 6. CONCLUSION AND FUTURE WORK 
6.1 Work completed and contribution 
The project implements a Caro web application and a teaching website for board 
representation, Freestyle rules, heuristic evaluation and adversarial search. The 
application connects a React interface and PixiJS board to a Rust/WebAssembly 
search Worker. The teaching website provides visual explanations and executable 
Python examples. Weekly reports and native research artifacts document the 
algorithmic development and its experimental evaluation [1], [53]. 
62 


=== PAGE 71 ===
The main contribution is an implementation-level account of how game decisions 
depend on representation and search policy. Board updates, history and rollback 
support recursive exploration. Terminal utility takes precedence over the static 
heuristic. Minimax defines alternating decisions, and Alpha-Beta pruning preserves 
the value of the same selected search tree while omitting branches that cannot 
change it. Candidate filtering changes the tree itself; ordering changes the sequence 
in which its moves are examined. The reference experiments extend this analysis to 
Zobrist hashing, transposition-table bounds and interrupted iterative search [11], 
[13]. 
The recorded native engine experiment reports 408 Minimax/Alpha-Beta 
comparisons with matching values and 820 successful restoration checks. Separate 
adapter and browser records exercise the connection between search and the 
application. In the reference experiments, move ordering reduced visited nodes on 
some positions, but its additional evaluation work could outweigh the saving in 
elapsed time. A hard candidate cap discarded immediate wins in one fixture, and 
cache reuse after a root-player change produced an incorrect score in another. These 
results show that search depth and node count alone are insufficient to assess 
correctness or efficiency [19], [31], [32], [49], [22], [27]. 
6.2 Limitations 
The active search is selective. Its soft tactical cap retains immediate winning and 
blocking completions, but deeper positional moves remain subject to the candidate 
limit. The configured limit falls from 15 at Hard to 8 at Master as depth rises from 
two to five plies. The static evaluator scores contiguous runs; gapped formations 
and intersecting threats depend on tactical assessment and deeper search. Persistent 
transposition tables and iterative-deepening budgets are studied in separate 
implementations rather than used by the active Rust search [10], [29], [13]. 
The implementation review also identifies boundary cases for further correction. 
GameController starts a round before validating the first direct move request, and 
the core coordinate predicate checks bounds without requiring integer indices. The 
normal pointer path supplies integer cells, while Worker responses have a separate 
integer check. Drag detection compares consecutive pointer positions, which can 
miss a slow drag made of small steps. In the teaching website, a failed or missing 
Pyodide loader can leave initialization state or waiting callers unresolved [2], [35], 
[37], [43].

The measurements cover a finite corpus and specific native or browser 
environments. The published snapshot includes the application and its binary, but 
the complete modified Rust engine and the caro-core-reference dependency are 
absent from that Git tree, limiting reproduction from a fresh clone. Historical timing 
and bot-match summaries also have narrower provenance than the controlled 
research records. Physical-device interaction, live host integration, human usability 
and calibrated playing strength remain subjects for further evaluation [1], [13], [46], 
[24], [11], [52]. 
6.3 Future development 
Reproducibility is the first development priority. A complete release should include 
the modified engine and reference library together with their manifests, lockfiles, 
experiment harnesses and build commands. Each experiment should identify the 
source revision, toolchain, platform and binary hash. The earlier baseline should 
remain available for comparison under its own identity. 
Input validation and lifecycle handling should be strengthened at their owning 
boundaries. The core should require integer coordinates and validate a move before 
advancing the match phase. Gesture classification should use displacement from the 
initial press, and the Pyodide loader should settle all waiting requests and permit 
retry after failure. Regression cases should include invalid first moves, fractional 
inputs, slow drags and failed runtime initialization. 
Further search evaluation should separate candidate selection from move ordering. 
A fixed corpus of reachable positions can compare all-legal search with radius and 
cap policies, including known wins, blocks and intersecting threats. Useful outputs 
include missed tactics, chosen moves, root values, ranking evaluations, recursive 
visits and elapsed time. Multiple seeds and explicit tie handling would make the 
comparison less dependent on one fixture. 
Persistent caching requires a defined compatibility context. Future work should 
include rules, evaluation weights, root perspective and mate-distance treatment in 
the cache design, then test exact, lower and upper bounds across depths and search 
windows. Warm-table and cold-table comparisons should include root changes and 
collisions. Memory measurements should include map capacity and allocation 
overhead as well as entry size. 
An anytime search could combine iterative deepening with cancellation and an 
explicit last-completed-result policy. Its telemetry should distinguish requested 
depth from completed depth and count work spent in aborted iterations. Tests 
64 


=== PAGE 73 ===
should cover Reset, Undo, stale replies and Worker failure while confirming that 
interrupted search restores the input position. 
Application evaluation should extend to physical target devices and the intended 
host environment. Repeated measurements of response latency and frame timing 
would complement the present automated checks. A participant study could 
examine control usability and perceived difficulty, while a multi-seed tournament 
against stated opponents could assess playing strength. Both require a documented 
protocol before their results can support conclusions. 
The teaching website should remain synchronized with the implementations it 
explains. Illustrative programs need explicit scope, especially where a horizontal 
example accompanies a four-direction rule description. Charts should link to the 
data and generation procedure that produced them. This would let readers move 
from an explanation to the corresponding source or experiment without confusing a 
demonstration with a measurement.
